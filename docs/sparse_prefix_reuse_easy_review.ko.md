# Sparse KV reuse의 불필요한 작업: 쉬운 설명

기준: `baek2sm/nntrainer`, `kv/sparse-prefix-reuse-20261110`, 커밋 `73f8feec4`.
HTP의 KV Manager와 sparse reuse가 **정상적으로 성공할 때도 드는 비용**을 우선 검토했다.

**손상이 흔하다는 근거는 없다.** 앞선 검사는 읽기 실패 등을 의도적으로 넣어 취약한 경로를
찾은 것이다. 발생 빈도를 측정한 것이 아니므로, 이를 성능 수정의 최우선 이유로 삼기는 어렵다.
이번 검사는 손상이나 실패를 주입하지 않았다.

## 먼저 이해할 두 가지

KV는 모델이 앞부분을 읽고 만든 계산 결과다. 같은 부분을 다시 읽을 때 가져다 쓰면 계산을
줄일 수 있다. Sparse reuse는 중간이 삭제된 입력에도 남은 부분의 KV를 모아서 쓴다.

```text
기존 입력: A B C D
새 입력:   A   C D E

A는 그대로 사용
C D는 앞으로 옮기고 K의 위치 정보를 보정
E는 새로 계산
```

위치를 보정하는 연산이 RoPE다. 옮긴 K에는 필요하지만 V는 그대로 복사한다.
Sparse 자체는 근사 재사용이다. 위치를 맞춰도 삭제된 내용을 과거에 참고한 영향까지 지우지는
못한다. 여기서는 그 알고리즘 성질과 별개로, 같은 결과를 내면서 줄일 수 있는 작업을 찾았다.

## 1. 복사해 놓고 바로 전부 덮어쓴다 — 먼저 고칠 만하다

현재는 옮겨야 할 K를 새 버퍼에 일단 복사한다. 그 버퍼를 다시 읽어 위치를 보정한 뒤,
보정 결과로 전체를 덮어쓴다.

```text
현재: 원본 → 새 버퍼에 복사 → 다시 읽어 위치 보정 → 새 버퍼에 저장
개선: 원본을 읽어 위치 보정 → 새 버퍼에 저장
```

중간의 복사는 없어도 된다. 원본을 수정할 필요도 없다. 검사한 FP16/FP32 입력에서 기존
구현과 바이트 단위로 같은 결과를 얻었다. V 복사와 위치가 그대로인 K의 복사는 남겨야 한다.

저장소에 기록된 Gemma4 구성에서 source 24K 중 4K를 삭제해 20K를 재사용하는 예를 계산하면,
이 사전 복사의 payload가 **260MiB**다. 기기에서 측정한 속도나 DRAM 절감량은 아니다.

코드: `Applications/CausalLM/kv_cache_manager.cpp:952–983`.

## 2. 0으로 채우고, 그 0을 한 번도 쓰지 않는다

새 K/V vector를 `resize()`하면 메모리를 0으로 채운다. 그런데 성공한 gather는 그 공간을
원본 KV 또는 보정 결과로 전부 채운다. 앞서 기록한 0은 최종 결과에 기여하지 않는다.

같은 실제 geometry의 destination K+V는 **600MiB**다. 600MiB를 0으로 채운 뒤 다시 쓰는
구조인 셈이다. 초기화하지 않는 소유 버퍼나 arena로 바꿀 여지가 있다.

다만 `resize()`를 `reserve()`로만 바꾸고 쓰면 안 된다. vector의 유효 크기와 객체 수명 규칙을
지키는 저장 형식 변경이 필요하다. 다른 종류의 KV 버퍼 초기화까지 모두 없애자는 뜻은 아니다.

코드: `kv_cache_manager.cpp:944–950`.

## 3. 전혀 바뀌지 않은 앞부분까지 새 사본을 만든다

위 예에서 삭제 전의 A는 위치도 값도 그대로다. 하지만 지금은 A의 KV도 새 page에 복사한다.
완전한 64행 page이고 source/destination 경계가 맞으면 기존 immutable page를 함께 소유할 수 있다.
옮긴 부분과 경계 부분만 새로 만들면 된다.

호스트 검사에서는 이 변경으로 데이터 버퍼 할당 640회와 page 객체 할당 320회를 줄였다.
실제 geometry로 계산하면 global 앞 4K의 **80MiB**를 새로 만들지 않아도 된다.

이미 sparse source를 작은 owned page로 저장하도록 고친 부분은 유지해야 한다. page 하나를
공유하려고 커다란 RPC slab 전체를 붙잡는 구조로 되돌리면 효과가 뒤집힐 수 있다.

코드: `kv_cache_manager.cpp:942–955`.

## 4. 임시 KV를 실제 버퍼로 복사한 뒤에도 임시본을 보관한다

현재 데이터 흐름은 다음과 같다.

```text
원본 KV → 모아서 만든 snapshot → 실제 계산용 host 버퍼 → HTP 처리
```

모아서 만든 snapshot과 실제 host 버퍼는 별개라서 KV 전체를 한 번 더 복사한다.
이 복사는 현재 버퍼 구조와 복원 절차에서 역할이 있다. 한 줄만 삭제할 수 있는 종류는 아니다.
최종 계산용 버퍼가 될 staging 영역에 직접 모으고 검증 후 연결하면 줄일 여지가 있다.

더 작은 수정은 복원 완료 뒤 **필요가 끝난 임시 snapshot을 해제**하는 것이다. sparse 결과는
새 exact source로 게시하지 않는데도 history가 참조를 유지한다. 같은 예에서는 600MiB가
생성 중에도 남을 수 있다. 일찍 해제해도 gather 순간의 최대 메모리까지 없어지는 것은 아니다.

기존 benefit benchmark는 prefill 직전에 이 history를 해제한다. 일반 실행 경로와 보관 시간이
다르므로, benchmark의 메모리 수치를 그대로 일반 경로에 적용해서는 안 된다.

코드: `models/causal_lm.cpp:1971–1987,2250–2264`, `kv_cache_manager.cpp:1022–1030`.

## 5. 버릴 행이라는 것을 알면서도 하나씩 방문한다

Sliding layer는 마지막 1,024행만 필요할 수 있다. 그런데 현재는 긴 run의 처음부터 순회하며
범위 밖인 행마다 `continue`한다. 필요한 첫 행에서 바로 시작하면 된다.

24K→20K 예에서 global을 포함한 행 루프 실행은 **512,000→128,000회**로 줄었고 결과는 같았다.
버리는 384,000회 반복을 없앤 것이다. 전체 실행시간이나 TTFT가 75% 줄었다는 뜻은 아니다.

코드: `kv_cache_manager.cpp:918–928`.

## 6. page마다 여러 번 할당하고, page 목록도 조금씩 늘린다

위 예에는 2,000개 page가 필요하다. page마다 객체 한 번, K 버퍼 한 번, V 버퍼 한 번으로
6,000회 정도의 할당이 발생한다. 목록과 scratch까지 포함한 호스트 계측값은 6,237회였다.

목록의 최종 크기는 미리 안다. `dst.pages.reserve()`만 추가해도 이 환경에서 145회가 줄었다.
다만 절감하는 메타데이터는 약 61KiB라서 수백 MiB KV 복사보다 우선순위가 높지는 않다.
더 큰 변화는 결과 snapshot 단위의 arena나 반환 가능한 page pool이다.

코드: `kv_cache_manager.cpp:914–916,944–950`.

## 7. 위치 정보가 없는 차원까지 위치 보정한다

Gemma4 global layer는 차원의 25%만 rotary다. 나머지는 주파수가 0이라 수학적으로 값이
그대로다. 현재는 그 차원까지 FP16→FP32 변환, identity 회전, FP16 저장을 한다.
실제 rotary 차원만 보정하고 나머지는 비트를 복사하는 최적화가 가능하다.

이 후보는 앞선 복사 제거보다 검증 부담이 크다. identity 연산도 signed zero 같은 비트를
바꿀 수 있어 기존 구현과 무조건 bitwise 같다고 할 수는 없다. 전체 모델의 75%를 줄이는
이야기도 아니다. 위 네 가지 호스트 변경 실험에는 포함하지 않았다.

HTP의 sin/cos는 이미 layer/run당 한 번 계산한다. 같은 삼각함수를 토큰마다 반복한다는
CPU core의 별도 지적을 HTP에도 적용하면 안 된다.

## 8. KV Manager 자체에도 작지만 확실한 중복 작업이 있다

- `publish()`는 소유 token vector를 만든 뒤 map에 넣을 때 다시 깊은 복사한다. move로
  줄일 수 있다. 다만 vocabulary의 남는 capacity까지 함께 넘기면 장기 보관량이 늘 수 있어
  용량 정리가 필요하다. 24K token vector 한 개는 96KiB다.
- prefix 개수 한도에 도달하면 옛 항목 제거 후 radix를 한 번, 새 항목 삽입 후 또 한 번
  재구축한다. 정상 성공 경로에서 한 번으로 줄이되 실패 시 owner 복구는 유지해야 한다.
- 같은 길이의 sparse 후보는 run 수가 적거나 resident인 쪽이 더 쌀 수 있다. 지금은 길이만
  비교한다. 1 run 대신 192 runs 후보를 고르는 사례도 앞선 호스트 검사에서 확인했다.
- 모델의 고정 RoPE 정보도 restore마다 다시 만든다. token vector 역시 몇 번 복사한다.
  줄일 수 있지만 대용량 KV 복사와 같은 급의 병목으로 볼 근거는 없다.

코드: `device_kv_manager.h:248–252,306–326,365–373,421–442`.

## 무엇을 실제로 확인했나

원래 `gatherSparsePrefix()`를 수정 없이 빌드해 비교 대상으로 삼았다. 계측본과 네 가지 누적
변경본은 FP16/FP32, RoPE 배치, 부분 page 등을 포함한 180회 대조에서 같은 바이트를 만들었다.
큰 입력에서도 결과가 같았고 원본 KV가 바뀌지 않았다. 실패·손상은 주입하지 않았다.
독립 gather 함수와 검사 fixture의 ASan/UBSan 검사도 통과했다.

큰 입력은 30 layers와 24K→20K 배치를 유지하되 head 크기를 축소했다. 이 호스트 실험의
payload는 31.25MiB다. 위의 260/600/80MiB는 실제 Gemma4 geometry로 따로 계산한 수치다.
HTP 실기기 TTFT, DRAM 트래픽, 전체 모델 품질을 이번 환경에서 측정하지 않았다.

수정 순서는 **K 사전 복사 제거 → sliding 시작점 조정과 pages reserve → exact page 공유와
임시 snapshot 해제 → arena/직접 gather → 부분 RoPE와 후보 비용 평가**가 적절하다.
