# Gemma에서 KV 한 묶음을 읽는 시간이 두 배가 된 이유 찾기

Android CPU 기기 실험 인계서 · Gemma 4 E2B · `kv-cache-fsu`

**첫 실험은 롤링을 끈 채로 한다.** 이전 이어쓰기에서 기본 FSU는 KV 한 묶음을 평균 2.88 ms, 롤링은 6.09 ms에 읽었다. 그런데 같은 기기의 **같은 고정 설정**도 실험 차수에 따라 2.53~2.59 ms와 5.81~6.02 ms로 갈렸다. 먼저 이 차이를 같은 세션에서 재현한다. 그다음 파일 읽기가 늦어진 구간과 실제 디코드가 기다린 구간을 각각 찾는다.

## 1. 무엇을 측정하는가

- **FSU**는 여기서 CPU가 attention에 필요한 과거 K와 V를 파일에서 DRAM 버퍼로 읽어 오는 실행 경로다. **한 묶음**은 캐시를 소유한 레이어 하나의 K와 V를 함께 가져오는 작업이다. 다른 레이어가 이 캐시를 공유할 수 있다.
- **선읽기**는 레이어가 KV를 요구하기 전에 읽기를 제출하는 것이다. **고정**은 정해진 예산 안의 빈 공간을 사용한다. **롤링**은 공간이 풀리면 다시 제출할 수 있고 필요할 때 상주 공간을 빌릴 수 있다. **32/4**는 총 KV 예산 32 MiB, 그 안에서 토큰 사이에 데이터를 보존할 상한 4 MiB다.
- **묶음 시간**은 작업자가 읽기를 시작해서 K와 V가 모두 준비될 때까지의 경과 시간이다. 선읽기 작업자가 시작하기 전의 큐 대기는 이 타이머 밖이다. **파일 읽기 시간**은 K와 V 각각의 `pread()` 루프 안에서 흐른 시간이다. CPU가 실행권을 잃은 시간도 포함할 수 있다. K와 V를 동시에 읽으면 두 구간이 겹친다.

기존 세 번째 요청(이어쓰기, 192토큰)의 출발점은 다음과 같다. 수치는 새 기기의 합격선으로 쓰지 않는다.

| 실행 | 묶음 수 | MiB/묶음 | 평균 ms/묶음 | K·V 파일 읽기 시간 합계, ms/묶음 |
|---|---:|---:|---:|---:|
| 기본 FSU, 상주 0, 깊이 1 | 1,351 | 2.172 | 2.884 | 5.241 |
| 고정 32/0, 깊이 1, 1차 두 실행 | 1,351 | 2.172 | 2.532 / 2.593 | 4.670 / 4.449 |
| 고정 32/0, 깊이 1, 2차 및 재확인 | 1,351 | 2.172 | 5.811 / 6.016 | 11.251 / 11.691 |
| 고정 32/4, 깊이 2 | 1,147 | 2.174 | 9.204 | 15.187 |
| 롤링 32/4, 깊이 2 | 1,147 | 2.174 | 6.088 | 8.804 |

두 번째 요청도 중요하다. 고정 32/0의 첫 측정과 2차 측정에서 K·V 병렬 읽기는 모두 0회였다. 묶음 시간이 2.415 → 5.916 ms로 늘 때 파일 읽기 구간도 2.414 → 5.914 ms로 늘었다. 이 요청을 함께 보면 V 작업자 대기와 저장소 경로를 혼동할 가능성이 줄어든다. ## 2. 같은 세션에서 재현하기

| 실험군 | pack의 lookahead | 총예산 C | 상주 R | rolling | 로그에서 확인할 조건 |
|---|---:|---:|---:|---:|---|
| A · 기본 FSU | 1 | 환경변수 해제 | 0 | 0 | `capped=0 write_back=0` |
| B · 고정 | 1 | 33554432 | 0 | 0 | `capped=1 write_back=0` |
| F · 고정 | 2 | 33554432 | 4194304 | 0 | `capped=1 write_back=1` |
| R · 롤링 | 2 | 33554432 | 4194304 | 1 | `capped=1 write_back=1` |

1. **입력을 맞춘다.** 같은 바이너리, 라이브러리, 가중치, 토크나이저, 생성 설정, 요청 파일, KV 파일시스템과 기기를 쓴다. 기존 SM-S947N에서는 CPU FP16, 연산 스레드 7개, direct I/O를 사용했다. pack 두 개는 깊이만 다르게 준비한다. resident(모든 KV를 DRAM에 두는 실행)로 같은 요청을 한 번 돌리고 네 요청의 전체 `output_ids`, `cached_before/after`를 보관한다. 장비 경로와 pack 준비는 [기존 기기 실행 안내](kv-fsu-rolling-device-test.ko.md)를 따른다.
2. **매 실행은 새 프로세스에서 네 요청을 순서대로 한 번에 수행한다.** index 1은 긴 두 번째 요청(223 → 984), index 2는 세 번째 이어쓰기(984 → 1207)다. 중간에 프로세스를 재시작하면 이어쓰기 입력이 달라진다. 별도 워밍업 한 회를 집계에서 빼고 기록한다. 기기 모델·OS·빌드 SHA, pack/요청 해시, 스레드 수, 시작·종료 시각, 전원 상태, 여유 저장 공간과 읽을 수 있는 온도·클럭을 남긴다. 충전·냉각·휴지 조건을 블록마다 맞춘다.
3. **먼저 A/B를 교차한다.** 한 블록은 A B B A, 다음은 B A A B로 시작 순서를 바꾼다. 기본 계획은 네 블록(군당 8회)이다. 블록별 B 평균에서 A 평균을 뺀 값과 개별 실행값을 보관한다. 중간에 시간이나 열 상태에 따라 두 군이 함께 변하는지도 본다.
4. **이어서 F/R도 같은 방법으로 교차한다.** F R R F와 R F F R을 번갈아 네 블록 실행한다. 이 쌍에서 같은 C·R·깊이로 롤링 효과를 비교한다. 기존 두 실행은 공간을 빌린 횟수가 모두 0이었다. 새 로그에서 차용이 일어나면 따로 표시한다. 시간이 부족하면 A/B를 먼저 끝내고 F/R의 실제 반복 수를 적는다.

다음은 **호스트 POSIX 셸**용 한 회 실행 예시다. 실험군과 출력 파일을 인자로 받는다. 실제 기기의 배포 경로와 입력 경로를 먼저 지정한다. 각 파일명에 블록·실행 순서를 넣는다.

```sh
run_one() (
  set -eu
  arm=$1
  log=$2
  : "${DEVICE_DIR:?기기의 배포 디렉터리}" "${PACK1:?깊이 1 pack}" "${PACK2:?깊이 2 pack}" "${REQ:?네 요청 입력}"
  case "$arm" in
    A) pack=$PACK1; cap='';                          r=0;       mode=0 ;;
    B) pack=$PACK1; cap='NNTR_KV_TOTAL_BYTES=33554432'; r=0;       mode=0 ;;
    F) pack=$PACK2; cap='NNTR_KV_TOTAL_BYTES=33554432'; r=4194304; mode=0 ;;
    R) pack=$PACK2; cap='NNTR_KV_TOTAL_BYTES=33554432'; r=4194304; mode=1 ;;
    *) return 2 ;;
  esac
  adb shell "cd '$DEVICE_DIR' && unset NNTR_KV_TOTAL_BYTES NNTR_KV_BUFFERED NNTR_KV_WRITE_THROUGH NNTR_KV_ASYNC_WRITE NNTR_KV_FLUSH_SYNC && LD_LIBRARY_PATH=. NNTR_ENGINE=cpu NNTR_NUM_THREADS=7 NNTR_KV_TIMING=1 $cap NNTR_KV_RESIDENT_BYTES=$r NNTR_KV_ROLLING=$mode ./nntr_causallm '$pack' --requests '$REQ'" > "$log" 2>&1
)
# 예: run_one A block01_01_A.log
```

**유효성 확인.** 네 요청 모두 resident의 토큰 ID 배열 및 캐시 경계와 대조한다. 매 실행의 `lookahead`, `direct_io=1`, `parallel_reader=1`, `async_writer=0`, `budget_bytes`, `rolling` 및 표의 조건을 실제 로그에서 읽는다. 제한 모드는 `kv_payload_peak_bytes <= total_budget_bytes`도 확인한다. 설정 불일치·요청 누락·출력 불일치는 이유와 함께 별도 표시하고 그 슬롯을 재실행한다. 느리다는 이유로 실행을 제외하지 않는다.

## 3. 추가 계측 전에 기존 카운터로 확인하기

각 실행에서 **요청별 한 행**을 만든다. 누적값의 차이 Δ는 같은 프로세스에서 현재 요청 직후 값에서 직전 요청 직후 값을 뺀 값이다. 첫 요청의 이전 값은 0이다.

| 산출 열 | 계산 및 해석 |
|---|---|
| 묶음 수 N, 평균 MiB | `N = Δowner_reads`, `Δread_bytes / (N × 1048576)`. N=0은 읽기 없음으로 표시한다. |
| 평균 묶음 ms | `Δowner_read_us / (1000 × N)`. 동기 읽기와 선읽기를 모두 포함한다. |
| K·V 파일 읽기 ms/묶음 | `[kv-fsu-timing] step`의 `io_read_us / (1000 × N)`. step은 이미 요청별 값이다. 병렬 실행에서는 이 열에서 묶음 시간을 빼서 대기 시간을 추정할 수 없다. |
| 실제 소비자가 기다린 시간 | `Δdemand_read_us`(필요한 순간 시작한 읽기)와 `Δconsumer_wait_us`(이미 제출한 읽기의 완료 대기)를 각각 초로 표시한다. |
| 함께 볼 지표 | `Δparallel_reads`, `Δreused_buffers`, `Δbacking_write_bytes`, step의 `io_write_us`, `Δborrowed_owners`, `Δbudget_blocks`, KV peak. 사용자 체감은 같은 요청의 `[PERF-SPLIT]`에서 `1000/steady_ms`(첫 토큰 이후 tok/s)와 `e2e_ms`로 확인한다. |

파서 검산은 [기본 로그](../tools/kv_cache/roll74_device_logs/g4_base_nocap.log)의 index 2로 한다. **N=1,351, Δread_bytes=3,076,734,976, 평균=2.884 ms**가 나와야 한다. 출력 텍스트와 첫 로그 태그가 한 줄에 붙을 수 있어 KV 태그는 줄 중간에서도 찾는다. 기존 [요약 스크립트](../tools/kv_cache/parse_kv_roll_logs.py)의 `owner_reads`와 대기 시간 출력은 누적값들을 합산하므로 이 계산에 그대로 쓰면 중복 집계한다. index 1에서 `Δparallel_reads=0`일 때 묶음 평균과 파일 읽기 평균이 얼마나 가까운지 다시 확인한다.

## 4. 느린 구간을 분리하는 2차 계측

**대상은 1차에서 차이가 재현된 쌍**이다. 같은 설정의 빠른 블록과 느린 블록만 갈린 경우에는 그 설정 자체를 반복한다. 계측 실행은 원본 성능 반복과 구분하고, 양쪽에 같은 계측을 켠다.

| 구분할 원인 | 기록 위치와 방법 | 판정 단서 |
|---|---|---|
| 제출 후 작업자 대기, K/V 병렬화 | 같은 단조 시계로 선읽기 제출, 작업 시작, K/V 각각의 `pread` 진입·반환, 묶음 완료, 소비자 대기 시작·끝을 찍는다. 요청·토큰·owner·K/V·작업 ID·스레드 ID·바이트·파일 오프셋·동기/선읽기 여부를 연결한다. | 제출 → 시작만 길면 선읽기 큐를 본다. V가 늦게 시작하거나 소비 시점에 완료가 안 되면 작업자 스케줄과 선읽기 타이밍을 본다. 바이트·owner·동기/선읽기가 같은 작업끼리도 비교한다. |
| 저장소 요청 및 동시 쓰기 | 기기에서 지원하는 Perfetto/ftrace 이벤트를 먼저 확인한다. 가능하면 블록 요청의 issue/complete, 읽기·쓰기 방향과 크기, sched_switch/wakeup, CPU 주파수를 수집한다. 앱과 커널 시계의 기준점을 맞추고 trace 누락을 검사한다. | 느린 `pread`와 겹친 블록 요청 자체가 길어졌는지, 쓰기가 함께 몰렸는지 본다. 한 앱 읽기가 여러 블록 요청으로 쪼개지거나 합쳐질 수 있다. 대응을 식별할 수 없으면 구간별 상관까지만 보고한다. |
| 목적지 DRAM 페이지 재준비 | 코드의 `releaseBuffer`는 제한 모드에서 `discardTail(..., 0)`으로 K/V 페이지를 반납한다. 기본 모드는 페이지를 재사용할 수 있다. 우선 같은 크기 구간의 재사용 횟수와 작업자 실행·대기 시간을 비교한다. | 제한 모드에서만 차이가 남으면 진단 빌드로 **이미 예산에 예약된 목적지**의 페이지를 읽기 직전에 한 번씩 미리 쓰는 경우와 기존 경로를 교차한다. 반납 정책과 예산은 유지한다. 페이지 준비, 이후의 읽기, 둘을 합친 시간, E2E를 모두 잰다. 읽기에서 준비 단계로 비용이 옮겨갔다면 페이지 준비 가설을 지지한다. |

이벤트는 메모리의 한정된 버퍼에 적재하고 요청 후 내보낸다. 매 `pread`에서 로그 파일에 쓰면 같은 저장소와 경쟁할 수 있다. 누락 건수와 계측 전후 차이를 남긴다. 커널 이벤트 접근이 안 되는 기기에서도 앱 타임스탬프와 원래 카운터로 실험을 마친다. 이 경우 커널 내부 및 물리 저장장치에 대한 귀속은 미확정으로 둔다.

## 5. 다음 에이전트가 남길 결과

1. **재현 묶음** — 실행 순서·시각·환경을 담은 manifest, 원본 로그, 요청별 계산표와 계산에 쓴 명령 또는 파서, 계측 시 빌드 diff와 trace. 원본 로그의 경로를 결과 문서에서 연결한다.
2. **숫자 두 줄** — index 2의 블록별 B−A와 R−F를 ms/묶음으로 제시하고 각 차이의 중앙값과 범위, 실행 수를 적는다. 같은 행에 디코드 tok/s와 E2E 차이도 놓는다. index 1의 직렬 읽기 결과를 대조군으로 붙인다. 측정 반복의 단위는 독립 프로세스 실행이다.
3. **원인 판정** — A/B가 시간대에 따라 같이 변하면 실행 환경 변화가 관측된 것이다. B만 일관되게 느리면 제한 모드의 버퍼·예산 경로를 좁혀 본다. F/R에서 묶음 시간은 비슷하고 소비자 대기만 줄면 읽기 완료와 연산의 겹침이 개선된 것이다. 각 결론 옆에 해당 로그·trace와 남은 대안 설명을 적는다. 차이가 재현되지 않으면 관측한 범위를 보고하고 과거 기본 대비 3.21 ms 차이는 원인 미확정으로 남긴다.
