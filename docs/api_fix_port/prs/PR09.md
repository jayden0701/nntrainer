# PR 9 — QNN binary context transaction과 load 실패 전달

## 목적

QNN serialized binary를 mapping하고 metadata를 해석해 context와 graph를
게시하는 전체 경로를 false-success, premature unmap과 worker exception에
안전하게 만든다. vendor 결과가 모호할 때 추측성 rollback으로 handle의
배후 자원을 파괴하지 않고 보수적으로 격리한다.

## 핵심 불변식

- binary 크기는 mapping에 사용하는 같은 fd의 `fstat` 결과에서 얻어
  open/size TOCTOU를 피한다.
- metadata의 내부 pointer와 graph count는 mapping 범위 안인지 검증하며,
  BinaryInfo V1/V2/V3 layout을 명시적으로 처리한다.
- context registry에는 vendor create 전에 `CREATING` entry를 예약하지만,
  success status와 non-null context/graph handle을 모두 확인한
  `ACTIVE` entry만 forwarding에 게시한다.
- 성공한 context가 persistent binary data를 참조할 수 있으므로 해당
  `contextFree()`가 확실히 성공할 때까지 source mapping을 유지한다.
- `SystemContextFree` 실패는 SystemContext handle과 input mapping을 함께
  격리한다. metadata pointer는 non-null인데 안전한 graph count가 없으면
  layout을 추측해 free하지 않고 한 번 격리한 뒤 새 context 생성을
  fail-sticky하게 차단한다.
- context-free 결과가 모호하면 QNNVar self-reference로 backend DSO, RPC,
  metadata, mappings와 context를 process lifetime 동안 보존한다.
- explicit worker thread는 main/worker 양쪽 예외를 보관하고 반드시 join한
  뒤 caller thread에서 전달한다. main-side failure가 우선이다.

## 비판적 검토와 범위 결정

`std::async`로 단순화하는 안은 repository가 이미 문서화한 Windows future
thread accumulation 회피와 충돌하여 사용하지 않았다. 명시적 thread를
유지하되 uncaught exception으로 `std::terminate`되지 않도록 했다.

성공한 QNN context load와 weight load는 병렬로 실행되고 양쪽 실패를
전달하지만, 두 resource를 하나의 atomic model transaction으로 rollback
하지는 않는다. 또한 registry mutex는 생성과 게시만 직렬화하며 forwarding
중 raw reference 수명까지 보호하지 않는다. 이 gap은 PR12의 execution
lease 범위로 명시적으로 남겼다.

확실히 실패하고 output이 null인 경우와 vendor 상태가 모호한 경우를
구분했다. 후자에서 임의의 free/unmap을 시도하는 것보다 process-lifetime
격리를 선택해 use-after-free와 unloaded function call을 피한다.

## 외부 환경에서 필요한 검증

- QAIRT 2.47 생성 header로 QNN-enabled x86 Linux 및 Android/arm64를
  compile한다.
- 정상, 빈 파일, 잘린/손상 binary, 잘못된 metadata와 context/graph create
  실패를 각각 주입한다.
- 정상 load/reload와 context-free 실패에서 mapping 및 backend lifetime이
  의도대로 보존되는지 확인한다.
- worker와 main-side load가 동시에 실패할 때 join과 error 우선순위를
  확인한다.
- 현재 Tensor V1 metadata 범위를 검증하고 Tensor V2가 필요하면 별도
  명시적 지원을 추가한다.

## 의존성과 후속 작업

PR8의 first-use 초기화 및 sticky failure에 의존한다. PR10은 생성된 graph의
실행 tensor와 hook/error 처리를, PR11은 RPC allocation/registration
ledger를, PR12는 forwarding과 teardown 사이의 수명 lease를 담당한다.
extension hook과 profile/device/backend/log의 최종 teardown 순서는
PR13의 별도 책임이다.
