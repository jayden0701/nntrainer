# PR 8 — QNN backend first-use 초기화

## 목적

CPU-only CausalLM process가 QNN plugin context를 등록했다는 이유만으로
vendor backend DSO와 RPC memory를 즉시 초기화하지 않도록 한다. 동시에
늦게 게시되는 allocator가 이미 등록된 Context와 Engine에 안전하게
전파되도록 core의 allocator publication 계약을 보강한다.

## 핵심 불변식

- generic `engine=qnn` layer 생성과 `MODEL_FORMAT_QNN` dispatch에 필요한
  lightweight plugin Context 등록은 유지한다.
- vendor backend/extensions, RPC memory와 QNN layer factory는 첫 QNN layer,
  명시적 `init()` 또는 binary load가 요청될 때 정확히 한 번 초기화한다.
- readiness는 backend, RPC allocator와 factory 준비가 모두 끝난 뒤 마지막에
  게시한다.
- 부분 vendor 자원의 rollback 안전성을 증명할 수 없으므로 첫 초기화 실패는
  sticky하며 같은 process에서 재시도하지 않는다.
- public virtual slot인 `QNNContext::init()`도 동일한 call-once status
  wrapper를 통과한다. 실제 vendor 작업은 private `initBackend()`에 있어
  직접 호출로 이중 초기화할 수 없다.
- Context allocator는 atomic shared-pointer operation으로 게시하고,
  `Engine::getAllocators()`는 registration mutex 아래 live Context에서
  ABI-preserved cache를 갱신한다.
- 소멸에 관여하는 QNN state는 명시적으로 초기화하며, `int init()` 실패
  경로는 성공값인 `false`/0을 반환하지 않는다.

## 비판적 검토와 범위 결정

QNN Context 등록까지 지연하면 generic QNN layer factory와 binary model
dispatch 자체가 사라지므로 수용하지 않았다. 지연 범위는 vendor 자원을
획득하는 단계로 한정했다.

allocator를 단순 raw/shared pointer assignment로 바꾸는 것도 충분하지
않았다. Context 등록 후 allocator가 생기는 순서를 지원하려면 publication과
Engine snapshot 양쪽의 동기화가 필요하다. 이를 검증하기 위한 host-side
assertion은 추가했지만 이 환경에서는 실행하지 않았다.

실패 후 재시도는 사용자 경험상 유용할 수 있으나, 부분 생성된 vendor
handle과 DSO의 정리 계약이 당시 입증되지 않아 fail-sticky가 더 안전하다고
판단했다. 세밀한 vendor 자원 teardown은 PR13 이후의 별도 범위다.

## 이 환경에서 수행한 검증

- 초기화 순서, allocator publication, failure semantics, generic QNN entry와
  SDK-free test 전략을 여러 독립 read-only 감사로 검토했다.
- 변경 C/C++ 파일에 대해 clang-format 14 strict dry-run을 확인했다.
- 누적 `git diff --check`를 수행했다.
- 두 커밋의 PR7 ancestry, DCO sign-off와 Codex co-author trailer를
  확인했다.
- configure, compile, 추가된 unit assertion, Gradle, Android와 runtime은
  실행하지 않았다.

## 외부 환경에서 필요한 검증

- CPU-only startup에서 첫 QNN layer/init/load 전 vendor 초기화 로그가
  발생하지 않는지 확인한다.
- `readelf -d libqnn_context.so`에서 QNN vendor DSO가 `DT_NEEDED`로
  고정되지 않았는지 확인한다.
- 여러 thread가 동시에 첫 QNN 사용을 요청해도 한 번만 초기화되는지
  확인한다.
- 첫 QNN 사용의 성공 및 단계별 실패를 주입하고 실패가 sticky한지, 같은
  process의 CPU model은 계속 사용할 수 있는지 확인한다.
- Context 등록 뒤 게시한 allocator가 `Engine::getAllocators()`에 보이는
  host-side regression test를 실행한다.

## 의존성과 후속 작업

PR7의 one-hot backend/loader 계약에 의존한다. PR9은 first-use 초기화를
전제로 binary mapping, SystemContext metadata와 context/graph handle의
생성·해제·실패 전달을 transaction으로 묶는다. 정상 teardown 순서와
forwarding 중 수명 배타성은 각각 PR13과 PR12까지 완성되지 않는다.
