# PR13 — QNN 런타임의 의존성 순서 teardown

## 목적

PR12에서 도입한 실행 lease와 shutdown admission 위에서 QNN 런타임을 실제
의존성의 역순으로 정리한다. 기존 `CLEANUP_PENDING` 경로는 이를 끝내는
finalizer가 없어 self-reference가 영구히 남을 수 있었으므로 제거하고, 종료
시점에 live RPC registration을 선제적으로 drain한 뒤 context와 상위 자원을
정리하도록 바꾼다.

## teardown·quarantine 설계

종료는 shutdown-exclusive lifecycle lease 아래에서 다음 순서로 진행한다.

1. 모든 memory registration을 전역 사전 검사하고 성공한
   `memDeRegister` node만 제거
2. 전체 context handle의 유일성을 검사한 뒤
   `beforeContextFree` → 각 `contextFree(context, profile)` →
   `afterContextFree`
3. profile free
4. device before-hook → device free → after-hook
5. backend before-hook → backend free → after-hook
6. BackendExtensions destroy
7. QNN log free
8. ResourceManager 및 system DSO release
9. function table 무효화와 backend DSO owner release

첫 vendor 호출 전 lifecycle, null 여부, ledger 구조, context/registration
handle alias, host-side count와 reserve 가능성을 검사한다. 각 자원은
`NOT_ACQUIRED`, `OWNED`, `UNSUPPORTED`, `RELEASED`, `QUARANTINED` 상태로
추적하며 `success + non-null`만 `OWNED`로 게시한다.

어느 단계든 false, error 또는 throw가 발생하면 그 뒤의 의존 자원에는 손대지
않는다. 이미 성공한 단계만 `RELEASED`로 확정하고, 모호한 handle과 source
buffer, extension, ResourceManager, backend DSO는 QNNVar self-reference로
process lifetime 동안 보존한다. 관련 QNN status 비교에는 raw 64-bit 값 대신
`QNN_GET_ERROR_CODE()`로 정규화한 public error code를 사용한다.

## 비판적 검토와 수용 판단

- `CLEANUP_PENDING`에 또 다른 재시도 경로를 덧붙이는 대신, 알려진
  registration을 context보다 먼저 drain하도록 종료 transaction 자체를
  완결했다.
- partial drain 뒤 ledger 전체를 지우지 않는다. 개별 deregistration 성공만
  반영하고 allocation node와 rpcmem backing은 늦은 MemoryPool release까지
  유지한다.
- 서로 다른 binary가 같은 context handle을 소유하는 경우에는 어떤 free도
  시작하지 않는다. 단일 context rollback에도 전체 registry alias 검사를
  적용해 다른 owner의 handle을 해제하지 않게 했다.
- SystemContext query, binary context create 또는 extension hook의 throw와
  `success + null`/`error + non-null`은 rollback 가능하다고 추정하지 않는다.
  vendor가 무엇을 획득했는지 확정할 수 없으므로 lifecycle admission을 즉시
  `QUARANTINED`로 닫는다.
- QAIRT 2.47의 BackendExtensions 생성자가 요구하는 non-null
  `genie::ResourceManager`를 QNNVar가 소유해 전달하도록 고쳐 기존 null
  dereference와 숨은 system DSO 소유권을 함께 제거했다.
- 생성 BackendExtensions와 ResourceManager 내부 DSO의 예외 안전성은 생성기
  수정이 필요하므로 PR15와 PR16으로 분리했다.

## 이번 작업에서 실제 수행한 검증

- 포맷된 tree를 대상으로 compile/API 호환성, concurrency/lock/lifetime,
  resource ownership/teardown을 각각 독립적인 read-only 감사로 확인했다.
- 변경 C/C++에 clang-format 14 strict dry-run을 적용했다.
- `git diff --check`, PR12 ancestry, DCO sign-off, Codex co-author trailer,
  정확한 5개 파일 범위와 `subprojects/` 무변경을 확인했다.
- configure, build, unit test, Gradle, Android 및 runtime 실행은 하지 않았다.

따라서 이 PR에서 확인된 것은 소스와 transaction 계약의 정적 일관성이지,
실제 QAIRT SDK를 사용한 컴파일이나 동작 성공이 아니다.

## 외부 환경에서 필요한 검증

- QAIRT 2.47 SDK를 사용한 QNN-enabled x86 Linux compile/link
- active forwarding과 QNNContext teardown의 경쟁
- 여러 context와 live RPC registration을 가진 정상 shutdown
- context/profile/device/backend/log free 단계별 failure injection과 DSO
  보존 확인
- `success + null`, `error + non-null`, hook exception에서 lifecycle이
  quarantine되는지 확인

## 의존성과 다음 PR

PR12의 shutdown-exclusive lifecycle lease가 직접 선행 조건이다. 다음
PR14는 종료 순서와 별개로, 런타임 중 `rpcmem` 및 QNN
register/deregister 결과가 모호해지는 즉시 admission을 닫고 handle alias를
게시 전에 검출한다. 생성 wrapper의 DSO 수명 문제는 PR15와 PR16에서 다룬다.
