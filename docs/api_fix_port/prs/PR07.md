# PR 7 — Native loader와 backend 계약 명확화

## 목적

PR6까지의 CausalLM unified API가 실제로 제공하는 native backend 선택
계약을 descriptor, loader 검증, extension ABI와 사용자 문서 전반에서
일치시킨다. 구현되지 않은 GPU 선택 가능성을 광고하지 않고, model 경로와
Windows 문자열 전달을 플랫폼의 실제 코드 경계에 맞춘다.

## 핵심 불변식

- 각 built-in 또는 extension catalog entry는 CPU, GPU, NPU 중 정확히 하나의
  concrete backend bit만 선언해야 한다.
- load 시 전달하는 backend는 같은 model을 다른 runtime으로 전환하는
  selector가 아니라 descriptor와 호출자의 기대가 같은지 확인하는
  compatibility assertion이다.
- Qwen과 Function Gemma catalog 및 Android fallback에서 구현되지 않은 GPU
  bit를 제거하고 실제 단일 backend만 광고한다.
- null 또는 빈 model base 경로는 Android에서만 download 위치를 사용하고,
  desktop에서는 `./models`를 기본값으로 사용한다.
- 이 코드의 `WSTR`는 Windows에서도 `std::string`이므로
  `Transformer::run()`에는 모든 플랫폼에서 동일한 UTF-8 byte string을
  전달한다.
- 변경된 extension descriptor 의미는 build tag `contract-r2`로 구분하여
  이전 계약의 plugin을 조용히 받아들이지 않는다.

## 비판적 검토와 범위 결정

초기 검토 중 Windows 전용 wide-string 변환이 제안됐지만, 실제 typedef를
추적한 결과 compile error를 만드는 잘못된 방향이었다. 최종 변경은 이미
공통 경계인 narrow UTF-8 byte path를 유지한다. 다만 내부 file API까지
wide path로 바꾸지는 않았으므로 non-ASCII Windows model 경로 지원은 이
PR이 보장하지 않는다.

backend mask도 미래 가능성을 이유로 복수 bit를 허용하지 않았다. 현재
catalog entry가 하나의 concrete implementation을 가리키는 계약에 맞춰
one-hot 검증을 적용했다. repository에 배포 model asset이 없으므로 Qwen과
Function Gemma의 실제 config가 CPU variant인지까지는 코드만으로 확정하지
않았다.

## 이 환경에서 수행한 검증

- backend/extension ABI와 Windows 문자열 경계를 독립 read-only 감사했다.
- 변경 C/C++ 파일에 대해 clang-format 14 strict dry-run을 확인했다.
- `git diff --check`를 수행했다.
- PR6 ancestry, DCO sign-off와 Codex co-author trailer를 확인했다.
- configure, compile, unit test, Gradle, Android와 runtime은 실행하지
  않았다.

## 외부 환경에서 필요한 검증

- 배포되는 Qwen 및 Function Gemma의 `nntr_config.json`이 public catalog가
  선언한 CPU variant인지 확인한다.
- CPU/GPU/NPU mask가 없거나 복수 bit인 built-in 및 extension descriptor가
  load에서 거부되는지 확인한다.
- Android null/empty base path와 Linux `./models` 기본 경로를 실제
  artifact에서 확인한다.
- Windows에서 ASCII/UTF-8 model 경로를 compile하고 실행한다. non-ASCII
  경로가 요구되면 별도 filesystem 경계 개선이 필요하다.
- `contract-r2` 이전 extension이 ABI 검증에서 명확히 거부되는지 확인한다.

## 의존성과 후속 작업

PR6의 source/install 정합성에 의존한다. PR8은 loader 계약을 유지하면서
QNN plugin 등록 자체는 가볍게 남기고 vendor DSO, RPC allocator와 layer
factory의 실제 초기화만 first-use로 옮긴다.
