# PR17 — native Linux QNN context plugin 빌드 복구

## 목적

QNN source list는 생성되지만 Engine이 로드하는 `libqnn_context.so` target이
사라진 native Linux 회귀를 복구한다. Android 경로와 같은 전체 QNN source를
사용해 plugin을 만들고, host와 plugin이 하나의 shared nntrainer runtime
identity를 사용하도록 build contract를 고정한다.

## build contract 설계

`platform=none`이고 host system이 Linux인 경우에만 Android.mk와 같은 전체
`qnn_sources_abs`로 `libqnn_context.so`를 빌드하고 설치한다.

- `PLUGGABLE=1`은 Engine이 `dlopen` 뒤 찾는
  `ml_train_context_pluggable` C ABI symbol을 생성한다.
- `ENABLE_QNN=1`은 RpcMem/QNNRpcManager의 실제 QNN 경로를 사용하게 하며,
  non-QNN fallback이 plugin에 들어가는 것을 막는다.
- `nntrainer_base_deps`로 plugin source가 직접 사용하는 loader, thread 등의
  dependency를 보존한다.
- `nntrainer_dep`가 아니라 `nntrainer_shared`에 직접 링크해 plugin 안에
  nntrainer registry와 singleton state가 복제되지 않게 한다.
- native QNN의 `default_library=static`은 SDK 생성 전에 명시적으로
  거부한다. static host와 shared-core plugin 조합도 한 프로세스에 두
  nntrainer runtime을 만들 수 있으므로 `shared` 또는 `both`만 허용한다.
- Android는 기존 Android.mk source/include 전달을 그대로 사용한다.
  Tizen, Yocto, Windows에는 새 target이나 지원 계약을 추가하지 않는다.

## 비판적 검토와 수용 판단

- 회귀는 `733d96c9`에서 Android용 전체 source list를 만들며 예전
  `nntrainer/qnn/jni/meson.build`의 native `shared_library()`를 삭제한 뒤,
  대체 target을 추가하지 않은 데서 발생했다. Engine은 여전히
  `libqnn_context.so`를 로드하므로 source 생성만으로는 기능이 완성되지
  않는다.
- 일반적인 `nntrainer_dep`를 재사용하면 `default_library=static` 설정에서
  plugin이 static core를 품거나 host와 다른 core instance에 연결될 수 있다.
  단순 link 성공보다 registry/singleton identity를 우선해 shared target을
  직접 사용하고 static-only 구성을 거부했다.
- `.so` 이름, PAL Linux source와 Engine loader 계약을 근거로 regular Linux
  범위만 복구했다. 검증하지 않은 Windows/Tizen/Yocto 지원을 묵시적으로
  확대하지 않았다.
- Android는 별도 Android.mk owner가 있으므로 native target 변경에 섞지
  않았다.
- 설치 중인 `qnn_context.h`는 생성 SDK/private header 없이는 독립적으로
  include할 수 없다. build-target 복구와 public packaging/doc 정정은 리뷰
  경계가 다르므로 PR18로 분리했다.

## 이번 작업에서 실제 수행한 검증

- 독립 감사 2개가 Meson 0.55 문법, target/source/include/dependency,
  platform guard, export define, shared runtime identity와 Android 무변경을
  정적으로 확인했다.
- `git diff --check`, PR16 ancestry, DCO/Codex trailer, 정확한 Meson 2개 파일
  범위와 `subprojects/` 무변경을 확인했다.
- C/C++ 변경이 없어 clang-format 대상은 없었다.
- generator, Meson configure, build, unit test, Gradle, Android 및 runtime
  실행은 하지 않았다.

따라서 target graph와 계약은 정적으로 확인했지만, 실제 SDK 생성과
`libqnn_context.so` 산출·로드 성공은 외부 빌드가 필요하다.

## 외부 환경에서 필요한 검증

- QAIRT 2.47 SDK를 사용한 `platform=none`, Linux host, `default_library`가
  `shared` 및 `both`인 Meson configure/build/install
- 생성된 `libqnn_context.so`의 `ml_train_context_pluggable` export 확인
- Engine의 plugin 탐색 경로에서 DSO load와 lazy vendor initialization
- host와 plugin이 동일한 nntrainer registry/singleton을 관찰하는지 확인
- `default_library=static`이 SDK 생성 전에 의도한 진단으로 거부되는지 확인
- Android NDK 경로가 계속 Android.mk의 source/include list로 빌드되는지 확인
