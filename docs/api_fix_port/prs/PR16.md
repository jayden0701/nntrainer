# PR16 — 생성 ResourceManager의 system DSO·DLC 소유권

## 목적

QAIRT SDK에서 생성하는 ResourceManager가 system DSO, optional system log,
DLC handle을 명시적인 상태 머신으로 소유하고 의존성 역순으로 정리하도록
고친다. provider 선택과 DLC create 결과를 게시 전에 분류하며, 모호한 vendor
상태에서는 잘못 free하거나 unload하지 않고 QNN runtime을 quarantine한다.

## teardown·quarantine 설계

system DSO handle은 provider 탐색 동안 local로 유지한다. null provider를
건너뛰고 API version과 실제 capability를 모두 만족하는 provider를 찾은
경우에만 function table과 DSO를 ResourceManager member에 게시한다.

- 기본 모드는 system context create, `getBinaryInfo`, free를 요구한다.
- DLC 모드는 DLC create/free, `getRecordByName`, `getRecordDataSize`,
  `readRecordDataMemoryMapped`를 추가로 요구한다.
- provider list는 SDK 원형과 동일한
  `const QnnSystemInterface_t **`로 처리해 legacy `const_cast`를 제거한다.

DLC create 결과는 다음 진리표로 분류한다.

- `success + non-null`: 유일한 정상 owned 상태
- `error + null`: wrapper가 명확히 rollback할 수 있는 clean failure
- `success + null`, `error + non-null`, throw: vendor 상태가 모호하므로
  free/close하지 않고 관찰한 상태와 DSO를 보존

`shutdown() noexcept`는 DLC mutex를 잡고 mutation 전에 handle과 owner DSO,
필요 free function의 일관성을 모두 검사한다. 성공 경로는 DLC → optional
system log → internal function table → system DSO 순서다. free error/throw
또는 `dlClose` 실패는 sticky하며 첫 실패 뒤의 dependency를 건드리거나
재시도하지 않는다.

QNNContext는 ResourceManager가 system DSO를 닫기 전에 QNNVar에 복사된
borrowed system function table을 먼저 비운다. shutdown 성공만 owner reset을
허용하며 실패 시 ResourceManager, system/backend DSO와 나머지 runtime을
self-reference quarantine으로 보존한다.

## 생성기 build contract

대형 Qualcomm 원문 블록을 생성기 안에 복제하지 않으면서 source drift를
fail-closed로 막기 위해, QAIRT 2.47.0.260601의 세 함수 블록을 고유 signature
boundary와 전체 SHA-256으로 검증한다.

- 기본 생성자, 327 bytes:
  `ed417e1a7e24bc25a8b6a47caefe65b6ce36a8d06477f3171549c3099fc194aa`
- DLC 생성자, 887 bytes:
  `3140c0dd56c1404bf5ca1572aad2fab9d12ca181d29fda1a5c0e018ebb080ae3`
- provider helper, 2256 bytes:
  `13b94339084c19b3ca73dd8122b4b485149a78c5d6aa08a208a15af4d1698b14`

새 선언·정의, copy/move 삭제, local DSO 사용, const provider 계약,
rollback site 수와 legacy pattern 부재를 모두 확인한 뒤에만 revision 3
stamp를 기록한다.

## 비판적 검토와 수용 판단

- DSO를 constructor member에 즉시 게시하면 이후 provider 검증 실패와
  constructor unwind에서 소유권이 불명확해진다. 검증이 끝날 때까지 local
  handle로 유지하는 방식을 채택했다.
- 정상 validation failure는 local DSO를 닫지만, provider call 자체가
  throw한 경우에는 DSO-defined exception metadata가 unwind 중일 수 있어
  loader reference를 닫지 않는다.
- `success + null`이나 `error + non-null`을 관대한 실패로 정리하지 않는다.
  vendor가 handle을 만들었는지 확정할 수 없으므로 process-lifetime retention이
  더 안전하다.
- 생성기 안에 proprietary 함수 원문 전체를 매치 문자열로 복제하지 않고
  boundary와 hash를 사용했다. source layout이 조금이라도 달라지면 수정을
  추측하지 않고 생성 단계에서 거부한다.
- no-op deleter를 가진 DLC memory-mapped record buffer는 ResourceManager
  lifetime 밖으로 escape할 수 있다. 이 문제는 owner state machine과
  독립적으로 검토할 수 있도록 host-owned copy와 record release 후속 PR로
  남겼다.
