## 한눈에 보기

이 PR은 실행 설정의 `max_seq_len`이 모델의
`max_position_embeddings`보다 크면, 모델이 지원하는 길이로 줄인다.

비유하면 모델이 읽을 수 있는 위치 안내표가 32,768칸뿐인데 사용자가 33,536칸짜리
길을 요청했을 때, 길을 32,768칸으로 잘라 주는 안전장치다. 요청값을 그대로 사용해
RoPE 위치표 밖을 읽는 것보다 훨씬 낫고, 문제를 경고로 알려 주는 방향도 맞다.

그러나 현재 수정은 간판의 “최대 길이” 숫자 하나만 바꾼다. 함께 맞춰야 하는
“생성할 토큰 수”, “이미 사용한 시스템 프롬프트와 이전 대화 길이”, “실제로 만든
RoPE 표의 길이”는 그대로다. 그래서 세 가지 경로에서 여전히 메모리 범위를 벗어날 수
있다.

## 발견 사항

### P1 — 일부 모델은 설정값보다 짧은 RoPE 표를 만들어 긴 문맥에서 그대로 충돌함

위치:

- 변경된 `Applications/CausalLM/models/transformer.cpp:182-202`
- `Applications/CausalLM/models/transformer.cpp:527-537`
- `Applications/CausalLM/models/gemma3/gemma3_causallm.cpp:197-206`
- `Applications/CausalLM/layers/mha_core.h:93-97`
- `Applications/CausalLM/layers/mha_core.cpp:1086-1094`

새 주석은 RoPE 표가 `MAX_POSITION_EMBEDDINGS`개 만들어진다고 설명한다. 하지만 이것은
모든 모델 경로에서 참이 아니다.

- Qwen2/3, LFM2, Gemma4, GPT-OSS는 MHA에
  `max_position_embeddings=MAX_POSITION_EMBEDDINGS`를 넘긴다.
- 기본 Transformer(Llama)와 Gemma3 경로는 이 값을 넘기지 않는다.
- 값을 받지 않은 MHA는 기본값인 40,960개만 RoPE 표를 만든다.

예를 들어 Gemma3 4B 이상은
[공식적으로 128K 문맥](https://deepmind.google/models/gemma/gemma-3/)을 지원한다.
설정 파일에 131,072가 있고 사용자가 100,000을 요청하면, 이번 조건에서는
`100,000 <= 131,072`라 아무것도 줄이지 않는다. 하지만 Gemma3 MHA가 실제로 만든
표는 40,960칸뿐이므로 40,960번째 위치부터 표 밖을 읽는다.

비유하면 건물 설계도에는 131,072번 방까지 있다고 적혀 있어서 출입을 허용했는데,
실제 안내 책자는 40,960번 방까지만 인쇄된 상태다. 설계도 숫자만 검사해서는 안내
책자 밖을 펼치는 사고를 막을 수 없다.

`apply_rotary_emb_tensor_v2()`는 `from < max_timestep`만 확인하고 바로
`freqs[from + h]`를 읽으므로, 이 차이는 실제 범위 밖 접근으로 이어진다.

권장 수정:

- 기본 Transformer와 Gemma3가 MHA를 만들 때도 모델의
  `MAX_POSITION_EMBEDDINGS`를 명시적으로 전달한다.
- 설정값이 40,960보다 큰 작은 테스트 모델을 만들어, 마지막 허용 위치의 prefill과
  decode가 안전한지 확인한다.

### P1 — 시스템 프롬프트와 이전 대화가 차지한 길이를 계산에서 빼지 않음

위치:

- `Applications/CausalLM/models/causal_lm.cpp:441`
- `Applications/CausalLM/models/causal_lm.cpp:548-575`
- `Applications/CausalLM/models/causal_lm.cpp:609-617`
- `Applications/CausalLM/models/causal_lm.cpp:665`
- `Applications/CausalLM/layers/mha_core.cpp:1100-1111`

현재 입력 문자열의 허용 길이는 다음처럼 계산한다.

```cpp
MAX_SEQ_LEN - NUM_TO_GENERATE
```

하지만 실제 RoPE와 KV-cache 위치는 다음 지점에서 시작한다.

```cpp
SYS_PROMP_LEN + global_token_len
```

여기서 `SYS_PROMP_LEN`은 미리 계산해 둔 시스템 프롬프트 길이이고,
`global_token_len`은 같은 객체로 앞선 대화를 실행하며 이미 쓴 길이다. 두 값은
허용 길이 계산에서 빠져 있다.

예를 들어 최대 100칸, 생성 10칸, 앞 대화가 이미 60칸을 사용했다고 하자. 실제 남은
자리는 40칸이지만 현재 코드는 새 입력을 최대 90칸까지 받는다. 그러면 prefill 끝이
150번 위치가 되어 100칸짜리 RoPE 표와 KV-cache를 넘어간다.

비유하면 100석 버스에 이미 60명이 타고 있는데도, 빈 버스라고 생각해 90장의 표를
더 파는 셈이다. 버스의 정원 표시를 100으로 고친 것만으로는 승객 수를 안전하게
제한할 수 없다.

이 경로는 가정만으로 만든 경우가 아니다. 코드가 매 실행 뒤
`global_token_len += generation_cnt + init_len`으로 값을 누적하고, 미리 저장한 시스템
KV-cache도 공식 실행 경로에서 불러온다. 즉 같은 객체의 두 번째 대화나 시스템
프롬프트 캐시를 사용할 때 실제로 일어날 수 있다.

권장 수정:

- 실행할 때마다 `SYS_PROMP_LEN + global_token_len`을 먼저 확인한다.
- 이미 사용한 길이를 뺀 “실제 남은 자리” 안에서 prompt와 generation을 제한한다.
- prefill과 decode를 호출하기 직전에 `from + 처리할 길이 <= MAX_SEQ_LEN`과
  `MAX_POSITION_EMBEDDINGS`를 모두 검사한다.
- 시스템 캐시가 있는 경우와 같은 객체를 두 번 실행하는 경우를 회귀 테스트에 넣는다.

### P2 — clamp 뒤 생성 길이를 다시 검사하지 않아 뺄셈이 뒤집히거나 한 칸 넘침

위치:

- 변경된 `Applications/CausalLM/models/transformer.cpp:184-202`
- `Applications/CausalLM/models/causal_lm.cpp:441-461`
- `Applications/CausalLM/models/causal_lm.cpp:609-629`
- `Applications/CausalLM/models/causal_lm.cpp:247-255`

GitHub에 올라온
[`Clamp the generation budget after shrinking max length`](https://github.com/nntrainer/nntrainer/pull/4144#discussion_r3643548266)
리뷰는 **적절하며 최신 head에도 유효하다**.

예를 들어 원래 설정이 다음과 같으면 PR 적용 전에는 생성 길이가 최대 길이보다 작다.

```text
max_seq_len = 33536
num_to_generate = 33000
max_position_embeddings = 32768
```

이번 코드가 `MAX_SEQ_LEN`만 32,768로 줄이면 `NUM_TO_GENERATE`는 33,000인 채로 남는다.
그 뒤 `MAX_SEQ_LEN - NUM_TO_GENERATE`는 unsigned 계산에서 아주 큰 양수로 뒤집힌다.
따라서 긴 prompt를 자르지 않고 작은 `input_sample`과 `ids_history`에 쓰거나, 짧은
prompt라도 생성 도중 배열 끝을 넘는다.

또 생성 길이가 최대 길이보다 작아도 경계가 한 칸 어긋난다. prompt 길이를 정확히
`MAX_SEQ_LEN - NUM_TO_GENERATE`까지 허용하면서, 생성 결과를 prompt 바로 다음 칸부터
`NUM_TO_GENERATE`번 기록한다. 마지막 기록 위치는 `MAX_SEQ_LEN`이지만 유효한 마지막
인덱스는 `MAX_SEQ_LEN - 1`이다.

비유하면 0번부터 99번까지 있는 100칸 사물함에 마지막 물건을 100번 사물함에 넣으려는
것과 같다. “생성 수가 최대 길이보다 작은가”만 검사하지 말고 첫 prefill 결과까지
포함한 정확한 마지막 인덱스를 계산해야 한다.

권장 수정:

- clamp한 뒤 `NUM_TO_GENERATE`가 새 길이에 들어오는지 검증하고, 잘못된 값은 명확히
  거부하거나 함께 줄인다.
- `NUM_TO_GENERATE`의 음수도 거부한다.
- prompt, prefill에서 나온 첫 토큰, decode 토큰을 모두 포함해 마지막 인덱스가
  `MAX_SEQ_LEN - 1` 이하인지 계산한다.
- `num_to_generate > max`, `== max`, 딱 마지막 칸을 채우는 경우를 각각 테스트한다.

## 기존 GitHub 리뷰에 대한 판단

현재 보이는 생성 예산 P2 리뷰는 단순한 이론적 우려가 아니다. clamp가 적용되기 전에는
유효했던 설정을 이번 변경이 위험한 조합으로 만들 수 있고, 실제 할당 크기와 기록
위치까지 따라가면 범위 밖 쓰기로 이어진다. 따라서 해결하지 않고 병합하면 안 된다.

다만 그 리뷰에서 제안한 대로 `NUM_TO_GENERATE <= MAX_SEQ_LEN`만 맞추는 것으로는
충분하지 않다. 위의 한 칸 차이와 시스템 프롬프트·이전 대화 길이도 함께 계산해야 한다.

## 맞게 구현된 부분

- `MAX_SEQ_LEN`과 `INIT_SEQ_LEN`이 모델 한도를 넘을 때 모델 한도 이하로 줄이는 기본
  방향은 맞다.
- clamp가 `CausalLM::setupParameters()`의 `ids_history` 할당보다 먼저 실행되므로,
  해당 버퍼 자체는 줄어든 `MAX_SEQ_LEN` 크기로 만들어진다.
- C/C++ 형식 검사, DCO, 일반 빌드 CI는 최신 head에서 통과했다.
- commit의 sign-off, AI 공동 작성자 trailer, 제목 형식은 저장소 규칙에 맞는다.

## 테스트와 문서에서 보완할 점

- 이번 문제를 재현하는 “설정 길이가 모델 한도보다 큰 경우” 전용 테스트가 없다.
  일반 빌드 CI는 숫자 경계와 두 번째 실행을 검사하지 않는다.
- PR 설명은 저장소가 요구하는 commit별 `<details>`, Self evaluation, Summary 형식을
  따르지 않는다.
- 경고문은 “한 번 출력”된다고 설명하지만 setup 함수가 여러 번 불리는 일부 subclass는
  같은 경고를 반복해서 출력할 수 있다. 충돌 문제보다는 낮은 우선순위지만, 정말 한 번만
  보여 주려면 출력 위치나 상태를 정리해야 한다.
