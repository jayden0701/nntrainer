## 요약

이 PR은 FP16 SwiGLU, scalar multiply, logit softcap용 NVRTC kernel 3개를
추가하고 promoted LLM layer의 CUDA decode fast path를 활성화한다. 직접
부모 #4117 대비 고유 변경은 6개 파일, 184줄 추가다.

kernel 수식과 일반적인 launch 크기는 타당해 보이지만, terminal output의
동기화와 operand residency 검증이 부족하다. 또한 fast path가 실패했을 때
device-only pointer를 그대로 CPU 구현으로 넘기며, softcap의 공개 layer
속성과 multi-batch 동작이 CUDA backend에서 달라진다.

## 발견 사항

### P1 — async 모드에서 softcap 완료 전에 CPU가 logits를 읽음

위치:

- `nntrainer/layers/llm/logit_softcapping.cpp:79-85`
- `nntrainer/layers/llm/logit_softcapping.cpp:137-144`
- `nntrainer/cuda/cuda_elementwise.cpp:76-82`
- `nntrainer/models/neuralnet.cpp:1680-1693`

`applyOnRange()`의 `finish()`는 softcap kernel을 enqueue하기 **전**에
호출되므로 이전 lm-head 작업까지만 기다린다. 그 뒤
`cuda_softcap_fp16()`이 새 kernel을 enqueue한다.

`dispatch1d()`는 `maybeFinish()`를 호출하지만 `NNTR_CUDA_ASYNC=1`에서는
동기화하지 않고 성공을 반환한다. 이후 `incremental_inference()`는 반환된
FP16 tensor를 곧바로 CPU `scopy_fp16_to_fp32()` 또는 `memcpy()`로 읽는다.
특히 WDDM의 pinned zero-copy output에는 page-fault 기반 암묵적 동기화도
없어 stale 또는 일부만 갱신된 logits로 token을 선택할 수 있다.

softcap kernel 뒤, 실제 host-read boundary 전에 명시적인 terminal
동기화가 필요하다.

### P1 — 세 fast path 모두 일부 pointer만 CUDA 접근 가능 여부를 검사

위치:

- `nntrainer/layers/llm/swiglu_layer.cpp:82-88`
- `nntrainer/layers/llm/scalar_multiply.cpp:162-168`
- `nntrainer/layers/llm/logit_softcapping.cpp:125-142`

SwiGLU는 첫 입력 `a`만 검사하고 두 번째 입력 `b`와 output `o`를 바로
kernel에 전달한다. Scalar와 softcap도 input만 확인하고 output은 확인하지
않는다.

mixed-engine graph, 외부 output, host/device boundary에서 한 operand만
UVM/device tensor이면 CUDA kernel에 일반 host pointer 또는 다른 backend
pointer가 들어갈 수 있다. launch 자체는 성공한 뒤 illegal access가
비동기로 나타날 수 있으며, wrapper는 성공으로 처리해 CPU fallback도
건너뛴다.

모든 input과 output을 `dev_accessible()`로 검증한 경우에만 CUDA path를
실행해야 한다.

### P1 — device-only tensor에서 kernel 실패 후 불가능한 CPU fallback 실행

위치:

- `nntrainer/layers/llm/swiglu_layer.cpp:75-91`
- `nntrainer/layers/llm/scalar_multiply.cpp:157-179`
- `nntrainer/layers/llm/logit_softcapping.cpp:120-153`

NVRTC compile, kernel resolve 또는 launch가 실패하면 세 layer 모두 기존
host 구현으로 내려간다. 하지만 input/output이 `cudaMalloc` 기반
device-only activation이면 host `getOps()->swiglu()`, `multiply()`,
`copyData()`가 해당 pointer를 역참조할 수 없어 crash하거나 잘못된 값을
만든다.

SwiGLU는 fast path가 batch/channel 조건 때문에 선택되지 않는 경우에도
scalar와 달리 `drain_if_async()`조차 호출하지 않는다. 따라서 UVM
fallback에서도 아직 완료되지 않은 producer 결과를 CPU가 읽을 수 있다.

device-only tensor의 CUDA 실행 실패는 오류로 전달해야 한다. host fallback을
지원하려면 명시적인 D2H/H2D staging과 동기화가 필요하다.

### P1 — softcap의 batch loop가 매번 batch 0만 처리

위치:

- `nntrainer/layers/llm/logit_softcapping.cpp:103-118`
- `nntrainer/layers/llm/logit_softcapping.cpp:137-144`

코드는 batch/channel을 순회하지만 `getSharedDataTensor()`의 offset을 항상
0으로 전달한다. 따라서 이번 PR에서 활성화한 CUDA kernel도 첫 chunk만
반복 처리하고 batch 1 이후의 output은 갱신하지 않는다. 일반
`forwarding()`에서는 뒤 batch가 softcap되지 않은 입력 복사값으로 남고,
incremental 경로에서는 stale 값이 남을 수 있다.

각 batch의 `getFeatureLen()`을 반영한 offset을 사용하고, channel을 view
차원에 포함할지 개별 순회할지 일관되게 정해야 한다.

### P2 — CUDA softcap이 `activation_type`을 무시하고 항상 `tanh` 사용

위치:

- `nntrainer/layers/llm/logit_softcapping.cpp:35-55`
- `nntrainer/layers/llm/logit_softcapping.cpp:149-153`
- `nntrainer/cuda/cuda_elementwise.cpp:67-71`

core layer는 `activation_type`으로 `ACT_NONE` 이외의 activation을 받아
CPU 경로의 `acti_func`에 적용한다. 새 CUDA kernel은 이 속성을 전달받지
않고 항상 `cap * tanh(x / cap)`을 계산한다.

현재 Gemma4 설정은 tanh라서 맞지만, sigmoid/ReLU 등 다른 공개 속성을
사용하면 backend에 따라 결과가 달라진다. fast path를 tanh일 때만
선택하거나 activation별 kernel을 제공해야 한다.

## 의존 PR에서 이어지는 문제

이 PR은 #4117 위에 쌓여 있다. #4117의 CUDA allocator 미연결 때문에
현재 graph에서는 새 fast path가 host pointer를 보고 실행되지 않을 수
있으며, kernel cache와 argument 동시성 문제도 그대로 포함한다.

- [PR #4117 리뷰](./pr-4117.md)
