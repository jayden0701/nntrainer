## 요약

이 PR의 고유 변경은 2개 파일이며, CausalLM이 OpenCL 또는 CUDA로
실행될 때 ARM KAI용 QS4CX repack 작업을 생략하려는 내용이다. 모든
consumer가 원본 QS4CX 데이터를 직접 사용하는 경우 이 최적화 자체는
타당하다. 하지만 새 helper는 실제로 만들어진 graph의 engine이 아니라
환경 변수와 빌드 옵션만 보고 engine을 추정한다.

## 발견 사항

### P1 — 실제 graph는 CPU인데 필수 repack을 건너뜀

위치:

- `Applications/CausalLM/llm_util.hpp:125-142`
- `Applications/CausalLM/models/transformer.cpp:368-372`
- `Applications/CausalLM/models/transformer.cpp:253-256`
- `nntrainer/engine.cpp:91-110`
- `nntrainer/tensor/float_tensor.cpp:1054-1065`
- `nntrainer/tensor/qs4cx_tensor.cpp:91-96`

`ENABLE_OPENCL`이 정의되어 있고 `NNTR_ENGINE`이 설정되지 않으면
`causallm_engine()`은 `"gpu"`를 반환한다. 따라서 `repack_weight()`은
QS4CX tensor를 하나도 pack하지 않고 바로 끝난다.

그러나 현재 헤드의 CausalLM layer 생성 코드는 어디에도 `engine=`
속성을 넣지 않는다. 새 helper도 repack guard에서만 사용된다.
`Engine::parseComputeEngine()`은 engine 속성이 없는 layer를 CPU context로
보내므로, 실제 graph는 여전히 CPU에서 실행된다.

ARM의 CPU `FloatTensor::dotQs4cx()` 경로는 `input.getPackedData()`를
호출한다. 앞에서 `pack()`을 생략했기 때문에 첫 QS4CX 행렬곱에서
`"pack before run model"` 예외가 발생한다. 즉, 기본 환경의 OpenCL 지원
빌드는 CPU graph를 만들면서 weight만 GPU graph인 것처럼 준비해 추론이
중단된다.

등록되지 않은 환경에서 `NNTR_ENGINE=cuda`를 지정해도 같은 문제가 생긴다.
새 helper는 CUDA context의 등록 여부를 확인하지 않고 `"cuda"`를
반환하지만, 실제 engine registry는 CPU로 fallback하기 때문이다.

repack 생략 여부는 실제 compile된 layer/run context를 기준으로 결정해야
한다. 또는 이 최적화를 적용하기 전에 graph 전체에
`engine=<causallm_engine()>`을 일관되게 전달하고 해당 context가 실제로
등록되었는지 검증해야 한다.

## 남은 위험

ARM/OpenCL 장비에서 직접 실행하지는 못했다. 또한 이 guard는
`ENABLE_OPENCL`이 application translation unit에도 전달된다고 가정한다.
향후 engine routing을 완성할 때에는 반대 방향의 불일치, 즉 실제 GPU
graph인데도 불필요한 repack을 수행하는 경우도 함께 테스트해야 한다.
