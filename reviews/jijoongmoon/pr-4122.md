## 요약

이 PR은 모델을 읽는 동안 QS4CX weight를 `cudaMemPrefetchAsync()`로 GPU에
옮겨, load 시점의 host RSS를 줄이는 선택 기능을 추가한다. 직접 부모
#4121 대비 고유 변경은 production 파일 3개, 80줄 추가다. 기능은
`NNTR_CUDA_WPREFETCH=2` 이상일 때만 켜진다.

아이디어 자체는 타당하지만 현재 구현은 CUDA 13 전용 API를 무조건
사용하므로 CUDA 12 계열에서 빌드되지 않는다. 병렬 loader에서는 사용자가
고른 GPU가 아니라 기본 GPU 0을 목적지로 사용할 수 있다. 또한 QS4CX의
실제 메모리 크기보다 짧은 범위를 넘기며, Windows/WDDM 기본 allocator에서는
모든 요청이 조용히 무효화된다. 마지막으로 migration 속도에 맞춘
back-pressure나 완료 대기가 없어, PR이 목표로 한 load-time peak RSS 감소를
보장하지 못한다.

## 발견 사항

### P1 — CUDA 12.x에서는 CUDA 빌드가 컴파일되지 않음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1119-1124`

새 코드는 다음 CUDA 13 형식만 사용한다.

```cpp
cudaMemPrefetchAsync(ptr, bytes, cudaMemLocation, flags, stream)
```

그러나 [CUDA 12.6.2 공식 API](https://docs.nvidia.com/cuda/archive/12.6.2/cuda-runtime-api/group__CUDART__MEMORY.html)는
목적지를 `int dstDevice`로 받는 4개 인자 형식이고,
[CUDA 13.0.3 공식 API](https://docs.nvidia.com/cuda/archive/13.0.3/cuda-runtime-api/group__CUDART__MEMORY.html)부터
현재 코드의 5개 인자 형식을 사용한다. nntrainer의 CUDA build 설정에는
CUDA 13만 허용한다는 검사도 없다. 따라서 CUDA 12.x header로
`enable-cuda` build를 하면 인자 수와 형식이 맞지 않아 컴파일이 실패한다.

`CUDART_VERSION`으로 API 호출을 나누거나, 실제로 CUDA 13 이상만 지원할
계획이라면 configure 단계에서 명확하게 거부하고 지원 조건을 문서화해야
한다.

### P1 — 병렬 loader가 `NNTR_CUDA_DEVICE` 대신 GPU 0으로 prefetch할 수 있음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1101-1124`
- `nntrainer/cuda/cuda_context_manager.cpp:111-128`
- `nntrainer/models/neuralnet.cpp:1118-1123`
- `nntrainer/models/neuralnet.cpp:1202-1205`

CUDA의 current device는 host thread마다 관리된다. 기존
`NNTR_CUDA_DEVICE` 처리는 context를 초기화한 thread에서
`cudaSetDevice()`를 호출하지만, 이 PR이 만드는 load worker에는
`EnsureCurrent()`나 별도의 `cudaSetDevice()`가 없다.

그 상태에서 helper는 worker의 `cudaGetDevice()` 결과를 prefetch 목적지로
사용한다. 예를 들어 `NNTR_CUDA_DEVICE=1`이어도 새 worker는 기본값인
device 0을 볼 수 있다. weight와 전역 stream은 GPU 1용인데 목적지는 GPU
0이 되어 잘못된 GPU로 이동하거나 API가 실패한다. 호출부가 반환값을
버리므로 실패 사실도 보이지 않는다.

각 worker에서 선택한 CUDA context를 current로 만든 뒤,
`cudaGetDevice()`가 아니라 `ContextManager`가 보관한 device ordinal을
목적지로 사용해야 한다.

### P2 — 짝수 `K`에서 QS4CX scale tail의 일부를 prefetch하지 않음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1118`
- `nntrainer/tensor/qs4cx_tensor.cpp:99-116`

helper가 계산하는 byte 수는 다음과 같다.

```cpp
N * ((K + 1) / 2) + N * sizeof(float)
```

반면 QS4CX tensor의 실제 크기와 scale 시작점은 연산 순서가 다른
다음 식을 사용한다.

```cpp
N * (K + 1) / 2 + N * sizeof(float)
```

`K`가 짝수이면 helper의 범위가 `floor(N / 2)` byte 짧다. 예를 들어
`N=3, K=4`이면 실제 nibble 영역 뒤 scale은 offset 7에서 시작하지만,
helper는 offset 6부터 scale 크기만큼 옮긴 것으로 계산한다. 결과적으로
fp32 scale tail의 마지막 1 byte가 prefetch 범위에서 빠진다.

호출자가 tensor의 `getMemoryBytes()`를 넘기게 하거나, 적어도 tensor
구현과 같은 크기 계산 함수를 함께 사용해야 한다.

### P2 — Windows/WDDM 기본 구성에서는 옵션이 전부 조용히 무효화됨

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1107-1111`
- `nntrainer/cuda_mem_allocator.cpp:38-56`
- `nntrainer/cuda_mem_allocator.cpp:97-120`
- `nntrainer/models/neuralnet.cpp:1190-1195`

helper는 pointer type이 `cudaMemoryTypeManaged`일 때만 prefetch한다. 하지만
`concurrentManagedAccess`를 지원하지 않는 Windows/WDDM 환경에서 기존
weight allocator의 기본값은 `cudaHostAllocMapped()`로 만든 host-mapped
memory다. 따라서 Windows의 discrete GPU에서도
`NNTR_CUDA_WPREFETCH=2`를 켜면 모든 weight가 조건에서 탈락한다.

helper는 `false`를 반환하지만 호출부가 `(void)`로 버리므로 load는
성공한 것처럼 끝나고, 사용자는 host RSS가 줄지 않은 이유를 알 수 없다.
지원할 수 없는 allocator 구성이라면 옵션을 켤 때 한 번은 명확히
경고하거나 거부해야 한다. 지원 가능한 구성에서도 실패 횟수를 숨기지
않아야 한다.

### P2 — enqueue만 계속해 load-time peak RSS 감소를 보장하지 못함

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1123-1129`
- `nntrainer/models/neuralnet.cpp:1118-1199`
- `nntrainer/models/neuralnet.cpp:1202-1210`

최대 8개의 loader가 weight를 읽은 뒤 하나의 CUDA stream에 비동기
prefetch를 계속 넣는다. 그러나 다음 weight를 읽기 전 migration 완료를
제한하는 back-pressure가 없고, worker를 join한 뒤에도 stream이나 event를
기다리지 않는다.

디스크·메모리 read가 PCIe migration보다 빠르면 요청이 모델 전체까지
쌓일 수 있다. 이 경우 모든 weight page가 먼저 CPU에서 touch되어 기존과
비슷한 peak RSS가 생기며, `load()`가 반환할 때도 migration 완료를
보장하지 못한다. 이후 연산이 같은 stream을 사용하면 순서는 지켜질 수
있으므로 계산 정확성 문제가 아니라, 이 PR의 메모리 목표를 달성하지
못하는 문제다.

일정한 outstanding byte 수마다 event를 기다리는 방식으로 load 속도를
제어하고, 최소한 load 종료 시 모든 요청의 성공과 완료를 확인해야 한다.

## 추가 관찰

`cuda_wprefetch_load`는 CUDA node가 하나만 있어도 model 전체에 대해
켜지지만, 실제 weight loop에서는 현재 `node->isComputeEngineCUDA()`를
다시 확인하지 않는다. mixed-engine graph에서는 CPU/OpenCL node의 QS4CX
weight까지 helper에 전달된다. 일반 host pointer라면 조용히 실패하고,
managed allocation이라면 불필요하게 VRAM으로 이동했다가 consumer에서
다시 migration될 수 있다. prefetch block 자체를 현재 CUDA node로
한정하는 편이 안전하다.

필요하다.
