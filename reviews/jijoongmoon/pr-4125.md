## 요약

이 PR은 `NNTR_DETERMINISTIC`을 기본으로 켜고 OpenCL kernel 객체를 최대 8개
복제해 순환시키며, Intel OpenCL reduction과 CUDA cuBLAS 실행 방식을 더
결정적으로 만들려는 변경이다. 고유 diff는 8개 파일, 158줄 추가와 13줄
삭제다.

의도와 달리 주력 Adreno attention 경로는 반환받은 kernel 포인터를
`static`으로 보관하므로 새 ring을 한 번만 거친 뒤 같은 객체를 계속
재사용한다. 새 ring 자료구조 자체도 동기화 없이 전역 상태를 수정해 병렬
모델 실행에서 C++ data race를 만든다. 초기 회전 순서도 한 칸 어긋나
약속한 재사용 간격보다 빨리 같은 clone을 돌려준다.

또한 기본값 변경으로 Intel attention의 기존 subgroup 경로를 꺼 코드
주석에 기록된 측정치 기준 136 ms에서 494 ms로 약 3.6배 느려질 수 있다.
반면 CUDA의 pedantic math 설정은 저장소에서 호출되지 않는 함수 안에만
있어 실제 CUDA 경로의 재현성을 바꾸지 않는다.

## 발견 사항

### P1 — 핵심 attention 호출부가 kernel ring을 완전히 우회함

위치:

- `nntrainer/cl_context.cpp:411-450`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2115-2123`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2238-2242`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2293-2299`

ring은 `registerClKernel()`을 호출할 때만 다음 clone을 반환한다. 그러나
Adreno image attention의 QK, softmax, SV 호출부는 반환 포인터를 각각
함수 정적 변수에 저장한다. 첫 호출 뒤에는 `registerClKernel()`을 다시
부르지 않고 동일한 `cl_kernel`에 인자를 다시 설정해 enqueue한다.

따라서 PR이 해결하려는 “이전 enqueue가 kernel 인자를 확정하기 전에 다음
호출이 같은 객체의 인자를 덮는 문제”가 바로 그 핵심 경로에 남는다. 변경
코드의 주석도 정적 캐시 호출부에는 singleton 동작이 남는다고 인정한다.
`NNTR_ATTN_DRAIN`의 기본값도 꺼져 있어 이전 제출 완료를 대신 보장하지
않는다.

회전을 kernel 등록 시점이 아니라 인자 설정과 enqueue를 포함한 dispatch
lease 단위로 적용하거나, 이 정적 캐시들을 ring-aware 구조로 바꿔야 한다.
현재 상태에서는 기본 deterministic 계약의 핵심 목적이 성립하지 않는다.

### P1 — 전역 ring 상태를 무잠금으로 변경해 병렬 실행 시 data race가 발생함

위치:

- `nntrainer/cl_context.cpp:435-450`

새 `static ring_map`은 매 호출마다 `operator[]`, `vector::push_back`,
`slot.second` 갱신을 수행하지만 mutex나 thread-local 분리가 없다.
서로 다른 모델 또는 API 스레드가 동시에 kernel을 등록·조회하면
`unordered_map` 재해시와 vector 변경 자체가 C++의 정의되지 않은 동작이
된다. ring을 모두 채운 뒤에도 회전 인덱스를 동시에 쓰므로 문제는
초기화 구간에 한정되지 않는다.

두 스레드가 같은 clone을 돌려받으면 각각 수행한 `clSetKernelArg`가 섞여
잘못된 buffer나 shape로 dispatch될 수도 있다. 자료구조 조회만 잠그는
것으로는 반환 이후의 인자 설정부터 enqueue까지 보호할 수 없으므로,
스레드별 clone 또는 dispatch 전체를 소유하는 lease가 필요하다.

### P1 — 기본값이 Intel attention의 측정된 고속 경로를 꺼 약 3.6배 회귀함

위치:

- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2609-2630`

환경 변수가 없으면 `NNTR_DETERMINISTIC`이 켜진 것으로 처리되어 Intel
buffer attention의 `sub_group_reduce_add` 경로를 사용하지 않고 LDS tree
reduction으로 돌아간다. 바로 위 코드 주석에는 같은 M=1024 attention에서
subgroup 경로가 136 ms, LDS 경로가 494 ms라고 적혀 있다. 즉 기본
동작만으로 해당 구간이 약 3.6배 느려질 수 있다.

PR 본문의 성능 확인은 RTX CUDA와 Adreno를 대상으로 한다. Adreno는 이
Intel 전용 subgroup 분기를 사용하지 않으므로 이 회귀를 검증하지 못한다.
“기본 활성화” 전에 Intel에서 end-to-end prefill 성능과 실제 재현성 차이를
측정해야 한다. 비용이 이 정도라면 deterministic을 명시적으로 요청한
경우에만 LDS 경로를 사용하거나 플랫폼별 기본값을 정해야 한다.

### P2 — ring 초기 회전이 한 칸 어긋나 약속한 K회 간격을 지키지 못함

위치:

- `nntrainer/cl_context.cpp:438-450`

clone을 `K`개 만드는 동안 `slot.second`는 계속 0이다. 모두 채운 다음
호출에서는 인덱스를 먼저 1로 증가시키고 `clones[1]`을 반환한다. K=8의
실제 초기 순서는 `0,1,2,3,4,5,6,7,1,...`이므로 clone 1은 8회가 아니라
7회의 다른 호출 뒤 재사용된다. 명시적으로 K=2를 설정하면
`0,1,1,0,...`이 되어 직전 enqueue와 같은 kernel을 즉시 다시 사용한다.

clone을 추가할 때 현재 인덱스를 마지막 clone에 맞추거나, 현재 clone을
반환한 뒤 인덱스를 증가시키는 방식으로 순서를 바로잡아야 한다. K=2 같은
작은 명시값을 포함한 순환 단위 테스트도 필요하다.

### P2 — CUDA pedantic 설정이 호출되지 않는 함수 안에 있어 실제 경로에 적용되지 않음

위치:

- `nntrainer/cuda/cuda_blas_manager.cpp:66-97`
- `nntrainer/cuda/cuda_blas_manager.h:45`

`NNTR_DETERMINISTIC`에 따라 `CUBLAS_PEDANTIC_MATH`를 설정하는 코드는
`BlasManager::sgemmRowMajor()` 안에만 추가됐다. 그러나 현재 PR 헤드 전체를
검색하면 이 함수는 선언과 정의만 있고 호출부가 없다. 현재 CUDA FC는
`igemmRowMajor()` 등 다른 경로를 사용한다.

결과적으로 PR의 RTX 실행·성능 측정도 이 분기를 실행하지 않았고, 이
변경만으로는 실제 FP32 CUDA 계산의 math mode가 고정되지 않는다. 실제
FP32 dispatch 경로에서 설정하거나 BLAS manager 초기화 시 handle 단위로
설정하고, mode 조회 또는 결과 반복 비교로 실행됐음을 검증해야 한다.

## 정상으로 확인한 부분

- `NNTR_DETERMINISTIC=0`일 때 기본 ring 크기가 1로 돌아가는 opt-out은
  구현되어 있다.
- 명시적인 `NNTR_CL_KERNEL_RING` 값이 deterministic opt-out보다 우선한다.
- Intel subgroup 경로는 `NNTR_FLASH_SG=1`로 명시적으로 다시 켤 수 있다.
- 기존 OpenCL program cache를 재사용해 clone마다 program을 다시
  컴파일하지는 않는다.
- `NNTR_POISON_FILL`은 기본값이 꺼진 진단 옵션이라 정상 실행 결과를
  직접 바꾸지 않는다.

## 진단 옵션의 남은 공백

`NNTR_CL_SYNC_IO=1`은 command queue manager wrapper를 통한 일부
write/read만 동기화한다. attention과 FC에 남은 직접
`clEnqueueWriteBuffer(..., CL_FALSE, ...)` 호출과 비동기 unmap은 이 옵션을
우회한다. 따라서 이 옵션을 켜도 host-I/O 비동기 문제를 완전히 배제했다고
판단해서는 안 된다. 이는 기본 실행의 별도 회귀라기보다 PR이 추가한 진단
도구의 한계로 분류했다.

## 이전 PR에서 이어진 문제

자동 리뷰가 지적한 아래 두 항목은 현재 헤드에서도 유효하지만 #4125의
고유 변경은 아니다.

- CUDA node가 있어도 graph allocator가 CPU allocator로 결정될 수 있는
  #4117의 allocator 선택 문제
- 등록 이름 `NNTR_CUDA_EAGER_CTX`와 실제 조회 이름
  `NNTR_CUDA_EAGER_INIT`이 다른 선행 변경

고유 finding에는 중복 기재하지 않았다.

## 테스트 공백

이 PR에는 고유 변경을 검증하는 자동 테스트가 없다. 최소한 다음이
필요하다.

- K=2와 K=8의 kernel 반환 순서 테스트
- 여러 스레드와 여러 모델이 같은 kernel key를 동시에 dispatch하는 테스트
- QK, softmax, SV 호출이 실제로 서로 다른 clone을 사용하는지 확인하는 테스트
- Intel OpenCL에서 deterministic on/off 결과 재현성과 prefill 성능 비교
- 실제 CUDA FP32 호출 경로에서 cuBLAS math mode가 적용되는지 확인

현재 환경에는 대상 OpenCL/CUDA GPU와 드라이버가 없어 runtime 재현은
수행하지 못했다.
