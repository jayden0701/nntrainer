## 한눈에 보기

이 PR은 `_Float16`을 지원하지 않는 MSVC에서도 FP16을 쓸 수 있도록, 16비트
정수를 속에 담은 `Half` 타입을 추가한다. 직접 부모와 비교하면 8개 파일,
642줄 추가와 13줄 삭제다.

가장 큰 문제는 새 `Half`가 “이 타입에서 가능한 가장 작은 값”을 표준
라이브러리에 알려 주지 않는다는 점이다. 그 결과 음수만 들어 있는 FP16
max-pooling은 실제 최댓값 대신 `0`을 반환한다. 소스 트리 안에서는 빌드되지만,
설치용 SDK에는 새 헤더와 타입 선택 정보가 빠진 문제도 있다. 또한 `double`을
Half로 바꿀 때 중간에 `float`로 한 번 더 반올림하여 native `_Float16`과 다른
비트를 만드는 경계값이 확인됐다.

## 발견 사항

### P1 — 음수만 있는 FP16 max-pooling이 존재하지 않는 `0`을 최댓값으로 고름

위치:

- `api/ccapi/include/half_fp16.h:152-173`
- `docs/design/msvc_fp16_half_wrapper.md:134`
- `nntrainer/layers/pooling2d_layer.cpp:361`
- `nntrainer/layers/pooling2d_layer.cpp:393`
- `nntrainer/layers/pooling2d_layer.cpp:446-452`
- `nntrainer/layers/pooling2d_layer.cpp:488-500`

`Half`에는 `std::numeric_limits<Half>` 정의가 없다. 따라서
`std::numeric_limits<Half>::lowest()`는 FP16의 최솟값이 아니라 기본값
`Half{}`를 돌려주며, 이 값은 `0`이다. 직접 작은 프로그램으로 확인한 결과도
다음과 같았다.

```text
lowest=0
is_specialized=0
```

반면 max-pooling과 global-max-pooling은 최댓값 찾기를
`std::numeric_limits<T>::lowest()`에서 시작한다. FP16 wrapper 빌드에서는
여기서 `T`가 `Half`가 된다. 예를 들어 입력이 `[-3, -2, -1]`이면 올바른 답은
`-1`이지만, 어떤 입력도 시작값 `0`보다 크지 않아 결과가 `0`으로 남는다.
학습 모드의 일반 max-pooling에서는 최대값 위치도 `-1`로 남을 수 있어
backward까지 틀어진다.

비유하면 참가자 점수가 모두 음수인데, 명단에 없는 0점 선수를 먼저 세워 놓고
우승자를 고르는 셈이다. 설계 문서는 `numeric_limits<Half>`가 어디에도
필요하지 않다고 적었지만, 실제 pooling 코드가 두 곳에서 사용하고 있다.

`std::numeric_limits<nntrainer::Half>`를 IEEE binary16 값으로 제대로
정의하고, 음수만 든 FP16 max/global-max의 forward와 backward를
`-Dfp16-impl=wrapper`에서 검사하는 테스트가 필요하다.

### P2 — 설치용 SDK에 새 Half의 “부품”과 “선택 방법”이 모두 빠져 있음

위치:

- `api/ccapi/include/tensor_dim.h:25-32`
- `api/ccapi/meson.build:16-24`
- `api/ccapi/meson.build:49-62`
- `api/ccapi/ccapi-ml-training.pc.in:12`
- `api/ccapi/include/layer.h:261-288`
- `meson.build:218-234`
- `debian/ccapi-ml-training-dev.install`
- `packaging/nntrainer.spec`

소스 트리 안에서는 `tensor_dim.h` 옆에 `half_fp16.h`가 있으므로 빌드된다.
하지만 public header 설치 목록과 Debian/Tizen 개발 패키지 목록에는
`half_fp16.h`가 없다. 설치된 `tensor_dim.h`는 wrapper 모드에서 존재하지
않는 파일을 include하게 된다.

또한 library를 만들 때 선택한 `ENABLE_FP16`과 `USE_HALF_WRAPPER`가
`nntrainer_ccapi_dep`나 pkg-config의 `Cflags`로 외부 사용자에게 전달되지
않는다. MSVC 사용자가 `ENABLE_FP16`만 주면 public header가 MSVC에 없는
`_Float16`을 선택하여 컴파일되지 않는다. 두 매크로를 모두 생략하면 더
위험하다. library 쪽 `Layer`에는 FP16 virtual 함수 두 개가 있지만 사용자 쪽
header에는 빠져, 이후 virtual 함수의 순서가 서로 달라질 수 있다.

비유하면 공장 안에서는 새 부품과 조립 설명서를 모두 갖고 제품을 만들었지만,
고객에게 보내는 상자에는 부품도 설명서도 넣지 않은 상태다. 함수 순서 문제는
서로 다른 목차를 보고 같은 페이지 번호를 누르는 것과 같아서, 잘못된 함수를
부를 수도 있다.

`half_fp16.h`를 모든 개발 패키지에 설치하는 것만으로는 충분하지 않다. 선택된
FP16 구현을 기록한 public config header를 생성·설치하고, public header가
그 설정을 직접 읽도록 해야 한다. `ENABLE_FP16` 전달 문제 자체는 이전에도
있었지만, 이 PR이 public 타입 선택에 새 `USE_HALF_WRAPPER` 조건을 추가하면서
MSVC 설치 경로에서 반드시 해결해야 하는 문제가 됐다.

새 헤더 설치 누락은 현재 head에 달린 기존 GitHub review에서도 같은 내용으로
지적되어 있다:
[discussion](https://github.com/nntrainer/nntrainer/pull/4129#discussion_r3619536940)

### P2 — `double`을 두 번 반올림하여 native `_Float16`과 다른 값이 나옴

위치:

- `api/ccapi/include/half_fp16.h:163-173`
- `docs/design/msvc_fp16_half_wrapper.md:29-36`

하나의 template 생성자가 `float`, `double`, `long double`, 정수를 모두 받은
뒤, 먼저 `float`로 바꾸고 다시 Half로 바꾼다. `double`과 `long double`은
native `_Float16`으로 바로 변환할 때보다 중간 반올림이 한 번 더 생긴다.

다음 경계값으로 실제 비트 차이를 확인했다.

```text
입력:    1 + 2^-11 + 2^-40
native:  0x3c01
wrapper: 0x3c00
```

비유하면 천 원 단위로 반올림해야 할 금액을 먼저 원 단위로 반올림한 뒤 다시
천 원 단위로 반올림하는 것과 같다. 대부분의 값은 결과가 같지만 경계에 아주
가까운 값은 반대쪽으로 넘어간다. 그러므로 PR 설명과 설계 문서의
“native와 byte-identical” 보장은 모든 산술 입력에 대해서는 성립하지 않는다.

`float` 변환과 `double`/`long double` 변환을 나누고, 뒤의 두 타입은 Half로
직접 한 번만 반올림해야 한다. 이를 지원하지 않을 계획이라면 drop-in 및
bit-identical 보장의 범위를 `float` 입력으로 명확히 줄이고 경계값 테스트를
추가해야 한다.

## 확인한 내용

- 직접 부모 대비 8개 파일의 고유 diff를 검토했다.
- 새 `Half`의 변환, 연산자, 표준 library 사용처를 전체 tree에서 검색했다.
- 작은 C++17 probe로 `numeric_limits<Half>::lowest() == 0`과
  음수 세 값의 max 결과가 `0`이 되는 것을 재현했다.
- 별도 probe로 `double` 직접 변환과 `float` 경유 변환의 비트 차이를 재현했다.
- mixed 연산 결과 타입은 native `_Float16`과 맞음을 확인했다.
- clang-cl의 MSVC 호환 모드에서 wrapper header와 AVX2 변환 파일이
  `/arch:AVX2` 조건으로 컴파일되는 것은 확인했다.
- 현재 GitHub 자동 검사는 모두 통과한다. 다만 Windows job은 FP16을 켜지 않고,
  Linux FP16 job은 `auto`에서 native `_Float16`을 선택하므로 새 wrapper
  경로를 검사하지 않는다.
- `git diff --check`는 설계 문서 끝의 불필요한 빈 줄 한 곳을 보고한다.

## 남은 위험

실제 `cl.exe` 전체 빌드와 Windows GPU inference는 이 리뷰에서 실행하지
않았다. MSVC의 F16C 변환과 software 변환은 NaN payload 비트를 서로 다르게
보존하므로, “모든 비트가 동일하다”는 보장은 NaN에서도 별도 정리가 필요하다.
최소한 CI에 `-Denable-fp16=true -Dfp16-impl=wrapper` 빌드와 위의 음수
max-pooling 회귀 테스트를 추가해야 이 PR의 핵심 경로를 계속 지킬 수 있다.
