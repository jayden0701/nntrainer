## 한눈에 보기

이 PR은 다음 PR에서 사용할 OpenCL 부품 세 개를 미리 추가한다.

1. RMSNorm과 INT8 양자화를 한 번에 하는 kernel
2. 여러 layer용으로 묶인 입력에서 한 layer 몫만 꺼내는 FP16 kernel
3. GPU 메모리 값을 관찰하는 진단용 probe

직접 변경은 5개 파일, 746줄 추가이며 이 PR 안에는 아직 caller와 test가 없다.
RMSNorm kernel의 행·열 인덱스, `K <= 2048` 범위, 마지막에 남는 원소, INT8
scale/zero-point/rounding과 row sum을 확인한 결과 kernel 안쪽의 확정된 범위
오류는 찾지 못했다.

하지만 부품을 실제 graph에 연결하는 바로 다음 PR #4150까지 따라가 보니,
`cl_mem`이 가리키는 큰 메모리 안에서 **몇 번째 batch부터 읽고 쓸지** 전달되지
않는다. batch가 2개 이상이면 두 번째 batch도 첫 번째 batch 자리에 접근한다.

비유하면 큰 아파트 건물 주소는 전달했지만 동·호수는 빼먹은 것이다. 첫 번째
집의 배달은 맞지만, 두 번째 집 물건도 전부 첫 번째 집 문 앞에 놓이게 된다.

## 직접 변경분의 문제

### P1 — `cl_mem` 경로가 batch별 tensor view의 시작 위치를 잃어버림

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1174-1184`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1198-1220`
- `nntrainer/tensor/tensor.cpp:1275-1285`
- 의도된 caller: PR #4150의
  `Applications/CausalLM/layers/per_layer_slice_gpu.cpp:71-93`

새 kernel은 전달받은 `cl_mem`의 0번 원소부터 다음처럼 읽고 쓴다.

```text
out[gid] = in[r * in_width + off + j]
```

wrapper에도 layer 내부 위치인 `off`는 있지만, 큰 tensor 안에서 input/output
view가 시작하는 위치는 인자로 없다. `Tensor::getClMem()`도 view의
`Tensor::getOffset()`을 더하지 않고 전체 allocation의 같은 `cl_mem`만 반환한다.

바로 다음 PR의 caller는 batch마다 다음 view를 만든다.

```text
input view  시작 = b * input feature length
output view 시작 = b * output feature length
```

SVM raw pointer 경로에서는 view의 포인터 자체가 이미 이동해 있으므로 맞다.
반면 `cl_mem` 경로에서는 모든 view가 똑같은 전체 buffer handle로 바뀐다.
따라서 `batch > 1`이면 다음 일이 생긴다.

- `b=0`: 우연히 올바른 곳을 읽고 쓴다.
- `b=1`: 다시 batch 0을 읽고 batch 0에 덮어쓴다.
- 실제 batch 1 output: 갱신되지 않은 값이 남는다.

현재 CausalLM의 흔한 1-prompt 추론에서는 batch가 1이라 숨을 수 있다. 그러나
layer 코드가 batch loop를 명시적으로 지원하고 있어, 여러 요청을 묶는
batched inference나 batch test에서는 조용히 잘못된 출력이 된다.

input/output의 element offset을 wrapper와 kernel 인자로 전달해 각각의 index에
더해야 한다. 또는 non-zero-offset view에서는 `cl_mem` 경로를 금지하고
offset이 반영되는 안전한 경로로 돌아가야 한다.

### P2 — fused 결과를 성공 전에 공개하고, 주소의 “세대”도 확인하지 않음

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2662-2701`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2703-2778`

fused INT8 결과 네 개는 kernel을 실행하기 전에 전역 pool에 등록된다.

```text
ptr:<output 주소>:fused_i8
ptr:<output 주소>:fused_scale
ptr:<output 주소>:fused_zp
ptr:<output 주소>:fused_rs
```

그 뒤 input buffer 생성·upload, gamma upload, kernel 등록, argument 설정 또는
dispatch 중 하나라도 실패하면 함수는 `false`를 반환하지만, 이미 공개한 항목을
지우거나 “실패한 결과”라고 표시하지 않는다. 후속 consumer는 lookup에 성공해
이번 output 대신 이전 값 또는 아직 채워지지 않은 buffer를 사용할 수 있다.

주소만 key로 쓴 점도 별도 위험이다. 계산이 끝난 tensor의 메모리 자리를 같은
크기의 새 tensor가 받으면 주소가 같아질 수 있지만, pool에는 “이 주소의 몇 번째
사용자인가”라는 정보가 없다. 예전에 살던 사람 이름이 붙은 택배함을 새 입주자도
그대로 쓰는 것과 같다.

이 문제는 앞서 살펴본 v8c activation cache와 같은 종류다. 현재 #4149에는
consumer가 없어 즉시 보이는 오류는 아니지만, PR이 설명한 “downstream FC가 이
결과를 바로 소비”하는 단계에서는 correctness 조건이 된다.

alias는 dispatch 성공 뒤에만 공개하고, tensor/MemoryData의 identity와 generation을
key 또는 metadata에 포함해야 한다. 모든 실패 경로에서도 해당 generation을
무효화해야 한다.

### P2 — gamma cache가 이름과 크기만 보고 예전 가중치를 재사용할 수 있음

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2570-2581`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2716-2744`

GPU로 복사한 RMSNorm gamma는 process-global `cl_mem` 하나에 보관되고,
`gamma.getName()`과 `K`가 같으면 다시 upload하지 않는다.

평범한 한 번의 inference 동안 gamma가 바뀌지 않는 경우에는 결과가 맞다. 그러나
같은 구조와 tensor 이름으로 모델을 unload한 뒤 다른 weight를 load하거나,
OpenCL context를 다시 만들면 이름과 길이는 같아도 내용과 GPU context는 달라질
수 있다. 현재 코드는 이를 구별하지 못해 이전 모델 gamma를 계산에 쓸 수 있다.

비유하면 책 제목과 페이지 수가 같다는 이유로 개정판을 펼치지 않고 예전 책의
복사본을 계속 읽는 것이다.

또 “gamma 이름별로 한 번 upload”라는 주석과 달리 실제 자료구조는 map이 아니라
슬롯 하나다. 여러 RMSNorm layer를 차례로 부르면 이름이 바뀔 때마다 직전
buffer를 버리고, 다음 token에서도 모든 layer의 gamma를 다시 blocking upload한다.
정확성 문제와 별개로 의도한 성능 효과도 얻기 어렵다.

cache key에는 context와 weight의 identity/generation을 포함하고, 이름별 entry를
보관하거나 model/context lifecycle에서 확실히 비워야 한다.

### P2 — FP32 전용 kernel이 불필요하게 FP16 지원을 요구함

위치:

- `nntrainer/tensor/cl_operations/cl_kernels/fused_rmsnorm_quant.cl:32`

이 kernel의 parameter와 계산은 모두 `float`, `char`, `int`이고 `half`를 전혀
쓰지 않는다. 그런데 파일 첫 부분에서 다음 확장을 무조건 켠다.

```text
#pragma OPENCL EXTENSION cl_khr_fp16 : enable
```

[Khronos의 공식 OpenCL 설명](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/EXTENSION.html)은
`enable`한 확장을 장치가 지원하지 않으면 이 pragma에서 error를 보고하도록
정한다. 즉 FP32 계산만 할 수 있는 장치도 필요 없는 “FP16 회원증”이 없다는
이유로 runtime kernel build에 실패한다.

특히 이 파일은 `enable-fp16=false`일 때도 기본 kernel 목록에 포함되고, PR 본문도
그 build 조합을 지원한다고 적었다. `cl_khr_fp16` pragma를 제거해야 한다.

### P3 — `=0`도 기능을 켜고, CHECK는 byte-identical을 검증하지 않음

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2644-2646`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2584-2597`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:2782-2832`

문서에는 `NNTR_FUSED_RMSQ=1`과 `NNTR_FUSED_RMSQ_CHECK=1`이라고 되어 있지만
구현은 환경변수가 **존재하는지만** 본다. 따라서 사용자가
`NNTR_FUSED_RMSQ=0`으로 명시적으로 끄려 해도 기능이 켜진다. 저장소에 이미 있는
`nntr_env_on()`과 같은 값 해석 helper를 써야 한다.

CHECK의 CPU 기준은 제곱합을 `double`로 앞에서부터 더한 뒤 `sqrt`를 사용한다.
GPU kernel은 64개 작업자가 `float`로 나눠 더하고 tree reduction과 `rsqrt`를
사용한다. 두 회계사가 금액을 서로 다른 묶음과 순서로 더하는 셈이라 아주 가까울
수는 있어도 마지막 비트와 INT8 반올림 결과까지 항상 같다고 보장할 수 없다.

실제로 CHECK 코드도 scale 차이를 허용하고 INT8 차이 개수를 출력한다. 따라서
“byte-identical CPU pipeline”이라는 설명은 너무 강하다. 허용 오차 기반의 수치
비교라고 문서를 고치거나, 실제 CPU RMSNorm 경로와 같은 연산을 기준으로
사용해야 한다.

## 진단 probe의 낮은 우선순위 문제

`clmem_probe_capture()`는 실행 결과가 아니라 디버깅용이므로 위 문제들보다
우선순위는 낮지만, 공개된 함수 계약에는 다음 빈틈이 있다.

- `bytes > 0`이면 허용하면서 dump에서 항상 처음 8바이트(`v16[0..3]`)를 읽어,
  1~7바이트 입력은 host OOB가 된다.
- SVM copy는 `bytes / 2`개의 FP16만 복사하므로 홀수 번째 마지막 바이트를
  빠뜨린다.
- 기본 모드의 buffer copy는 앞선 compute와 확실히 순서를 맞추지 않아 코드
  주석 자체가 stale/zero snapshot 가능성을 인정한다.
- process-global vector와 kernel argument 재설정에 mutex가 없어 동시 capture를
  안전하게 지원하지 않는다.

현재 다음 PR의 의도된 호출은 큰 FP16 tensor여서 작은/홀수 byte 오류가 바로
나타나지는 않는다. 그래도 범용 API라면 최소 크기 제한, event dependency,
SVM ownership 전환과 동시성 규칙이 필요하다.

## 현재 branch에서 확인된 범위

- #4149 안의 새 함수 세 개는 저장소 내 caller가 0개이고 관련 test도 없다.
- 새 RMSNorm kernel은 로컬 clang OpenCL frontend의 syntax 검사를 통과했다.
- 이 Windows 환경의 Intel Iris Xe OpenCL driver에서
  `clBuildProgram`과 `clCreateKernel`도 성공했다.
- 위 결과는 Android/Adreno runtime compile이나 kernel 실행·수치 비교까지
  확인한 것은 아니다.
- C++ 직접 변경분의 clang-format 14 검사와 `git diff --check`는 통과했다.
- fused RMSNorm kernel의 `M/K` indexing, `K` tail, local-memory 한계,
  min/max, quant scale/zero-point/clamp와 row sum에서는 확정 오류를 찾지 못했다.

최소한 다음 test가 필요하다.

1. `batch=2`와 non-zero input/output view offset의 `cl_mem` slice 결과
2. kernel dispatch 실패 뒤 fused alias가 lookup되지 않는지 확인
3. 같은 이름·크기의 gamma 값을 바꾼 model reload
4. FP16 확장이 없는 OpenCL 장치에서 FP32 fused kernel runtime build
5. `NNTR_FUSED_RMSQ=0/1`과 CHECK 설정별 선택

## 최종 판단

새 fused RMSNorm+quant kernel의 기본 계산 자체는 살펴본 범위에서 일관적이다.
그러나 `per_layer_slice`의 `cl_mem` 경로는 view offset을 표현할 수 없어 바로
다음 PR의 `batch > 1` 연결에서 잘못된 메모리를 읽고 쓴다. 먼저 offset을
명시적으로 전달하는 방식으로 고쳐야 한다.

fused 결과와 gamma cache도 이름·주소만으로 현재 tensor인지 판단해서는 안 된다.
성공한 이번 계산의 결과라는 generation/lifetime 정보를 넣고, 실패한 결과는
consumer에게 보이지 않게 해야 한다. 그 뒤 runtime OpenCL test와 model reload,
batch 2 test로 실제 소비 경로까지 검증하는 것이 안전하다.
