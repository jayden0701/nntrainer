## 한눈에 보기

OpenCL 메모리 pool에는 같은 tensor를 위해 두 종류의 자리를 함께 마련할 수 있다.

- SVM 자리: CPU와 GPU가 함께 볼 수 있는 공간
- `cl_mem` 자리: GPU가 전용 방식으로 사용하는 공간

기존 코드는 어떤 tensor가 SVM만 사용하더라도 두 자리를 모두 만들었다. 이번 PR은
먼저 각 tensor의 사용 방식을 분류한 뒤, SVM만 사용하는 메모리 자리에는 필요 없는
`cl_mem`을 만들지 않는다.

비유하면 모든 입주자에게 일반 주차 자리와 전기차 충전 자리를 하나씩 예약하던 것을,
전기차를 실제로 쓰는 입주자가 있는 경우에만 충전 자리를 남기는 변경이다. 긴
KV-cache처럼 큰 tensor에서는 사용하지 않는 두 번째 공간을 수백 MB 줄일 수 있다.

직접 변경한 로직을 따라가 본 결과, SVM tensor와 GPU tensor가 같은 메모리 자리를
시간차로 재사용하는 경우도 안전하게 처리한다. 이번 PR 고유 79줄에서 새 correctness
blocker는 찾지 못했다.

## 이번 PR 고유 변경에서 확인한 내용

### token과 메모리 자리의 연결이 맞음

`MemoryPool::requestMemory()`는 요청 순서대로 token `1, 2, 3, ...`을 반환한다.
`padded_offsets_[i]`도 같은 요청 순서로 만들어진다. 따라서 이번 코드가
`i + 1`을 token으로 사용하는 것은 맞다.

### 분류 전·후 결과가 달라질 경로가 없음

allocation 전에 하는 예비 분류와 allocation 뒤 실제 tensor에 찍는 분류는 같은
`ResidencyPlanner` 객체와 같은 입력을 사용한다.

- producer engine
- 모든 consumer가 GPU인지 여부
- 자료형
- tensor 역할과 이름
- view 수

`classify()`도 내부 상태를 바꾸지 않는 함수다. 따라서 예비 분류에서 SVM이라고 보고
`cl_mem`을 생략했는데, 직후 실제 분류에서는 갑자기 `GPU_CLMEM`이 되는 경로는 현재
코드에 없다.

### 같은 자리를 재사용하는 경우도 필요한 버퍼를 보존함

planner는 서로 동시에 살지 않는 tensor에 같은 offset을 줄 수 있다. 이번 코드는
token 하나만 보지 않고, 같은 offset을 쓰는 token 전체를 확인한다.

| 같은 offset을 쓰는 tensor | 처리 |
|---|---|
| 모두 SVM | 사용하지 않는 `cl_mem` 생략 |
| SVM과 `GPU_CLMEM`이 섞임 | `cl_mem` 유지 |
| 모두 `GPU_CLMEM` | `cl_mem` 유지 |

비유하면 오전 입주자와 오후 입주자가 같은 주차 칸을 번갈아 쓰더라도, 둘 중 한 명이라도
전기차라면 충전 시설을 남기는 방식이다. 따라서 나중에 GPU tensor가 필요한 버퍼를
찾지 못하는 문제는 생기지 않는다.

### SVM 원본과 해제 경로는 유지됨

이번 변경은 두 번째 `cl_mem` plane만 골라서 생략한다. 기본
`MemoryPool::allocate()` 또는 `allocateFSU()`가 만드는 SVM backing은 그대로 있고,
해제도 기존 경로를 그대로 탄다. 현재 `getClMem()` 사용처도 `isClMem()`으로 분류를
확인한 뒤 GPU 버퍼를 사용한다.

`NNTR_CLMEM_SVM_SKIP=0`을 프로세스 시작 전에 설정하면 기존처럼 모든 offset의
`cl_mem`을 만드는 비교 실행도 가능하다.

## 직접 변경에 권장하는 보강

### PR 설명의 “assert”는 실제 코드에 없음

PR 본문은 생략된 offset에 실제 `cl_mem` bind가 들어오면 assert한다고 설명한다.
하지만 이번 diff에는 그런 assert가 없다.

- `getClMem()`은 handle이 없으면 `nullptr`을 반환한다.
- `ensureZeroFilled()`과 raise/lower 함수는 handle이 없으면 조용히 돌아간다.

현재는 앞뒤 분류가 완전히 같아서 이 불일치가 일어나는 실제 경로를 찾지 못했다.
따라서 지금 당장 발생하는 blocker로 분류하지는 않는다. 다만 약속한 안전장치를
구현하려면 실제 stamp 단계에서 다음 invariant를 검사하는 편이 좋다.

```text
분류가 GPU_CLMEM이면 device_mem은 반드시 null이 아니어야 한다.
```

비유하면 충전차 등록표와 충전 자리 배정표가 지금은 같은 담당자에게서 나와 맞지만,
마지막 출차 전에 “충전차인데 자리가 없는가”를 한 번 확인하면 이후 코드 변경에도
안전하다.

### 새 동작을 검사하는 테스트가 없음

이번 PR은 테스트 파일을 추가하지 않았다. 현재 CI는 컴파일과 기존 테스트는 통과하지만,
다음 핵심 조합을 직접 검사하지 않는다.

1. 같은 offset을 SVM token만 재사용하면 `cl_mem`이 없는가
2. 같은 offset에 SVM과 `GPU_CLMEM` token이 섞이면 `cl_mem`이 남는가
3. kill switch를 켜면 예전 allocation 수로 돌아오는가
4. allocation 전·후 분류가 같고 `GPU_CLMEM`에는 항상 handle이 있는가

작은 가짜 planner layout으로 위 네 경우를 검사하면 실제 대형 모델을 실행하지 않고도
회귀를 막을 수 있다.

## 선행 PR에서 그대로 넘어온 미해결 blocker

GitHub에는 현재 네 개의 review thread가 있고, 모두 최신 head에서
`unresolved`, `not outdated` 상태다. #4145가 직접 바꾼 3개 파일 밖의 문제이며,
직접 부모인 #4114와 그 아래 스택에서 넘어왔다.

### P1 — GPU addition이 새 residual OpenCL 경로를 사용하지 않음

[`Route GPU addition through the CL residual op`](https://github.com/nntrainer/nntrainer/pull/4145#discussion_r3643580510)

GPU factory가 일반 `AdditionLayer`를 만들지만 이 layer는 여전히
`copy()/add_i()`를 사용한다. OpenCL용 residual 연산으로 연결되지 않아 지원되지 않는
element-wise 함수에서 실행이 실패할 수 있다.

### P2 — incremental FC에서 fused activation을 적용하지 않음

[`Apply fused FC activation during incremental inference`](https://github.com/nntrainer/nntrainer/pull/4145#discussion_r3643580518)

일반 forward에서는 FC 뒤 activation을 적용하지만 token을 하나씩 만드는 incremental
경로에서는 생략한다. 같은 FC가 prefill과 decode에서 서로 다른 계산을 하게 된다.

### P1 — 서로 다른 planner offset이 정렬 뒤 같은 GPU buffer가 될 수 있음

[`Preserve distinct cl_mem buffers for distinct offsets`](https://github.com/nntrainer/nntrainer/pull/4145#discussion_r3643593012)

서로 다른 raw offset을 위쪽으로 정렬한 값을 buffer의 신분증처럼 사용한다. 예를 들어
정렬 단위가 128일 때 raw offset 32와 96은 모두 128이 된다. 동시에 살아 있는 서로
다른 tensor가 같은 GPU buffer의 0번 위치부터 쓰게 되므로 서로의 값을 덮을 수 있다.

이번 PR도 그 `padded_offset`을 기준으로 생략 여부를 모으므로, 이 부모 문제를 고치지는
않는다. 자세한 근거는 [PR #4109 리뷰](./pr-4109.md)에도 정리돼 있다.

### P2 — reinitialize 뒤에는 ClBufferPool이 사라짐

[`Recreate pools through the allocator factory`](https://github.com/nntrainer/nntrainer/pull/4145#discussion_r3643593018)

처음 만들 때는 allocator factory를 통해 `ClBufferPool`을 얻지만,
`reinitialize()`와 `setAllocator()`는 일반 `MemoryPool`을 직접 만든다. 같은 graph를
다시 초기화하면 GPU buffer handle이 더 이상 붙지 않을 수 있다.

그 밖에 producer/consumer의 실제 cl_mem 지원 여부, graph output lower, FC host
epilogue와 boundary copy 문제도 직접 부모의 [PR #4114 리뷰](./pr-4114.md)에 정리한
상태 그대로다.

## 최종 판단

이번 PR이 새로 추가한 “SVM-only offset의 `cl_mem` 생략” 방식 자체는 합리적이며,
코드에서 새 기능 결함을 찾지 못했다. 선행 #4114가 먼저 수정되어 깨끗한 base가 된다는
조건이라면 이 direct delta는 승인할 수 있다.

현재 GitHub의 #4145 전체를 그대로 병합하는 것은 권장하지 않는다. 위의 미해결 P1/P2가
같은 head에 포함돼 있기 때문이다. 먼저 부모 스택의 blocker를 해결하고 rebase한 뒤,
작은 allocation 단위 테스트와 설명에 약속한 invariant 검사를 추가하는 것이 안전하다.
