## 한눈에 보기

이 PR은 header 안에 있던 `ThreadManager::Global()`의 실제 생성을 cpp 파일로
옮긴다. 직접 부모 대비 2개 파일, 22줄 추가와 1줄 삭제의 작은 변경이다.

한 shared `nntrainer.dll`을 모든 사용자가 함께 불러오는 구성이라면 이 방향은
맞다. 모든 호출이 DLL 안의 한 함수로 모여 같은 `ThreadManager`를 받는다.
하지만 현재 공식 Windows 설정은 `nntrainer`를 정적으로 연결한다. CausalLM의
여러 layer DLL이 그 정적 library를 각자 품으므로, 새 cpp 함수와 그 안의
`static ThreadManager`도 DLL마다 복사된다. 따라서 이 PR이 고치려는 실제
Windows 구성에서는 결과가 이전과 같다.

## 발견 사항

### P1 — Windows 기본 구성은 cpp까지 DLL마다 복사하므로 목적한 수정이 동작하지 않음

위치:

- `configurations/windows-native.ini:14`
- `configurations/windows-native-clang.ini:14`
- `nntrainer/meson.build:111-149`
- `Applications/CausalLM/layers/meson.build:88-109`
- `Applications/CausalLM/layers/mha_core.cpp:596`
- `Applications/CausalLM/layers/embedding_layer.cpp:567`
- `nntrainer/utils/thread_manager.cpp:43-48`

두 Windows 설정은 모두 `default_library = 'static'`이다. 이때
`nntrainer/meson.build`는 `nntrainer_dep`가 `nntrainer_shared`가 아니라
`nntrainer_static`을 가리키게 한다.

CausalLM의 `mha_core_layer`와 `embedding_layer`는 서로 다른 shared library,
즉 Windows에서는 서로 다른 DLL로 만들어진다. 두 DLL 모두
`nntrainer_dep`를 연결하고 실제로 `ThreadManager::Global()`을 호출한다.
정적 library를 DLL에 연결하면 `thread_manager.cpp`도 DLL마다 한 벌씩 들어간다.
결국 각 DLL 안의 `Global()` 함수와 함수 내부 `static ThreadManager instance`도
서로 다른 객체다.

비유하면 여러 사무실에 흩어져 있던 관리자를 한 관리실로 옮겼지만, 관리실이
든 건물 전체를 DLL마다 복사한 셈이다. 복제된 건물마다 관리실과 관리자가 다시
하나씩 생기므로 “회사 전체에 관리자 한 명”이 되지 않는다.

모든 Windows DLL이 하나의 `nntrainer.dll`을 import하도록 별도의 shared
dependency를 제공하거나, thread manager만 소유하는 공용 DLL을 둬야 한다.
`default_library=static`을 유지해야 한다면 단순히 함수를 cpp로 옮기는 것으로는
해결할 수 없다. 최소 두 개의 실제 DLL에서 `&ThreadManager::Global()`을
가져와 주소가 같은지 검사하는 Windows 회귀 테스트가 필요하다.

참고로 `default_library=shared` 구성에서는 이 PR의 방식이 동작한다. Windows
shared `nntrainer`는 정적 object의 외부 symbol을 모아 `.def`를 생성하므로 새
`Global()`도 export된다. 문제는 현재 기본·CI 구성이 그 shared dependency를
사용하지 않는다는 점이다.

### P2 — 부모의 `Global()`도 그대로 남아 한 binary 안에서 두 관리자를 만들 수 있음

위치:

- `nntrainer/utils/singleton.h:28-49`
- `nntrainer/utils/thread_manager.h:145-159`
- `nntrainer/utils/thread_manager.cpp:43-48`

`ThreadManager`가 새로 선언한 static `Global()`은 부모
`Singleton<ThreadManager>::Global()`을 override하지 않는다. static 함수는
override할 수 없고, 새 함수가 부모 이름을 가릴 뿐이다. 부모 함수 안에는
자신만의 `static ThreadManager instance`가 그대로 남아 있다.

따라서 아래 두 주소는 이 PR 이후 서로 다르다.

```cpp
&ThreadManager::Global()
&Singleton<ThreadManager>::Global()
```

이전에는 첫 표현도 상속받은 부모 함수를 가리켰으므로 두 호출이 같은 객체를
돌려줬다. 이제 부모 형태로 호출하는 기존 또는 외부 코드는 별도 worker pool을
만든다. 두 객체는 `config_`만 공유하고 worker thread, `once_flag`, 종료 시점은
각각 가진다.

비유하면 `Global`이라고 적힌 문이 두 개 있는데, 같은 관리실로 이어지는 것이
아니라 각기 다른 관리자에게 연결된 상태다. 현재 repository 안에는 부모
형태의 호출이 없어 당장 기본 경로를 깨지는 않지만, public으로 열려 있는
호출이며 “항상 하나”라는 보장을 약하게 만든다.

`Singleton<ThreadManager>::Global()` 자체를 owner library에서 명시적으로
구현하고 `ThreadManager::Global()`도 그 한 구현으로 전달하거나, 이 타입에서
부모 accessor를 외부가 부를 수 없게 해야 한다. 두 표기와 서로 다른 DLL을
조합해도 모두 같은 주소인지 테스트해야 한다.

  따라갔다.

  있음을 확인했다.
- 함수 내부 static 생성과 `initializeOnce()`의 동시 호출 안전성에는 별도
  회귀를 찾지 못했다.

  test도 없다.
- `git diff --check`는 통과했다.
- 현재 GitHub 자동 검사와 두 개의 기존 approval은 모두 통과 상태다.

## 권장 수정 순서

1. Windows의 여러 layer/plugin DLL이 하나의 shared `nntrainer.dll`을
   사용하도록 연결 구조를 먼저 고친다.
2. 부모와 자식의 두 `Global()` 표기가 한 owner 함수로 모이게 한다.
3. 서로 다른 DLL 두 곳에서 받은 주소, worker 수, 초기화 횟수가 모두 하나인지
   검사하는 Windows test를 추가한다.
