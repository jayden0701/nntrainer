## 한눈에 보기

이 PR은 #4149에서 만든 GPU 부품을 CausalLM의 RMSNorm과
`per_layer_slice` layer에 연결한다. 기존 CPU layer는 그대로 두고
`engine=gpu`를 명시한 경우에만 새 구현을 선택하는 구조다.

현재 저장소의 Gemma4 graph에는 `engine=gpu`가 지정되어 있지 않아, 평소
설정에서는 새 layer가 아직 선택되지 않는다. 즉 지금 당장 기본 실행을 망가뜨리는
변경은 아니지만, GPU layer를 켜는 순간 드러나는 문제가 여러 개 있다.

비유하면 새 GPU 전용 차선을 만들어 표지판까지 달았지만, 아직 기본 내비게이션은
그 길을 안내하지 않는 상태다. 그렇다고 차선 자체의 끊긴 구간을 합쳐도 되는 것은
아니다.

## 주요 문제

### P1 — Android에서는 새 GPU 코드가 빌드 결과에서 빠짐

위치:

- `Applications/CausalLM/jni/Android.mk:87,94`
- `jni/meson.build:40-49`
- `jni/Android-prebuilt.mk.in:3-7`
- `Applications/CausalLM/layers/rms_norm_gpu.cpp:26-31,178-337`
- `Applications/CausalLM/layers/per_layer_slice_gpu.cpp:13-18,79-97`
- `nntrainer/tensor/cl_operations/meson.build:15-24`

Android.mk에는 새 GPU 소스 파일이 들어갔지만, prebuilt nntrainer가 CausalLM
소스를 컴파일할 때 `ENABLE_OPENCL`을 전달하지 않는다. 따라서 전처리기가 두
파일의 OpenCL 부분을 통째로 제외한다.

그 결과 FP16 RMSNorm은 GPU kernel을 부르지 못하고 지원하지 않는 조합이라는
예외로 끝난다. GPU 엔진은 설치했지만 앱을 포장할 때 “GPU 사용 가능” 스티커를
붙이지 않아, 포장 담당자가 GPU 부품을 상자에서 빼 버린 셈이다.

`ENABLE_OPENCL`만 전달해도 아직 끝나지 않는다. 두 새 파일이 include하는
`blas_kernels.h`는 Android prebuilt의 설치 header 목록에 없으므로 이번에는
컴파일이 `header not found`로 실패한다.

이 문제는 Android에서 GPU layer를 사용하면 항상 발생한다. OpenCL 매크로를
prebuilt 소비자에게 export하고, 필요한 API를 설치되는 public header로
노출하는 수정이 함께 필요하다.

### P1 — FP16 경로가 FP32로 저장된 gamma를 FP16 파일처럼 읽음

위치:

- `Applications/CausalLM/layers/rms_norm_gpu.cpp:51-57`
- 비교 대상: `Applications/CausalLM/layers/rms_norm.cpp:31-41`
- `nntrainer/layers/layer_node.cpp:691-696`
- `nntrainer/models/neuralnet.cpp:971-1001`

기존 CPU RMSNorm은 모델 파일의 gamma가 FP32로 저장된다는 이유로 명시적으로
FP32 weight를 요청한다. 새 GPU RMSNorm은 activation과 같은
`context.getWeightDataType()`을 요청한다.

따라서 FP16 activation을 쓰면, FP32 네 바이트 숫자가 들어 있는 파일을 FP16
두 바이트 숫자 줄로 잘못 읽는다. 넓은 칸에 인쇄된 숫자를 절반 너비의 자로
끊어 읽는 것과 같아서 값이 달라지고, 뒤 weight를 읽기 시작할 파일 위치까지
어긋날 수 있다.

이 문제는 현재 흔한 FP32 activation 설정에서는 발생하지 않지만, 이 PR이
추가하려는 **FP16 GPU RMSNorm을 켜면 확정적으로 발생**한다.

GitHub에 남아 있는 “gamma는 FP32로 요청해야 한다”는 리뷰는 올바르다. 다만
gamma만 FP32로 요청하면 현재 FP16 dispatch 조건과 맞지 않아 예외가 나므로,
FP32로 정확히 읽은 뒤 GPU용 FP16 복사본을 만들거나 kernel이 FP32 gamma를
받도록 함께 고쳐야 한다.

### P1 — `cl_mem` slice는 batch 2부터 계속 batch 0 자리에 접근함

위치:

- `Applications/CausalLM/layers/per_layer_slice_gpu.cpp:70-93`
- 부모 PR의 `nntrainer/tensor/cl_operations/blas_kernels.cpp:1174-1220`
- `nntrainer/tensor/tensor.cpp:1275-1285`

새 layer는 batch마다 큰 tensor의 일부를 가리키는 view를 만든다. 그러나
`getClMem()`은 전체 GPU buffer만 돌려주고, view가 몇 번째 원소에서 시작하는지는
전달하지 않는다. #4149 kernel에도 그 시작 위치를 받는 인자가 없다.

예를 들어 두 batch가 다음과 같고 가운데 두 값을 꺼낸다고 하자.

```text
batch 0: [10, 11, 12, 13] -> [12, 13]
batch 1: [20, 21, 22, 23] -> [22, 23]
```

실제로는 두 번째 반복도 GPU buffer의 맨 앞을 읽고 맨 앞에 쓴다. 큰 아파트
주소만 주고 동·호수를 빼먹어 모든 배달이 1호 집으로 가는 것과 같다.

기본적인 batch 1 실행에서는 숨는다. `batch > 1`이고 tensor가 `cl_mem`에
상주하는 경우에는 항상 잘못된다. input/output view의 element offset을 kernel에
전달해 index에 더하거나, offset이 0이 아닌 view에서는 이 경로를 쓰지 않아야
한다.

### P2 — 캐시 뒤에서 시작한 여러 토큰 prefill을 decode로 오해함

위치:

- `Applications/CausalLM/layers/rms_norm_gpu.cpp:124-125`
- `Applications/CausalLM/layers/per_layer_slice_gpu.cpp:45-46`
- CPU 비교: `rms_norm.cpp:62-64`, `per_layer_slice.cpp:43-45`
- 실제 호출 흐름: `Applications/CausalLM/src/causal_lm.cpp:544-575`

GPU layer는 `from == 0`일 때만 prefill이라고 보고 `skip_prefill`을 적용한다.
CPU layer는 `from == 0`이거나 한 번에 처리하는 token이 두 개 이상이면
prefill이라고 본다.

예를 들어 캐시에 이미 32개 token이 있고 새 prompt 10개를 처리하면
`from=32`, `to=42`다. 시작 페이지가 0이 아니어도 여러 페이지를 한꺼번에 읽는
prefill인데, GPU 구현은 한 token decode라고 착각해 원래 건너뛰어야 할 layer를
실행한다.

일반적인 첫 prefill(`from=0`)에서는 문제가 없고, cache를 불러온 뒤 여러 token을
한 번에 넣는 대화 재개·prefix cache 시나리오에서 발생한다. GitHub의
`skip_prefill` 리뷰는 현재 head에도 정확히 적용된다. CPU와 같은
`!from || (to - from) > 1` 판정을 써야 한다.

### P2 — FP16 epsilon을 모델 값보다 100배 크게 바꿈

위치:

- `Applications/CausalLM/layers/rms_norm_gpu.cpp:234-239`

Gemma4의 RMSNorm epsilon은 `1e-6`인데, 새 FP16 경로는 이를 최소 `1e-4`로
올린다. 주석은 `1e-6`이 FP16에서 0이 된다고 설명하지만, FP16은 subnormal로
약 `1.01e-6`을 표현할 수 있다. 일부 GPU가 subnormal을 0으로 처리할 수 있다는
문제와 숫자 자체를 표현할 수 없다는 말은 다르다.

보통 activation의 제곱 평균이 충분히 크면 차이는 작다. 반면 모든 값이
`0.001`인 작은 row에서는 gamma가 1일 때 대략 다음처럼 결과가 달라진다.

```text
epsilon 1e-6 -> 약 0.707
epsilon 1e-4 -> 약 0.0995
```

흔들림 방지용 받침을 100배 두껍게 만들어 작은 물체를 눌러 버리는 셈이다.
모델의 수식을 바꾸지 말고 kernel의 epsilon 인자를 FP32로 받는 편이 안전하다.

### P2 — coarse SVM의 CPU/GPU 사용권 전환이 빠짐

위치:

- `nntrainer/tensor/cl_operations/blas_kernels_templates.h:364-430`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1398-1419,1492-1524`
- 새 caller: `Applications/CausalLM/layers/rms_norm_gpu.cpp:254-255,397-401`

이 PR이 연결한 RMSNorm wrapper는 coarse-grain SVM pointer를 GPU kernel에
넘기기 전에 `unmap`하지 않고, 계산 뒤에는 output을 `CL_MAP_WRITE`로 map한다.
다음 실행 전에도 다시 unmap하지 않는다.

[Khronos의 공식 OpenCL 설명](https://registry.khronos.org/OpenCL/sdk/3.0/docs/man/html/clEnqueueSVMUnmap.html)에
따르면 coarse-grain SVM은 host에 map된 동안 kernel이 접근하면 동작이 정의되지
않는다. 같은 줄에 CPU용 “사용 중” 팻말과 GPU용 “사용 중” 팻말을 동시에 놓는
상태다. in-order queue라는 사실만으로 이 소유권 규칙이 없어지지는 않는다.

이 문제는 `NNTR_GPU_CLMEM_POOL=0`인 FP16 GPU 경로나
`NNTR_DEVRES=1`인 FP32 경로에서 나타난다. driver에 따라 우연히 맞아 보일 수
있지만 반복 실행의 정확성을 보장할 수 없다. 입력·gamma·출력의 map 상태를
명확히 추적하고 kernel 전후에 올바른 unmap/map을 해야 하며, CPU가 읽을
output은 read 권한으로 map해야 한다.

## 낮은 우선순위 문제

- `rms_norm_gpu.cpp`는 32비트 ARM NEON에서도 경로를 켜면서 AArch64 전용
  `vaddvq_f32`를 사용한다. Clang 14의 ARMv7 NEON target으로 최소 재현하면
  컴파일되지 않는다. 현재 공식 CausalLM Android가 arm64라 주 경로에는
  바로 드러나지 않지만 저장소의 ARMv7 호환 helper를 써야 한다.
- `NNTR_DEVRES=0`, `NNTR_NORM_NOMAP=0`,
  `NNTR_RMSQ_GPU_DISPATCH=0`도 환경변수가 존재한다는 이유만으로 기능을 켠다.
  저장소의 값 해석 helper를 사용해야 한다.
