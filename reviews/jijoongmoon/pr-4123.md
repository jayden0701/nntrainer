## 요약

이 PR은 `NNTR_CUDA_I8_JIT=1`일 때 QS4CX weight를 매 prefill마다
int8 scratch로 풀어 쓰는 경로를 추가한다. 모든 weight의 int8 복사본을
영구 cache하는 대신, 하나의 재사용 scratch만 유지해 VRAM 사용량을
줄이려는 기능이다. 직접 부모 #4122 대비 고유 변경은
`cuda_fc_qint4.cpp` 한 파일, 135줄 추가와 8줄 삭제다.

새 scalar/vector unpack kernel의 nibble 부호 변환, `[N, Kh]`에서
`[K, N]`으로 바꾸는 index, tile 경계와 tail 조건은 서로 일관된다.
환경 변수를 켜지 않으면 기존 persistent cache 경로를 그대로 사용한다.

다만 새 JIT scratch는 같은 cuBLAS IMMA에 전달되는 기존 weight buffer와
달리 tail padding 없이 정확한 `K * N` byte만 할당한다. 저장소의 기존
코드가 명시적으로 방어하는 wide tail read를 다시 노출하므로 수정이
필요하다.

## 발견 사항

### P2 — transient int8 weight scratch에 IMMA용 tail padding이 빠짐

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:642-646`
- `nntrainer/cuda/cuda_fc_qint4.cpp:773-787`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1143-1146`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1183-1188`
- `nntrainer/cuda/cuda_blas_manager.cpp:160-170`

기존 persistent int8 weight는 다음처럼 256 byte의 여유 공간을 둔다.

```cpp
cudaMalloc(&dw.w8, (size_t)N * K + FC_I8_TAIL_PAD)
```

반면 새 JIT 경로는 같은 cuBLAS operand를 정확한 크기로만 만든다.

```cpp
ensure_buf((void **)&jit_w8, &jit_cap, (size_t)K * N)
```

이후 두 buffer는 모두 `igemmRowMajor()`의 B operand로 전달된다. 기존
activation, persistent weight, GEMM output, K-chunk scratch가 모두
`FC_I8_TAIL_PAD`를 두는 이유도 코드에 적혀 있다. 일부 cuBLAS int8 IMMA
kernel이 마지막 logical element 근처에서 넓은 vector load를 하므로,
딱 맞는 allocation에서는 끝을 넘어 읽어 illegal memory access가 날 수
있기 때문이다.

따라서 `NNTR_CUDA_I8_JIT=1`로 처음 처리하는 weight가 현재 scratch의
최대 크기라면 뒤쪽 여유 공간이 없다. 마지막 B tile의 wide read가
allocation 경계를 넘으면 prefill이 실패하거나 sticky CUDA error가 남아
후속 layer까지 망가질 수 있다.

JIT scratch도 아래처럼 기존 weight buffer와 동일한 계약으로 할당해야
한다.

```cpp
ensure_buf((void **)&jit_w8, &jit_cap,
           (size_t)K * N + FC_I8_TAIL_PAD)
```

이 문제는 GitHub의 기존 자동 리뷰에서도 지적됐으며, 이번 리뷰 head에도
아직 남아 있음을 확인했다.

## 정상으로 확인한 부분

- scalar kernel의 low/high nibble sign 복원은 기존 `plain ^ 0x88`
  표현과 일치함
- scalar kernel의 32×64, vector kernel의 64×64 transpose index가
  `[K, N]` 출력 layout과 일치함
- vector 경로 조건 `K % 8 == 0 && N % 4 == 0`이 4-byte input/output
  access의 row alignment를 보장함
- scalar fallback이 odd `K`와 불완전한 마지막 tile을 범위 안에서 처리함
- JIT compile·allocation·dispatch가 동기적으로 실패하면 기존
  dp4a, naive 경로로 내려가는 구조임
- 환경 변수를 설정하지 않으면 이번 PR의 JIT 경로가 실행되지 않음

## 테스트 공백

고유 변경에는 자동 test가 없다. PR 본문의 검증은 RTX 5060의 gauss4
shape에서 vector 경로를 수동 실행한 내용이라, scalar fallback과
allocation 경계 검사는 다루지 않는다.

최소한 다음 검증이 필요하다.

- persistent unpack과 JIT unpack 결과의 byte 단위 비교
- vector 경로와 scalar 경로, odd `K/N`, 마지막 불완전 tile
- 큰 weight 뒤 작은 weight 및 작은 weight 뒤 큰 weight의 scratch 재할당
- `compute-sanitizer`로 cuBLAS B operand의 allocation tail 검사

현재 환경에는 CUDA toolkit과 GPU가 없어 runtime 검증은 수행하지 못했다.
