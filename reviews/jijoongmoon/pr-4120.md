## 요약

이 PR은 QS4CX FC에 activation을 int8로 동적 양자화하는 dp4a 경로와
prefill용 cuBLAS int8-IMMA 경로를 추가한다. 직접 부모 #4119 대비 고유
변경은 6개 파일, 1,185줄 추가와 4줄 삭제다.

cuBLAS의 row-major 변환, K chunk offset, zero-point 보정과 scale 수식은
서로 일관된다. 그러나 decode 전용 GEMV는 일반 QS4CX shape에서 K의
꼬리 항을 누락한다. 새 weight cache와 선택적 activation dedup cache도
주소를 객체의 identity로 사용해 모델 reload·반복 inference에서 이전
값을 재사용한다. 또한 비동기 실행 오류를 감지해 dp4a로 내려간다는
복구 경로는 실제 CUDA 오류 시점과 맞지 않는다.

## 발견 사항

### P1 — `M=1`, `K % 4 != 0`이면 GEMV가 마지막 항을 계산하지 않음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:375-417`
- `nntrainer/cuda/cuda_fc_qint4.cpp:698-707`
- `nntrainer/cuda/cuda_compute_ops.cpp:46-51`

`dp4a_gemv()`는 각 lane에서 4개 원소 묶음만 처리한다.

```cpp
for (int k = lane * 4; k + 4 <= K; k += 32 * 4)
```

일반 GEMM kernel과 달리 이 loop 뒤에는 남은 1~3개 원소를 처리하는
tail loop가 없다. 그런데 GEMV 선택 조건은 `M == 1`뿐이고
`CudaComputeOps::fc()`도 `K > 0`과 weight height만 확인한다. QS4CX
tensor 자체에도 K가 4의 배수여야 한다는 제약은 없다.

예를 들어 `M=N=1`, `K=5`이면 다섯 번째 activation·weight 곱은 빠진다.
반면 zero-point 보정용 `wrowsum`은 K 전체를 포함하므로 조용히 잘못된
출력을 만든다. tail을 구현하거나 `K % 4 != 0`인 경우 검증된 일반
kernel로 보내야 한다.

### P1 — 파생 weight cache가 주소 재사용을 새 weight로 구분하지 못함

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:629-694`
- `nntrainer/cuda/cuda_fc_qint4.cpp:761-817`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1039-1069`

decode용 `g_dp4a_plain_cache`와 prefill용 `g_i8_weight_cache`는 모두
`plain_w` raw pointer 하나만 key로 사용한다. `N`, `K`, tensor 소유자,
generation을 저장하거나 검증하지 않고 entry를 지우는 경로도 없다.

같은 tensor storage에 checkpoint를 다시 읽으면 원본 nibble이 바뀌어도
예전 packed weight와 rowsum으로 계산한다. 모델 unload 뒤 allocator가
같은 주소를 재사용해도 동일하며, 새 shape가 더 크면 이전의 작은
`plain`, `w8`, `rowsum` allocation을 새 `N/K`로 읽어 device OOB가
발생한다.

메모리 영향도 크다. 보통 prefill 뒤 decode를 실행하면 weight마다 원본
QS4CX 외에 int8 복사본과 packed-int4 복사본이 모두 영구 상주한다.
모델을 내려도 해제되지 않아 반복 load 시 VRAM이 계속 누적된다. cache를
weight 객체의 수명과 generation에 묶고 unload/reload 때 명시적으로
무효화·해제해야 한다.

### P1 — `NNTR_QUANT_DEDUP=1`이 이전 요청의 activation을 재사용

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:768-771`
- `nntrainer/cuda/cuda_fc_qint4.cpp:925-968`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1002-1033`

선택 기능인 quant dedup은 마지막 activation을 `(Xh 주소, K)`만으로
식별한다. 같은 tensor buffer 주소는 다음 forward나 다음 prompt에서도
재사용되지만 내용은 바뀔 수 있고, key에는 `M`이나 내용 generation도
없다.

더구나 dp4a 경로가 같은 전역 `q8/ascale/azp` scratch를 덮어도 marker를
갱신하거나 무효화하지 않는다. 따라서 다음 순서로 쉽게 오염된다.

1. prefill이 주소 P의 activation을 양자화하고 marker에 P를 저장한다.
2. decode의 dp4a가 같은 scratch를 다른 activation으로 덮는다.
3. 다음 prefill에서 memory planner가 P를 다시 사용하면 양자화를
   건너뛰고 decode의 1-row 값과 나머지 stale 값을 IMMA에 넣는다.

`dp4a_stage_scratch()`가 더 큰 M 때문에 buffer를 새로 할당한 뒤에도
marker가 유지되어 미초기화 scratch를 재사용할 수 있다. 모든 scratch
writer와 재할당에서 marker를 무효화하고, request/forward 단위 generation을
key에 포함해야 한다.

### P1 — 비동기 IMMA 실행 오류를 기다리지 않아 dp4a 폴백이 동작하지 않음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1059-1096`
- `nntrainer/cuda/cuda_stream_manager.cpp:118-153`

IMMA GEMM과 dequant epilogue를 enqueue한 뒤 코드는 `maybeFinish()`와
`cudaGetLastError()`를 호출해 실행 오류를 잡고 dp4a로 폴백하려 한다.
그러나 discrete GPU에서 `NNTR_CUDA_ASYNC=1`이면 `maybeFinish()`는
stream을 기다리지 않는다. `cudaGetLastError()`는 작업이 아직 실행
중인 시점에 성공을 반환할 수 있어 함수도 `true`를 반환하고 폴백을
건너뛴다. 오류는 다음 layer나 sync에서 나타나며 output은 미완성 또는
오염된 상태다.

또한 illegal-address 같은 실행 오류는 CUDA context를 sticky error
상태로 만들 수 있어, 오류를 읽어 지운 뒤 같은 context에 dp4a를
enqueue한다고 깨끗하게 복구되는 것도 아니다. 실행 후 오류에 의존한
폴백 대신 launch 전에 지원 shape/capability를 검증하고, 실행 오류는
해당 inference 실패로 전달해야 한다.

## 남은 위험

이번 커밋에는 CUDA kernel 단위 test나 수치 비교 test가 없다. 특히 새
fast path는 FP16/FP32 activation을 int8로 다시 양자화하므로, dp4a와
cuBLAS끼리는 같은 int32 결과를 낼 수 있어도 기존 naive FP 경로와
bit-identical하지는 않다. fallback 여부에 따라 수치가 바뀌는 정도와
모델 품질 허용치를 검증해야 한다.

또한 prefill에서 i8 cache만 준비된 뒤 첫 decode를 CUDA graph로 capture하면
dp4a cache의 첫 `cudaMalloc`이 capture 안에서 실행될 수 있다. 현재
코드에서 graph replay가 본격 연결되기 전에 cache warm-up 또는
capture-safe 수명 정책을 마련해야 한다.
