## 한눈에 보기

이 PR은 여러 GPU subgroup이 attention 점수의 부분합을 합치는 방법을 바꾼다.

기존 방식에서는 계산원 네 명이 모두 같은 네 줄의 영수증을 각자 다시 합쳤다.
새 방식은 계산원마다 담당 줄만 한 번 합쳐 공용 게시판에 적고, 모두 게시판의
완성된 값을 읽는다. 중복 작업을 줄이는 최적화다.

직접 변경은 2개 파일, 62줄 추가와 3줄 삭제다. 계산 순서, 담당 행, barrier와
꼬리 처리를 따라간 결과 새 XRED 부분에는 빠진 값·두 번 더한 값·동기화 누락을
찾지 못했다.

## 새 XRED 계산이 맞는 이유

위치:

- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1085-1131`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2714-2718,2747-2783`

### 1. 모든 행에 담당자가 정확히 한 명 있음

새 코드는 subgroup 번호 `sg`부터 시작해 `NSG`칸씩 건너뛰며 담당 행을 고른다.

```text
r = sg; r < TM; r += NSG
```

허용되는 `NSG={2,4}`, `TM={4,8,16}` 조합을 모두 열거해 확인했다. 모든 행은
정확히 한 subgroup에 한 번씩 배정되고, 빠지거나 겹치는 행이 없다.

### 2. 덧셈 순서가 기존과 같음

기존 경로도 새 경로도 각 행에서 subgroup 부분합을 다음 순서로 더한다.

```text
g=0, g=1, ... g=NSG-1
```

새 경로는 이 결과를 `ssum`에 한 번 적고 다른 subgroup들이 읽을 뿐이다.
FP32 덧셈 순서를 바꾸지 않았기 때문에 알고리즘상 같은 값을 만든다.

### 3. 공용 메모리를 읽기 전후의 신호가 있음

- 모든 subgroup이 `psum`을 쓴 뒤 work-group barrier
- 담당 subgroup이 `ssum`을 쓴 뒤 work-group barrier
- 다음 key batch가 공용 공간을 덮어쓰기 전 work-group barrier

barrier를 만나는 조건도 work-group 전체에서 동일하다. 일부 작업자만 신호를
건너뛰어 서로 기다리는 deadlock이나, 쓰기가 끝나기 전에 읽는 race가 없다.

마지막 key tile의 남는 lane과 마지막 query tile의 남는 row도 기존과 같은
`lane < kt`, `m0 + r < M` 조건으로 걸러진다.

## 실제 영향 범위

기본 설정에서 XRED가 켜지는 범위는 생각보다 좁다.

- Intel DPAS 기능이 있음
- causal full-attention임
- sliding window가 아님
- `head_dim=512`
- XMX 경로가 켜짐

`head_dim <= 256`은 기본 `NSG=1`이라 XRED 코드가 컴파일에서 빠진다. non-causal,
sliding-window, non-DPAS 장치와 Adreno도 영향을 받지 않는다.

`NNTR_FLASH_XMX_XRED=0`은 의도대로 기존 all-to-all 경로를 선택한다. XRED 값은
kernel compile option과 cache key에도 포함되어 있어, 예전에 컴파일한 XRED-off
kernel을 XRED-on으로 착각해 재사용하는 문제도 없다. host가 정한
`LWS=16*NSG`와 kernel의 필수 work-group 크기도 일치한다.

## 낮은 우선순위 보완점

### P3 — SLM 사용량 계산에 새 `ssum` 공간이 빠짐

위치:

- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2784-2793`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1067-1072`

host의 공용 메모리 사용량 계산은 기존 `vtile + psum`만 세고, 새로 추가한
`ssum`은 세지 않는다.

다만 현재 기본 `d=512, NSG=4, TM=16, XB=1`은 실제로 약 21KB이고,
실험 설정의 최대 `XB=4`도 약 36KB라 코드가 가정한 Xe의 64KB 안에 들어간다.
따라서 현행 기본 Xe2/Xe3 경로의 재현 가능한 오류로 볼 수는 없다.

향후 설정 범위를 늘리거나 32KB만 제공하는 구현을 지원할 때 잘못된 판단을 하지
않도록 `ssum`도 공식에 포함하고, 고정 64KB 대신 장치의 실제
`CL_DEVICE_LOCAL_MEM_SIZE`를 확인하는 것이 좋다.

### P3 — “모든 환경에서 bit-identical”이라고 보장하기에는 검증이 약함

소스 수준에서는 기존과 같은 순서로 더해 같은 결과가 예상되고, PR의 Xe3 측정도
이를 뒷받침한다. 그러나 기본 OpenCL 옵션에는 `-cl-fast-relaxed-math`가 있어
다른 compiler가 부동소수점 식을 재배치하지 않는다는 언어 차원의 보장은 없다.

또 `NNTR_FLASH_XMX_CHECK`는 **새 XRED-on과 기존 XRED-off를 한 실행에서 직접
비교하는 도구가 아니라**, XMX 결과와 block-Q 기준 결과의 오차가 0.02보다 큰지
확인하는 도구다. `over_tol=0`만으로 byte 단위 동일성을 자동 증명하지는 않는다.

현재 계산 오류라는 뜻은 아니다. 문서 표현을 “Xe3에서 동일함을 관찰했다”로
제한하고, XRED on/off 결과를 byte 단위로 비교하는 회귀 test를 추가하면 주장이
더 정확해진다.

## 누적 stack에서 남은 문제

이 PR의 직접 변경에는 blocker가 없지만, 부모 #4148에서 확인한 다음 문제는
그대로다.

- DPAS 확장 문자열만 보고 SG16 전용 kernel을 기본 선택함
- deterministic 및 FP16-score 설정이 XMX와 일관되지 않음
- coarse-grain SVM을 안전하게 넘겨받지 않고 CHECK에서 host가 읽음

자세한 내용은 [PR #4148 리뷰](./pr-4148.md)에 정리했다.

GitHub의 현재 unresolved thread 두 건도 #4151의 두 변경 파일이 아니라 아래
stack에서 상속된 문제다.

- FC의 fused activation을 일반 forwarding에만 적용해 incremental/backward와
  동작이 달라짐
- GPU FC output의 SVM map이 끝나기 전에 host activation이 접근할 수 있음

따라서 이번 XRED 최적화 자체에는 승인을 줄 수 있지만, 전체 stacked PR은 부모
blocker를 해결한 뒤 병합해야 한다.

형식을 따르지 않는다. AI가 작성했다고 표시했지만 commit에는 저장소 규칙의
`Co-authored-by:` trailer도 없다.
