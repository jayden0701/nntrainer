## 요약

이 PR은 QS4CX int4 weight를 CUDA에서 직접 dequantize하며 곱하는 FC
kernel과 `CudaComputeOps`를 추가한다. 직접 부모
`fd1c437e4b373fe0dfb119ca7f070a9f981509ee` 대비 고유 변경은 6개 파일,
423줄 추가다.

QS4CX nibble 해석과 기본 GEMM 수식은 현재 저장 형식과 맞는다. 다만 CUDA
경로가 실패했을 때 device-only pointer를 CPU 연산으로 넘기고, 성공
경로에서도 output의 CUDA 접근 가능 여부와 host 후처리 전 동기화를
보장하지 않는다. scale cache도 weight의 실제 수명보다 오래 살아 잘못된
scale을 재사용하거나 범위를 벗어나 읽을 수 있다.

## 발견 사항

### P1 — CUDA 경로 실패 시 device-only tensor를 CPU가 직접 역참조

위치:

- `nntrainer/cuda/cuda_compute_ops.cpp:50-84`
- `nntrainer/tensor/manager.h:141-146`
- `nntrainer/cuda/cuda_mem_allocator.cpp:93-95`
- `nntrainer/cuda/cuda_mem_allocator.cpp:126-127`

`CudaComputeOps::fc()`는 CUDA 경로를 선택하지 못하거나 scale 생성,
NVRTC compile, kernel dispatch 중 하나라도 실패하면
`input.dot(weight, output, ...)`을 호출한다. 그러나
`NNTR_CUDA_DEV_ACT=1`에서는 activation pool이 `cudaMalloc` 기반의
device-only 메모리를 사용할 수 있다. 이 pointer는 host
`Tensor::dot()`이 읽거나 쓸 수 없다.

특히 graph capture 중 처음 만난 weight는 scale buffer를 새로 만들지 않고
`false`를 반환하므로 이 폴백에 확정적으로 진입한다. 또한 FP16 activation과
QS4CX weight 조합에는 유효한 host dot 구현도 없어 예외로 끝난다.

device-only tensor에서 CUDA 실행이 불가능하면 오류를 반환해야 한다. CPU
폴백을 유지하려면 명시적인 D2H/H2D staging과 동기화가 필요하다.

### P1 — output의 CUDA 접근 가능 여부를 확인하지 않고 kernel에 전달

위치:

- `nntrainer/cuda/cuda_compute_ops.cpp:55-76`
- `nntrainer/cuda/cuda_mem_allocator.cpp:163-175`

FP16과 FP32 경로 모두 weight `W`와 input `X`만 `dev_accessible()`로
검사한다. output `Y`는 검사하지 않은 채 CUDA kernel argument로 넘긴다.

예를 들어 input과 weight는 device-accessible이지만 output allocation만
CUDA allocation 실패 후 일반 host allocation으로 내려가면, kernel이
host pointer에 쓰면서 illegal memory access를 일으킨다. launch 오류가
비동기로 보고되면 함수는 성공으로 반환할 수도 있다.

CUDA path 선택 전에 `Y`를 포함한 모든 operand의 residency를 검증해야
한다.

### P1 — async FC 직후 CPU bias·activation 후처리와 kernel이 경쟁

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:190-212`
- `nntrainer/cuda/cuda_fc_qint4.cpp:216-252`
- `nntrainer/layers/fc_layer_cl.cpp:129-143`
- `nntrainer/layers/fc_layer_cl.cpp:182-191`

새 FC wrapper는 마지막에 `maybeFinish()`만 호출한다.
`NNTR_CUDA_ASYNC=1`에서는 이 함수가 stream을 기다리지 않고 성공을
반환한다. 바로 다음 `FullyConnectedLayerCl` 코드는 같은 output에 host
`add_i()`로 bias를 더하고, 설정된 경우 host activation도 적용한다.

따라서 CPU가 아직 계산 중인 GEMM output을 동시에 읽고 써 bias나
activation이 누락·오염될 수 있다. output이 device-only이면 host
후처리 자체가 접근 위반이다. CUDA epilogue를 제공하거나, 실제 host
소비 경계에서 stream을 명시적으로 기다려야 한다.

### P1 — scale cache가 해제된 weight 주소를 새 weight로 오인

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:118-150`

process-wide scale cache는 `fp32_scales`의 raw pointer 주소만 key로
사용한다. `N`, tensor 소유자, generation 정보가 없고 entry와 CUDA
buffer를 지우는 경로도 없다.

모델을 해제한 뒤 allocator가 같은 주소를 새 weight scale에 재사용하면
예전 FP16 scale buffer를 돌려준다. 새 `N`이 같거나 작으면 조용히 잘못된
결과를 만들고, 더 크면 kernel의 `sc[n]`이 이전 allocation 범위를
벗어난다. 같은 tensor 주소에 checkpoint를 다시 읽는 경우에도 scale
내용 변경을 알아채지 못한다. 서로 다른 주소를 쓰는 모델을 반복해서
load/unload하면 CUDA allocation도 계속 누수된다.

cache entry를 weight 수명에 묶고 shape/version까지 검증하거나, 호출자가
소유하는 derived-weight buffer로 관리해야 한다.
