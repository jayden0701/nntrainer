## 요약

이 PR은 FP16 activation과 QS4CX int4 weight를 직접 곱하는 ARM i8mm 커널, FP16
LHS packer, 호출용 facade와 `HalfTensor::dot()` dispatch를 추가한다. 직접 부모와
비교하면 16개 파일에 1,485줄이 추가됐다.

가장 큰 문제는 실제 모델이 만드는 packed RHS와 새 커널이 기대하는 형식이 다르다는
점이다. `QS4CX_Tensor::pack()`은 8개 출력 채널을 한 묶음으로 만드는 `nr=8`
레이아웃을 사용한다. 반면 새 FP16 facade는 전달된 variant를 무시하고 `nr=4`
커널을 고정 호출한다. 버퍼 전체 크기가 같더라도 weight payload와
sum/scale/bias의 경계가 달라, 첫 타일부터 weight 바이트를 양자화 파라미터로
해석하게 된다.

추가된 세 테스트는 빌드 시스템에 등록되지 않았고 현재 PR에 없는 별도
`Int4Utils` API를 참조한다. device test는 실제 `QS4CX_Tensor::pack()`도 우회하며
오차가 커도 항상 성공을 반환한다. 따라서 CI가 모두 통과한 것은 새 생산 경로의
정확성을 검증했다는 뜻이 아니다.

## 발견 사항

### P1 — `nr=8`로 패킹한 RHS를 `nr=4` 커널이 읽어 모든 QS4CX×FP16 결과가 오염될 수 있음

위치:

- `nntrainer/tensor/qs4cx_tensor.cpp:69-87`
- `nntrainer/tensor/half_tensor.cpp:723-753`
- `nntrainer/tensor/cpu_backend/arm/arm_compute_backend_fp16.cpp:443-459`
- `nntrainer/tensor/cpu_backend/arm/kai_interface/kleidiai_interface_qai8dxp_qsi4cxp.cpp:413-475`

생산 경로의 `QS4CX_Tensor::pack()`은 `opt_kernel_idx = 8`로
`get_rhs_packed_size...()`와 `rhs_pack...()`을 호출한다. 현재 variant 표에서
index 8은 `qsi4cxp8x8`, 즉 `nr=8` 레이아웃이다. 기존 FP32 경로가 M=1일 때
선택하는 index 2도 `nr=8`이어서 이 packed buffer를 재사용할 수 있었다.

새 FP16 경로는 `input.getPackedData()`로 같은 버퍼를 받아 facade에
`idx_variant=2`를 전달한다. 그러나 facade는 그 값을 `(void)idx_variant`로 버리고
`qsi4cxp4x8_4x4x32`, 즉 `nr=4` 커널을 무조건 호출한다. 주석의
“index 2가 4x4 계약을 나타낸다”는 설명도 variant 표와 맞지 않는다. 현재 표에서
4x4 i8mm variant는 index 5이고 index 2는 `nr=8` dotprod variant다.

예를 들어 K=32일 때 두 형식은 다음처럼 배치된다.

| 형식 | 한 super-row의 weight payload | sum/scale/bias trailer | stride |
|---|---:|---:|---:|
| 실제 `nr=8` pack | 128 B | 96 B | 224 B |
| 새 `nr=4` 커널 기대 | 64 B | 48 B | 112 B |

따라서 커널은 offset 64부터 metadata가 있다고 가정하지만, 실제 버퍼의 그 위치에는
아직 나머지 네 채널의 weight가 있다. 다음 N worker가 사용하는 offset 112도
`nr=8` super-row의 중간이다. 단순히 전체 버퍼 범위를 벗어나는 문제가 아니라,
payload와 양자화 파라미터를 체계적으로 잘못 읽어 출력 자체가 깨지는 문제다.

수정하려면 실제 `QS4CX_Tensor::pack()`과 FP16 커널이 동일한
`nr/kr/sr` 계약을 사용해야 한다. 선택지는 `nr=8` FP16 커널을 사용하거나,
FP16용 `nr=4` packed buffer를 별도로 만들고 타입/metadata로 레이아웃을
구분하는 것이다. facade는 variant를 무시하지 말고 지원하는 레이아웃인지
검증해야 한다. 실제 `Tensor::pack() → HalfTensor::dot()` 연결을 거치는 테스트도
필수다.

### P2 — FP16 커널의 LHS offset helper가 실제 pack stride보다 타일마다 16바이트 크게 계산함

위치:

- `nntrainer/tensor/cpu_backend/arm/kai_interface/kai/matmul_clamp_f16_qai8dxp_qsi4cxp/kai_matmul_clamp_f16_qai8dxp4x8_qsi4cxp4x8_4x4x32_neon_i8mm.c:60-73`
- `nntrainer/tensor/cpu_backend/arm/kai_interface/kai/matmul_clamp_f16_qai8dxp_qsi4cxp/kai_matmul_clamp_f16_qai8dxp4x8_qsi4cxp4x8_4x4x32_neon_i8mm.c:120-125`
- `nntrainer/tensor/cpu_backend/arm/kai_interface/kai/pack/kai_lhs_quant_pack_qai8dxp_f16.c:59-67`
- `nntrainer/tensor/cpu_backend/arm/kai_interface/kai/pack/kai_lhs_quant_pack_qai8dxp_f16.c:84-92`

새 microkernel의 `kai_lhs_packed_stride()`는 각 row에 int32 offset, float
multiplier뿐 아니라 존재하지 않는 float bias까지 있다고 계산한다.

```text
helper: mr × (Kpad + offset 4 B + multiplier 4 B + bias 4 B)
packer: mr × (Kpad + offset 4 B + multiplier 4 B)
```

실제 FP16 packer와 assembly의 다음 4-row block 이동량은 아래 식을 사용한다.
예를 들어 K=32이면 두 번째 block의 실제 시작은 160 B인데 getter는 176 B를
반환한다.

현재 wrapper는 이 helper에 `m_idx=0`만 넘겨 차이가 드러나지 않는다. 하지만
공개된 offset API를 이용해 M 방향 chunking이나 병렬화를 추가하면 두 번째
block부터 잘못된 LHS를 읽고 마지막에는 범위 밖을 읽을 수 있다. upstream FP32
helper와 동일하게 LHS에는 bias를 포함하지 않도록 고쳐야 하며, `m_idx=4, 8`의
offset을 실제 pack 결과와 비교하는 테스트가 필요하다.

### P2 — 추가된 테스트 세 개가 현재 tree에서 빌드·실행되지 않고 실패도 판정하지 않음

위치:

- `test/q4_kai_bytecompat.cpp`
- `test/q4_kai_matmul_device.cpp`
- `test/q4_roundtrip_kai.cpp`
- 관련 Meson/CMake 테스트 목록

세 파일은 standalone `main()` 프로그램이지만 Meson, CMake 또는 CI 스크립트
어디에도 등록되지 않았다. 또한 현재 head의 `int4_utils.h/.cpp`에는 테스트가
호출하는 다음 API와 상수가 없다.

- `Int4Utils::quantizeAndPackKai`
- `Int4Utils::assembleKaiRhsPacked`
- `Int4Utils::KAI_NR`, `KAI_KR`, `KAI_SR`
- `Int4Utils::kaiNibblePayloadBytes`

즉 이 PR만 checkout해서는 테스트를 그대로 컴파일할 수 없다. 특히
`q4_kai_matmul_device.cpp`의 `report()`는 MSE, relative L2와 max error를
출력만 하고 threshold나 assertion을 검사하지 않는다. `main()`도 각 case의
결과와 무관하게 항상 0을 반환한다.

더 중요한 점은 device test가 별도 `Int4Utils`로 `nr=4` RHS를 직접 조립하여
microkernel을 호출한다는 것이다. 생산 경로인 `QS4CX_Tensor::pack()`의
`nr=8` 버퍼를 통과하지 않으므로 앞의 P1 문제를 구조적으로 발견할 수 없다.

현재 PR 안에서 빌드 가능한 테스트로 만들고 정식 test target에 등록해야 한다.
최소한 아래를 자동 실패 조건과 함께 확인해야 한다.

- 실제 `QS4CX_Tensor::pack() → HalfTensor::dot()` end-to-end
- M/N이 1, 2, 3 및 타일 경계를 넘는 경우
- K가 32의 배수가 아닌 padding tail
- 오차 threshold 초과 시 non-zero exit
- packed variant/layout 불일치 시 명시적 거부

## 현재 head에서 확인한 보완 사항

- 이전 리뷰의 x86/Windows unresolved external 문제는 QS4CX case를 ARM
  전처리 가드 안으로 옮겨 현재 head에서 해소됐다.
- M/N partial store와 K padding assembly에서는 별도의 확정 오류를 찾지 못했다.
- 직접 부모 대비 `git diff --check`는 통과했다.
- GitHub의 현재 자동 체크는 통과했지만, 위 테스트 파일들은 그 체크에 포함되지
  않는다.

## 권장 수정 순서

1. production RHS pack과 FP16 커널의 `nr/kr/sr` 계약을 하나로 통일한다.
2. facade가 variant를 무시하지 않도록 하고 잘못된 packed layout을 거부한다.
3. LHS offset helper에서 존재하지 않는 bias stride를 제거한다.
4. 실제 Tensor 연결 경로를 검증하는 자동 테스트를 현재 PR에 포함하고 CI에
   등록한다.
5. 이미 제안된 KleidiAI FP16 커널 통합 PR #4133과 중복 구현 여부를 정리한다.
