## 한눈에 보기

기존 CUDA decode FC는 다음 두 작업을 별도 kernel로 실행한다.

1. FP16 activation 한 줄을 INT8로 양자화
2. 양자화된 값과 INT4 weight를 곱함

이 PR은 두 작업을 한 kernel 안에 합친다. 다만 각 output block이 양자화를
반복하므로 RTX 5060에서는 오히려 약 31% 느렸고, 그래서
`NNTR_CUDA_FC_FUSED_DECQ=1`을 명시할 때만 켜진다. 기본 실행은 변하지 않는다.

보통 transformer처럼 `K`가 32의 배수이면 min/max, 양자화, DP4A 누적과
마지막 output block 처리는 기존 경로와 일치한다. 문제는 QS4CX가 허용하는
일반적인 API 범위가 그보다 넓다는 점이다.

## 직접 변경분의 문제

### P2 — `K % 4 != 0`이면 마지막 1~3개 곱을 빼먹음

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:458-486`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1052-1060`
- weight sum: `nntrainer/cuda/cuda_fc_qint4.cpp:230-246`

발생 조건은 다음과 같다.

- FP16 QS4CX FC
- decode 한 줄인 `M == 1`
- `NNTR_CUDA_FC_FUSED_DECQ=1`
- `K % 4 != 0`

새 kernel은 activation `K`개를 모두 INT8로 바꾼다. weight의 row sum도
마지막 weight까지 전부 포함한다. 그러나 실제 곱셈은 다음 4개 묶음 loop만
있고, 끝에 남는 1~3개를 처리하는 loop가 없다.

```text
kk = lane * 4
kk + 4 <= K인 동안만 계산
```

예를 들어 `K=5`이면 앞의 네 물건은 계산대에서 스캔하지만 마지막 한 물건은
스캔하지 않는다. 그런데 재고표인 `wrowsum`에는 다섯 물건이 모두 적혀 있어
zero-point 보정까지 서로 맞지 않게 된다. 함수는 실패가 아니라 성공을
반환하므로 결과가 조용히 틀린다.

기존 #4120의 split `dp4a_gemv`에도 같은 버그가 있다. 따라서 PR의
“기존 경로와 bit-identical”이라는 말은 이 경우에도 역설적으로 맞을 수 있다.
**두 경로가 똑같이 틀린 것**은 correctness 증명이 아니다.

QS4CX tensor는 `(K+1)/2` 저장을 지원하고 생성자도 K의 배수를 제한하지 않는다.
다만 실제 LLM weight는 K가 32의 배수인 경우가 흔해 이 문제가 보통 모델에서
자주 보이지는 않는다.

scalar tail을 두 GEMV에 추가하는 것이 가장 좋다. 최소 수정으로는 fused와
기존 GEMV를 `K % 4 == 0`에서만 사용하고 나머지는 tail을 처리하는 일반
kernel로 보내야 한다.

### P2 — 큰 K의 shared memory 한도를 확인하지 않고 안전한 split 경로도 건너뜀

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:433-435`
- `nntrainer/cuda/cuda_fc_qint4.cpp:804-815`
- `nntrainer/cuda/cuda_fc_qint4.cpp:1056-1062`

새 kernel은 block마다 다음 shared memory를 요구한다.

```text
동적 공간: K바이트의 q8
고정 공간: min/max용 1,024바이트
```

host는 장치와 kernel의 block당 shared memory 한도를 확인하지 않고 `K`바이트를
바로 launch 인자로 넘긴다. [NVIDIA CUDA 가이드](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)는
block당 48KB를 넘는 shared memory가 장치별 기능이며 명시적인 최대 동적
shared-memory 설정이 필요하다고 설명한다.

보통 LLM의 K가 수천~수만이면 안전하다. 하지만 API가 허용하는 더 넓은
`K=65536` 같은 FC에서는 64KB 이상의 공간이 필요해 장치에 따라 launch가
거절된다.

거절 자체는 감지하므로 잘못된 값을 성공으로 돌려주지는 않는다. 문제는 이때
정상 동작할 수 있는 기존 `양자화 kernel + dp4a GEMV`로 내려가지 않고 함수
전체가 `false`를 반환한다는 점이다. 상위 코드는 훨씬 느린 naive FP 경로로
바로 넘어간다. 고속 계산대의 새 장비가 크기 제한에 걸렸을 때 옆의 기존
고속 계산대를 쓰지 않고 건물 밖 수기 계산대로 보내는 셈이다.

launch 전에 실제 device/function 한도를 확인하고 필요하면 opt-in attribute를
설정해야 한다. 지원할 수 없는 K라면 새 fused branch만 건너뛰고 바로 아래의
기존 split-dp4a 코드를 실행해야 한다.

### P3 — `false`와 `off`도 기능을 켬

위치:

- `nntrainer/cuda/cuda_fc_qint4.cpp:1052-1055`

현재 설정은 값 전체가 아니라 첫 글자가 `0`인지 여부만 본다.

```text
unset, "", "0" -> OFF
"1"            -> ON
"false", "off" -> ON
```

기본값과 문서에 적힌 `=0`은 올바르게 꺼진다. 그러나 운영 script가 일반적인
boolean 값 `false`를 쓰면, 이 PR에서 31% 느렸다고 밝힌 경로가 뜻밖에 켜진다.
인접 CUDA 설정처럼 정확히 `1`만 허용하거나 저장소의 공통 환경변수 helper를
쓰는 편이 좋다.

## 맞게 구현된 부분

`K % 4 == 0`이고 shared memory 안에 들어가는 범위에서는 다음을 확인했다.

- 기존 256-thread와 새 128-thread min/max reduction은 같은 FP16 값들의
  최솟값·최댓값을 고른다.
- `asym_qparams`, `rintf`, clamp가 같아 INT8 값과 zero-point가 같다.
- 각 warp lane은 겹치지 않게 K의 모든 4바이트 묶음을 한 번씩 처리한다.
- `n >= N`인 warp는 모든 block barrier가 끝난 뒤 반환하므로 deadlock이 없다.
- 마지막 block에서 N이 4의 배수가 아니어도 남는 warp만 빠지고 유효 output은
  각각 한 번 작성된다.
- 기본값은 실제로 OFF이며 FP32, prefill, non-QS4CX 경로에는 영향이 없다.
