## Review summary

이 PR은 #4112 위에 static `ResidencyClass`, cl_mem activation pool,
producer/consumer classification과 v8c direct input/output 경로를 추가한다.
#4112 대비 고유 delta는 29개 파일, 2,647줄 추가/476줄 삭제다.

현재 planner는 layer가 실제로 cl_mem plane을 읽고 쓰는지는 확인하지 않고
`GPU producer + GPU consumers + FP16`만으로 `GPU_CLMEM`을 선택한다. 따라서
아직 host/SVM 구현인 GPU/engine-neutral layer가 device plane의 producer 또는
consumer로 분류된다. 외부 graph output과 host FC epilogue에도 lower/raise가
없고, 공개한 boundary policy는 application 및 copy 경로에 연결되지 않았다.

## Findings

### P1 — cl_mem을 지원하지 않는 layer도 `GPU_CLMEM` producer/consumer로 분류됨

위치:

- `nntrainer/tensor/residency_planner.h:74`
- `nntrainer/layers/layer_node.cpp:723`
- `nntrainer/layers/layer_node.cpp:824`
- `Applications/CausalLM/layers/mha_core.cpp:1467`
- `Applications/CausalLM/layers/mha_core.cpp:1481`
- `nntrainer/layers/cl_layers/concat_cl.cpp:178`
- `nntrainer/layers/cl_layers/concat_cl.cpp:337`

`ResidencyPlanner::classify()`에는 producer와 consumer가 cl_mem plane을
실제로 지원하는지 나타내는 capability가 없다. 특히 `LayerNode`는
`mha_core`의 실제 실행 경로와 무관하게 output spec의 engine을 GPU로 강제한다.
그러나 `MHACoreLayer`는 FP16 결과를 `output.getData<_FP16>()`에 쓰며,
해당 layer에는 `getClMem()`을 사용하는 경로가 없다.

그 출력의 다음 consumer가 GPU `wo` FC이면 `all_consumers_gpu`가 true로
남으므로 planner는 `mha_core:out0`을 `GPU_CLMEM`으로 분류하고 device plane을
zero-fill한다. MHA는 host/SVM plane만 갱신하지만 FC는 cl_mem을 bind하므로
zero/stale attention 결과를 읽는다.

같은 문제가 일반 GPU layer에도 있다. 예를 들어 `ConcatLayerCl`은 GPU
factory에 등록되어 있지만 입력을 `getData()`에서 upload하고 결과를 다시 host
pointer로 readback한다. GPU producer → concat → GPU consumer graph에서는
concat 입력과 출력 모두 device plane으로 분류될 수 있어 양방향으로 stale
plane을 사용한다.

Residency classification에 producer/consumer별 cl_mem capability를 포함하고,
capability가 없는 경계에서는 명시적으로 lower/raise하거나 SVM으로
downgrade해야 한다. `mha_core`를 engine-neutral consumer로 취급하는 것과 그
output을 GPU producer라고 선언하는 것은 별개의 결정이어야 한다.

### P1 — terminal GPU output이 host로 lower되지 않은 채 API에 반환됨

위치:

- `nntrainer/tensor/tensor_pool.h:409`
- `nntrainer/tensor/tensor_pool.cpp:362`
- `nntrainer/graph/network_graph.cpp:421`
- `nntrainer/graph/network_graph.cpp:522`

`SourceDetails::all_consumers_gpu`는 true로 시작하고 `TensorPool::view()`가
downstream consumer를 등록할 때만 변경된다. graph output에는 downstream
view가 없으므로 FP16 GPU output은 외부 host/API reader가 있음에도
`GPU_CLMEM`으로 분류된다.

`NetworkGraph::forwarding()`과 `incremental_forwarding()`은 output tensor를
그대로 복사해 반환하며 `clmem_lower_cl()`이나 동등한 readback을 수행하지
않는다. v8c direct-out 또는 다른 cl_mem-aware producer가 device plane만
갱신한 경우 caller는 stale/zero host shadow를 받는다.

graph output을 implicit CPU consumer로 planner에 등록하거나, 반환 전에
device plane을 host로 lower해야 한다. FP16 GPU layer가 terminal인 최소
inference graph 테스트가 필요하다.

### P1 — v8c direct-out 뒤 fused activation이 stale host plane에서 실행됨

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1749`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1759`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1806`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:247`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:262`
- `nntrainer/layers/fc_layer_cl.cpp:143`

계획된 FP16 `GPU_CLMEM` output에서는 기본 `direct_out`이 GEMM 결과를
`MemoryData::deviceMem()`에 직접 쓰고 host/SVM shadow는 갱신하지 않는다.
그 직후 `FullyConnectedLayerCl`의 fused activation은
`ClComputeOps::apply_activation()`으로 들어가지만, 이 함수는 host
`ActiFunc`로 `out`을 직접 읽고 쓸 뿐 lower/raise를 하지 않는다.

따라서 host activation은 stale input에 적용되고, 다음 GPU consumer는
activation 이전의 cl_mem 결과를 계속 읽는다. cl_mem activation epilogue를
사용하거나 host fallback 전후에 lower/raise해야 하며, bias 및 activation을
포함한 전체 FC epilogue가 동일한 plane을 사용하도록 보장해야 한다.

### P1 — `ResidencyPolicy` boundary promotion과 실제 copy가 연결되지 않음

위치:

- `nntrainer/tensor/residency_policy.h:43`
- `nntrainer/tensor/tensor_pool.cpp:318`
- `nntrainer/tensor/residency_planner.h:95`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1032`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1079`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:216`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:227`

PR 설명과 header는 CausalLM이 `raise_patterns`, `lower_patterns`,
`engine_neutral_types`를 model build 시 설정한다고 하지만, current head 전체를
검색하면 이 필드에 값을 쓰는 application code가 없다. 따라서 advertised
embedding/output boundary policy는 in-tree에서 활성화되지 않는다.

더 큰 문제는 `clmem_raise_cl()`과 `clmem_lower_cl()`의 유일한 call pair가
v8c FC **fallback 내부**에 있다는 점이다. embedding producer, final norm,
lm_head 또는 graph boundary에는 copy 호출이 없다. application이나 환경
변수로 raise pattern을 설정하면 planner는 CPU-produced tensor를
`GPU_CLMEM`으로 승격하고 device plane을 zero-fill하지만 producer는 host만
쓴다. 다음 GPU consumer는 untouched cl_mem을 읽는다. lower pattern은 반대로
CPU consumer가 stale host shadow를 읽게 한다.

실제 producer/consumer boundary에 copy를 연결하기 전에는 해당 tensor를
SVM으로 유지해야 한다. policy 설정과 copy가 함께 작동하는 end-to-end
테스트도 필요하다.

## Residual risk

OpenCL hardware에서 직접 실행하지 못했다. 추가로
`Tensor::getSharedDataTensor()`가 nonzero-offset view에도 base
`TensorBacking`을 그대로 전파하고, resident RMSNorm gamma cache는 tensor
name만 key로 사용하는 process-global raw `cl_mem`이라 model reload/context
교체 시 stale buffer를 재사용할 수 있다. 새 SwiGLU cl_mem whole-op도
`row_offset`을 kernel argument에 전달하지 않아 해당 API가 연결되면
incremental row 0을 잘못 읽고 쓴다.
