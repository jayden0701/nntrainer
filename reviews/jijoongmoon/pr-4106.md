## Review summary

이 PR은 backend 이름 registry, `DeviceCaps`, layer factory 등록 facade,
그리고 tensor/run-context의 engine tag를 추가한다. PR #4105 위에 쌓인
변경이므로 고유 delta 12개 파일을 먼저 보고, GitHub에 보이는 전체
stack diff도 함께 확인했다.

이름 기반 조회와 기본 CPU fallback은 일관되지만, 새 facade와 engine tag
threading이 비-CPU 및 refinalize 경로에서 완결되지 않았다.

## Findings

### P1 — 비-CPU backend의 layer factory 등록 facade가 항상 실패함

위치:

- `nntrainer/engine.h:192`
- `nntrainer/context.h:293`
- 관련 context: `nntrainer/cl_context.h`, `nntrainer/qnn/qnn_context.h`

`Engine::registerLayerFactory("gpu", ...)`는 등록된 `ClContext`를 찾은 뒤
새 virtual을 호출한다. 그러나 현재 head에서
`registerLayerFactory()`를 override하는 구현은 `AppContext`뿐이다.
`ClContext`와 QNN context는 기본 `Context` 구현으로 내려가 경고를
남기고 `-1`을 반환한다.

따라서 문서가 설명하는 “backend 이름으로 특정 backend에 factory를
등록”하는 새 API는 CPU 외에는 동작하지 않는다. 이 PR 본문에서 concrete
override를 후속 변경으로 미뤘더라도, 현재 공개하는 facade의 핵심 계약과
맞지 않는다.

기존 `registerFactory<Layer>()`를 가진 각 concrete context에서
non-template virtual을 override하거나, 구현 전에는 facade를 노출하지
않고 지원 범위를 명확히 제한해야 한다. GPU/QNN 등록 성공 및 생성까지
검증하는 테스트가 필요하다.

### P2 — refinalize가 출력 tensor engine tag를 항상 CPU로 되돌림

위치:

- `nntrainer/layers/layer_node.cpp:808`
- `nntrainer/layers/layer_context.cpp:121`
- `nntrainer/layers/layer_context.h:111`

일반 `finalize()`는 node의 engine을 `InitLayerContext` 생성자에 전달하고,
`requestOutputs()`가 이를 output `TensorSpecV2.engine`에 기록한다.
반면 `LayerNode::refinalize()`는 engine 인자를 전달하지 않아 기본값
`CPU`를 사용한다.

이 PR은 이를 위한 것으로 보이는 `InitLayerContext::setComputeEngine()`도
추가하지만 실제 호출은 없다. 따라서 shape 변경 등으로 refinalize된
GPU/CUDA/QNN layer의 새 output spec은 CPU producer로 잘못 표시된다.
현재 PR에서는 tag consumer가 아직 없지만, 후속 residency planner가 이를
읽는 순간 잘못된 memory plane을 선택하게 된다.

`refinalize()`에서도 `toLayerComputeEngine(compute_engine)`을 생성자에
전달하거나 output 요청 전에 setter를 호출하고, 최초 finalize와
refinalize의 spec engine이 같은지 테스트해야 한다.
