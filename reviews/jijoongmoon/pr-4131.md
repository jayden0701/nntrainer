## 한눈에 보기

이 PR의 고유 변경은 Windows GPU 빌드 설정 한 개와 GitHub Actions 워크플로 한 개다.
직접 부모와 비교하면 2개 파일, 101줄 추가다.

방향 자체는 좋다. OpenCL, CUDA, FP16을 함께 켠 MSVC 빌드를 자동으로 확인하려는
목적이고, shared library를 기본으로 두되 static을 선택할 여지도 남긴 부분도 의도대로
동작한다.

하지만 현재 상태는 새 화재경보기를 달아 놓고 전원선은 연결하지 않은 것과 비슷하다.
현재 PR 브랜치 이름은 워크플로의 실행 조건과 맞지 않고, PR용 실행 조건도 없다.
게다가 수동 실행도 병합 전에는 사용할 수 없다. 어렵게 실행시킨다고 해도 MSVC용 FP16
변환 코드가 이 브랜치에 없어서 컴파일이 실패한다.

## 발견 사항

### P1 — 추가한 Windows GPU 검사가 이 PR과 일반 PR에서 실행되지 않음

위치:

- `.github/workflows/msvc_gpu_verify.yml:18-23`

워크플로는 다음 두 경우에만 실행된다.

```yaml
on:
  push:
    branches: [ 'ci/msvc-*' ]
  workflow_dispatch:
```

그러나 실제 PR head 브랜치는 `upstream-pr/trackW4-msvc-gpu-ci`다. `ci/msvc-*`와
일치하지 않으므로 push해도 실행되지 않는다. `pull_request` 조건도 없어서 이 PR뿐
아니라 이후 일반 PR의 Windows GPU 필수 검사 역할도 하지 못한다.

`workflow_dispatch`도 지금은 대안이 아니다. GitHub는 수동 실행할 워크플로 파일이
기본 브랜치에 이미 있어야 한다고 명시한다. 이 파일은 아직 `main`에 없으므로 병합
전에는 수동으로 현재 PR을 검사할 수 없다.

실제로 현재 head의 GitHub 검사 목록에는 DCO와 PR 설명 검사만 있고
`Windows GPU MSVC verify` 실행 기록은 없다. 또한 PR이 현재 `main`과 충돌 중이라,
`pull_request` 조건을 추가한 뒤에도 충돌을 먼저 풀어야 실행된다. GitHub는 충돌이
있는 PR의 `pull_request` 워크플로를 실행하지 않는다.

비유하면 새 검사대를 만들었지만 출입문 표지판을 다른 이름으로 달아 둔 상태다.
검사할 물건이 와도 문이 열리지 않으므로, 검사대가 고장 났는지조차 알 수 없다.

권장 수정:

1. 최소한 `pull_request` 트리거를 추가해 `main` 대상 PR에서 실행되게 한다.
2. 현재 merge conflict를 해결한 뒤 이 PR의 head에서 실제 성공 기록을 확인한다.
3. 작업 브랜치 push도 유지하려면 실제 사용하는 브랜치 이름과 맞는 패턴으로 바꾼다.

참고: [GitHub Actions 이벤트 설명](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch),
[워크플로 트리거 문제 해결](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#troubleshooting-workflow-triggers)

### P1 — FP16은 켰지만 MSVC용 FP16 구현이 현재 브랜치에 없음

위치:

- `configurations/windows-native-gpu.ini:5-8`
- `.github/workflows/msvc_gpu_verify.yml:3-10`
- `meson.build:214-218`
- `api/ccapi/include/tensor_dim.h:25-30`

설정은 `enable-fp16=true`를 켠다. 워크플로 주석은 `fp16-impl=auto`가 MSVC용
`Half` 구현을 자동 선택한다고 설명한다.

하지만 리뷰한 head에는 `fp16-impl` 옵션도, `half_fp16.h`도 없다. 현재 코드는
x86_64에서 FP16을 켜면 `_FP16`을 `_Float16`으로 정의한다. MSVC의 `cl.exe`는 이
타입을 지원하지 않으므로 현재 커밋 그대로는 컴파일할 수 없다.

PR 본문에 #4129를 의존 PR로 적어 두기는 했지만, #4129의 변경은 현재 head의 조상에
포함되어 있지 않다. “변환 어댑터가 필요하다”는 설명만 있고 실제 상자에는 어댑터가
없는 셈이다.

권장 수정:

1. [#4129](./pr-4129.md)의 수정된 FP16 구현을 이 브랜치에 실제로 포함한 뒤 CI를
   실행한다.
2. 그 전까지는 이 설정에서 FP16을 켜지 않는다.
3. 주석에 쓰인 `fp16-impl=auto`가 실제 Meson 옵션으로 존재하는지도 함께 검증한다.

#4129 자체에도 FP16 max-pooling 오동작 등 병합 전 고쳐야 할 문제가 있으므로, 단순히
현재 #4129 head를 가져오는 것만으로 완료됐다고 보기는 어렵다.

### P2 — CausalLM을 켜지 않아 이 PR이 의존하는 GPU 앱 경로를 컴파일하지 않음

위치:

- `configurations/windows-native-gpu.ini:1-33`
- `meson_options.txt:82`
- `Applications/meson.build:53-57`

`enable-transformer`의 기본값은 `false`인데 새 설정과 `meson setup` 명령 어디에서도
이를 `true`로 바꾸지 않는다. 따라서 `Applications/CausalLM`은 빌드 대상에서 빠진다.

이 PR은 CUDA LM head가 포함된 #4124에 의존하고, 설정 주석에는 “library + app
compile”이라고 적혀 있다. 그러나 현재 검사는 자동차 엔진만 조립해 보고, 실제로 그
엔진을 쓰는 CausalLM 차체는 창고에 둔 채 검사를 마치는 것과 같다. core library
컴파일은 확인할 수 있어도 CausalLM의 Windows OpenCL/CUDA/FP16 조합이 함께
컴파일되는지는 확인하지 못한다.

CausalLM까지 검증하려는 목적이라면 `-Denable-transformer=true`를 추가해야 한다.
core library만 검증하려는 목적이라면 워크플로 이름과 설명에서 앱 검증 주장을 빼고,
CausalLM용 검사를 별도로 두는 편이 명확하다.

### P2 — 외부 Action을 바뀔 수 있는 이름으로 실행하고 권한 범위도 명시하지 않음

위치:

- `.github/workflows/msvc_gpu_verify.yml:25-50`

`Jimver/cuda-toolkit@v0.2.35`와 `bus1/cabuild/action/msdevshell@v1`은 고정된 commit
SHA가 아니라 움직일 수 있는 tag다. 나중에 tag가 가리키는 코드가 바뀌면 같은
nntrainer commit을 다시 검사해도 다른 코드가 실행될 수 있다. 외부 창고에서 공구를
빌리면서 공구의 정확한 일련번호는 기록하지 않은 것과 비슷하다.

또한 워크플로에 명시적인 `permissions`가 없어 저장소의 기본 설정에 권한 범위를
맡긴다. 최소한 다음과 같이 읽기 권한만 선언하고, 외부 Action은 검토한 full commit
SHA로 고정하는 것이 안전하다.

```yaml
permissions:
  contents: read
```

## 확인한 내용

- GitHub에서 PR의 현재 head, 브랜치 이름, 충돌 상태, 검사 목록을 확인했다.
- 직접 부모와 비교한 고유 변경 2개 파일을 검토했다.
- 현재 head에 `fp16-impl` 옵션과 `half_fp16.h`가 없고, #4129가 ancestry에 포함되지
  않았음을 확인했다.
- Meson 옵션과 `Applications/CausalLM` 진입 조건을 따라가
  `enable-transformer=false`에서는 CausalLM이 빌드되지 않음을 확인했다.
- `default_library`를 생략했을 때 shared가 기본이고 static은 명령행으로 선택할 수
  있다는 설명은 맞음을 확인했다.
- `git diff --check`는 통과했다.
- Windows GPU 빌드는 실행하지 못했다. 새 워크플로 자체가 현재 PR에서 실행되지
  않았고, 로컬 환경은 Windows GPU CI와 동일한 준비 상태가 아니다.

## 권장 수정 순서

1. #4129의 수정 완료본을 실제 브랜치에 포함한다.
2. `pull_request` 트리거를 추가하고 현재 충돌을 해결한다.
3. CausalLM도 범위라면 `enable-transformer=true`를 켠다.
4. Action 권한과 외부 Action 버전을 고정한다.
5. 새 Windows GPU job이 현재 head에서 실제로 성공한 것을 확인한다.
