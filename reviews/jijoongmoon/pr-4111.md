## Review summary

이 PR은 #4110의 v8c int8×int4 FC 위에 Intel Xe2/Xe3용 XMX/DPAS
prefill fast path를 추가한다. #4110 대비 고유 delta는 4개 파일,
369개 추가 라인이다.

새 경로의 shape gate가 Intel 2D block-I/O 명세의 최소 surface 폭을
완전히 반영하지 않아 `K=64`에서 undefined behavior가 발생한다. 또한 공개된
튜닝 환경변수를 검증하지 않아 흔한 잘못된 값 하나만으로 프로세스가
0 나눗셈에 도달한다.

## Findings

### P1 — `K=64`가 XMX gate를 통과하지만 weight surface 폭은 명세 최솟값보다 작음

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1682`
- `nntrainer/tensor/cl_operations/cl_kernels/int8_int8_gemm_xmx.cl:148`

host gate는 `K % 64 == 0`만 확인하므로 `M > 4`, `N % 64 == 0`,
`K=64`인 정상 FC shape를 XMX로 보낸다. 새 kernel은 weight 2D block
read의 `width`와 `pitch`에 `K / 2`를 전달하므로 이때 surface 폭은
32바이트다.

그러나
[`cl_intel_subgroup_2d_block_io` 명세의 Restrictions](https://registry.khronos.org/OpenCL/extensions/intel/cl_intel_subgroup_2d_block_io.html#modifications-to-the-opencl-c-specification)는
`width >= 64 bytes`를 요구하고, 제한을 만족하지 않을 때의 동작을
undefined로 규정한다. 따라서 해당 shape는 잘못된 결과나 device fault를 낼 수
있다. gate에 `K >= 128`을 추가해 `K=64`를 DP4A로 보내거나, weight
surface를 최소 64바이트 pitch로 패딩해야 한다. 이 경계 shape를 실제 XMX
device에서 DP4A 결과와 비교하는 테스트도 필요하다.

### P1 — 잘못된 XMX tile 환경변수가 0 나눗셈을 일으킴

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1696`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1701`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1744`

`NNTR_XMX_NT`를 `atoi()` 결과 그대로 수용한 뒤
`N % ((unsigned)xmx_nt * 16)`을 계산한다. 따라서
`NNTR_XMX_NT=0`뿐 아니라 `NNTR_XMX_NT=foo`처럼 `atoi()`가 0을
반환하는 값도, XMX gate를 통과한 첫 prefill FC에서 divisor 0을 만든다.
kernel 등록 실패 후 DP4A로 복귀할 기회조차 오기 전이다.

`NNTR_XMX_SGM=0` 또는 비숫자 값도 `mpwg=0`을 만든 뒤 `Mpad` 계산에서
0으로 나눈다. `NT`와 `SG_M`을 지원하는 양의 tile 범위로 엄격히 파싱하고,
잘못된 값은 각각 기본값 2와 4로 되돌리거나 XMX를 끄도록 해야 한다.
`SG_M`은 device work-group 한도도 함께 확인해야 한다. `0`, 비숫자, 음수,
과도하게 큰 값에 대한 host-side 경계 테스트가 필요하다.

## Residual risk

로컬에 XMX-capable Intel GPU가 없어 kernel 수치 결과와 driver별 compile/
enqueue 동작은 실행 검증하지 못했다. 특히 capability gate는 DPAS extension만
검사하지만 kernel은 별도의 2D block-I/O extension과 subgroup 제약도 요구한다.
kernel build 실패를 negative-cache하지 않으므로, 이런 capability 조합에서는
여러 FC가 같은 실패한 compile을 반복할 가능성도 남아 있다.
