## 요약

이 PR은 CausalLM 전용 GLU, scalar, tied-embedding 구현을 core library로
옮기고, model 선택 분기문을 registry로 교체한다. 현재 헤드에서는 앞서
자동 리뷰가 지적했던 Android source 목록과 `size_t` overflow 문제가
수정되었다. 다만 여러 구현을 합치는 과정에서 resumed prefill, GPU scalar의
일반 forwarding, OpenCL 데이터 및 weight coherence가 깨진다.

직접 부모인 PR #4114 대비 고유 변경은 44개 파일이다.

## 발견 사항

### P1 — nonzero 위치에서 시작하는 multi-token prefill이 GLU layer에서 예외 발생

위치:

- `nntrainer/layers/llm/swiglu_layer.cpp:71-76`
- `nntrainer/layers/llm/geglu_layer.cpp:51-59`
- `Applications/CausalLM/models/causal_lm.cpp:553-578`

두 promoted GLU 구현은 `from != 0`이면서 `to - from != 1`인 incremental
호출을 거부한다. 그러나 CausalLM은 system-prompt cache를 불러왔거나 이전
대화 뒤에 새 prompt를 이어 붙일 때 `prefill_from`을 0보다 크게 설정하고,
새 multi-token prompt 전체를 한 번의 `incremental_inference()`로 전달한다.

`skip_prefill=false`인 일반 SwiGLU/GeGLU node에서는 이 경로가 prompt를
계산하지 않고 `invalid_argument`를 발생시킨다. 이 PR에서 삭제된
application 전용 SwiGLU는 `to - from`개 row를 처리했으므로 같은 호출을
지원했다.

GLU는 임의 길이의 prefill 구간을 처리하고, 1-token decode만 별도
최적화해야 한다. 최소한 `from > 0`, `to - from > 1`인 회귀 테스트가
필요하다.

### P1 — `engine=gpu` scalar의 일반 forwarding이 아무 계산도 하지 않음

위치:

- `nntrainer/layers/llm/scalar_multiply_gpu.h:47-48`
- `nntrainer/cl_context.cpp:236-240`

새 OpenCL factory는 `scalar_multiply`를 `ScalarMultiplyLayerGPU`로
연결한다. 하지만 이 class의 `forwarding()` override 본문은 비어 있다.
따라서 `engine=gpu` scalar node를 일반 forward/inference로 실행하면
출력 tensor가 갱신되지 않는다. 실제 곱셈은 `incremental_forwarding()`에만
구현되어 있다.

`forwarding()`에서도 전체 tensor 연산을 수행하거나, 두 경로가 안전하게
공유하는 구현을 호출해야 한다.

### P1 — CLMEM boundary copy가 batch 0만 처리함

위치:

- `nntrainer/layers/llm/tie_word_embedding.cpp:508-510`
- `nntrainer/layers/llm/tie_word_embedding.cpp:538-540`

embedding output raise는
`(to - from) * out_dim * dtype_size` byte만 복사하고, lm-head input lower도
`(to - from) * width * dtype_size` byte만 복사한다. 두 크기 모두 tensor의
batch 차원을 빠뜨렸지만, 주변 embedding/lm-head loop는 모든 batch를
계산한다.

`clmem_raise_cl()`과 `clmem_lower_cl()`은 offset 0부터 전달받은 byte 수만
복사한다. 따라서 `batch > 1`이면 이후 batch의 device embedding 또는 host
lm-head input이 stale 상태로 남아 조용히 잘못된 결과를 만든다. 활성
batch/channel 전체를 복사하거나 batch별 offset으로 전송해야 한다.

### P1 — OpenCL lm-head weight cache가 checkpoint 재로딩 후에도 이전 weight 사용

위치:

- `nntrainer/layers/llm/tie_word_embedding.cpp:787-788`
- `nntrainer/layers/llm/tie_word_embedding.cpp:852-855`
- `nntrainer/layers/llm/tie_word_embedding.cpp:916-948`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2789-2803`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:3116-3130`

새로 사용되는 Q6_K 및 FP32 OpenCL lm-head helper는 process-static device
weight buffer를 host allocation 주소만으로 구분한다. 같은 pointer가 처음
나왔을 때 한 번만 weight를 upload한다.

`TieWordEmbedding::read()`는 기존 tensor allocation에 다른 checkpoint를
다시 읽을 수 있으므로 pointer는 같지만 내용은 달라질 수 있다. model을
삭제한 뒤 allocator가 같은 주소를 재사용해도 동일하다. 이후 inference는
이전 checkpoint의 `cl_mem` weight를 재사용해 잘못된 결과를 낸다.

cache key에 owner/generation을 포함하고 weight load 때 명시적으로
invalidate하거나, host weight가 바뀔 때 device buffer를 다시 올려야 한다.

### P1 — GeGLU kernel 실패가 무관한 scalar와 tied-embedding factory까지 제거

위치:

- `nntrainer/cl_context.cpp:230-245`
- `nntrainer/tensor/cl_operations/geglu_cl_op.cpp:317-354`

`ScalarMultiplyLayerGPU`와 `TieWordEmbedding`의 GPU factory 등록이
`if (registerGeGLUClKernels(*this))` 내부에 들어 있다. 어떤 driver에서
무관한 GeGLU kernel compile 또는 등록이 실패하면 GeGLU를 전혀 사용하지
않는 model도 scalar와 tied-embedding factory를 잃고 layer 생성 단계에서
실패할 수 있다.

두 factory를 GeGLU 조건문 밖으로 옮기고, 각 factory를 자신의 선행 조건에만
연결해야 한다.

## 남은 위험

OpenCL 장비에서 직접 실행하지는 못했다. promoted layer에는 nonzero-offset
prefill, multi-batch 실행, checkpoint reload, 일반 GPU forwarding에 대한
테스트가 부족하므로 해당 경로를 집중적으로 보강해야 한다.
