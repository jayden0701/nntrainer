## Review summary

This PR promotes the CausalLM-specific GLU, scalar, and tied-embedding
implementations into the core library and replaces the model-selection chain
with a registry. The current head fixes the earlier Android source-list and
`size_t` overflow reports, but the merged layer implementations regress resumed
prefill, full GPU scalar execution, and OpenCL data/weight coherence.

The review compares the 44-file PR delta against its direct parent, PR #4114.

## Findings

### P1 — Resumed multi-token prefill throws in the promoted GLU layers

Locations:

- `nntrainer/layers/llm/swiglu_layer.cpp:71-76`
- `nntrainer/layers/llm/geglu_layer.cpp:51-59`
- `Applications/CausalLM/models/causal_lm.cpp:553-578`

Both promoted GLU implementations reject any incremental call for which
`from != 0` and `to - from != 1`. That assumption does not hold for CausalLM:
after loading a system-prompt cache or continuing a conversation,
`prefill_from` is nonzero and the application sends the entire new multi-token
prompt in one `incremental_inference()` call.

For ordinary SwiGLU/GeGLU nodes whose `skip_prefill` property is false, this
path deterministically raises `invalid_argument` instead of processing the
prompt. The application-local SwiGLU removed by this PR processed
`to - from` rows and therefore supported this call shape.

The GLU implementations should process arbitrary prefill windows, while
retaining the single-token optimized decode path. At minimum, add coverage for
a multi-token call with a nonzero `from`.

### P1 — `engine=gpu` scalar multiplication does nothing in normal forwarding

Locations:

- `nntrainer/layers/llm/scalar_multiply_gpu.h:47-48`
- `nntrainer/cl_context.cpp:236-240`

The new OpenCL factory routes `scalar_multiply` to
`ScalarMultiplyLayerGPU`, but that class overrides `forwarding()` with an empty
body. Consequently, any full forward/inference call on an `engine=gpu` scalar
node returns an untouched output tensor. Only `incremental_forwarding()` performs
the multiplication.

`forwarding()` must execute the full tensor operation (or safely delegate to a
shared implementation); an empty override is not a valid implementation for a
registered core layer.

### P1 — CLMEM boundary copies omit every batch after batch 0

Locations:

- `nntrainer/layers/llm/tie_word_embedding.cpp:508-510`
- `nntrainer/layers/llm/tie_word_embedding.cpp:538-540`

The embedding output raise copies only
`(to - from) * out_dim * dtype_size` bytes, and the lm-head input lower copies
only `(to - from) * width * dtype_size` bytes. Both sizes omit the tensor batch
dimension even though the surrounding embedding and lm-head loops process every
batch.

`clmem_raise_cl()` and `clmem_lower_cl()` use the supplied byte count from
offset zero. With `batch > 1`, later batches therefore retain stale device
embedding data or stale host lm-head input and produce silently incorrect
results. Copy all active batches/channels, or issue correctly offset transfers
per batch.

### P1 — OpenCL lm-head weight caches survive an in-place checkpoint reload

Locations:

- `nntrainer/layers/llm/tie_word_embedding.cpp:787-788`
- `nntrainer/layers/llm/tie_word_embedding.cpp:852-855`
- `nntrainer/layers/llm/tie_word_embedding.cpp:916-948`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2789-2803`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:3116-3130`

The newly used Q6_K and FP32 OpenCL lm-head helpers keep process-static device
weight buffers keyed only by the host allocation address. They upload the
weight once when that pointer is first encountered. `TieWordEmbedding::read()`
can subsequently load another checkpoint into the same tensor allocation, so
the pointer remains unchanged while its contents change. Allocator address
reuse after destroying a model has the same effect.

Later inference then reuses the old `cl_mem` weight buffer and silently computes
with the previous checkpoint. The cache needs an owner/generation identity and
explicit invalidation on weight load, or it must refresh the device buffer when
the host weight changes.

### P1 — GeGLU kernel failure removes unrelated scalar and tied-embedding factories

Locations:

- `nntrainer/cl_context.cpp:230-245`
- `nntrainer/tensor/cl_operations/geglu_cl_op.cpp:317-354`

The GPU factories for `ScalarMultiplyLayerGPU` and `TieWordEmbedding` are
registered inside `if (registerGeGLUClKernels(*this))`. If the unrelated GeGLU
kernel fails to compile or register on a driver, models that never contain
GeGLU still lose both factories and can fail while creating scalar or tied
embedding nodes.

Move those registrations out of the GeGLU conditional and gate each factory
only on its own prerequisites.
