## Review summary

이 PR은 #4110의 v8c weight prebuild에 대형 weight 병렬 pack/upload와 소형
weight non-blocking upload registry를 추가한다. 행 분할, upload offset 및
`row_sum` 인덱스 계산은 유효한 N/K 범위에서 서로 일치했다.

그러나 기본 활성화된 non-blocking 경로는 지원되는 out-of-order queue에서 첫
GEMM과 의존성이 없다. 또한 pending upload를 실제 첫 dispatch가 아닌 다음
weight의 prebuild 시작 시 flush하여 마지막 batch가 회수되지 않고, 대형 weight
worker의 예외 경로는 기존 fallback 대신 프로세스를 종료할 수 있다.

## Findings

### P1 — out-of-order queue에서 weight upload보다 GEMM이 먼저 실행될 수 있음

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2211`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2233`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:853`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:950`
- `nntrainer/opencl/opencl_command_queue_manager.cpp:128`

64 MiB 미만 weight의 기본 경로는
`clEnqueueWriteBuffer(..., CL_FALSE, ..., &event)`로 upload를 enqueue하고
backing을 즉시 반환한다. event는 process-global pending list에만 보관되며,
후속 GEMM의 wait-list나 해당 backing에 연결되지 않는다. 구현 주석은 command
queue가 in-order라고 가정하지만, 같은 head에서 문서화된
`NNTR_GPU_SVM_POOL=0` 경로는
`CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE`로 queue를 만든다.

유일한 `v8c_flush_pending_uploads()` 호출은 실제 `dotCl_v8c()` dispatch가
아니라 다음 `dotCl_v8c_prebuild_weight()` 시작부에 있다. 따라서 마지막 또는
유일한 eligible weight의 upload는 첫 GEMM 전에 기다리지 않으며, OOO queue가
GEMM을 먼저 실행하면 부분적으로 채워졌거나 초기화되지 않은 weight를 읽는다.

OOO queue에서는 async upload를 끄거나, backing별 completion event를 첫
consumer의 wait-list에 전달해야 한다. 최소한 실제 dispatch 경계에서 upload
완료를 보장하는 회귀 테스트가 필요하다.

### P1 — 대형 weight의 thread 생성·worker 할당 실패가 `std::terminate`를 호출함

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2178`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2181`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:634`

대형 weight 경로는 raw `std::thread`를 vector에 순서대로 추가한 뒤 마지막에
join한다. 하나 이상의 thread가 생성된 뒤 다음 `emplace_back()`이
`std::system_error`를 던지면 stack unwinding 중 joinable `std::thread`의
destructor가 `std::terminate`를 호출한다. worker 내부의 최대 16 MiB staging
vector 할당 또는 `pack_rows()`가 던지는 예외도 thread entry에서 잡히지 않아
동일하게 프로세스를 종료한다.

이전 serial 경로에서는 해당 실패가 상위 catch를 거쳐 CPU/fallback 경로로
전환될 수 있었다. 항상 join하는 RAII guard를 사용하고 worker 예외를
`std::exception_ptr` 등으로 호출 thread에 전달해야 한다.

### P2 — flush 위치가 잘못되어 마지막 staging과 event가 process lifetime 동안 남음

위치:

- `nntrainer/tensor/cl_operations/blas_kernels.cpp:1979`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2003`
- `nntrainer/tensor/cl_operations/blas_kernels.cpp:2034`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:853`

PR 설명은 첫 FC dispatch가 pending upload를 회수한다고 하지만, 실제 유일한
flush 호출은 **현재 weight를 만들기 전**이다. 그 결과 다음 prebuild는 직전
upload를 즉시 기다려 의도한 load-time overlap을 줄이고, 마지막 prebuild가
추가한 staging vector와 raw `cl_event`는 첫 forward에서도 회수되지 않는다.
추가 prebuild나 256 MiB cap overflow가 없으면 process-global registry에
계속 남는다.

flush를 model-load 완료 또는 실제 첫 v8c dispatch 경계로 옮기고, lifecycle
종료 시에도 pending command를 기다린 뒤 event를 release하는 RAII ownership을
추가해야 한다. `v8c_wait_and_free()`는 `clWaitForEvents()`의 오류와 event의
negative execution status도 확인하여 upload 실패를 weight cache 성공으로
취급하지 않아야 한다.

## Residual risk

OpenCL hardware에서 직접 실행하지 못했다. 특히 OOO queue 재현과 upload
failure injection, thread/allocation failure injection 테스트가 없다. 또한
동시 producer가 각자 cap overflow batch를 lock 밖에서 기다리는 동안 global
list가 다시 차오를 수 있어, “256 MiB bounded”는 전체 프로세스 기준의 엄격한
상한이 아니다.
