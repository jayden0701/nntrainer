## 요약

이 PR은 CUDA 장치 초기화 때 약 15개의 환경변수 기본값을 주입해 별도
설정 없이도 GPU 최적화 경로를 사용하게 한다. 직접 부모 #4126 대비 고유
변경은 `nntrainer/cuda_context.cpp` 64줄이다.

문제는 기본으로 켜는 기능이 현재 tree에서 준비되지 않았다는 점이다.
모든 discrete GPU에서 `NNTR_CUDA_M2B=1`을 넣어 #4126의 미완성 graph
replay를 opt-in이 아닌 기본 decode 경로로 만든다. 동시에
`NNTR_CUDA_DEV_ACT=1`로 activation을 `cudaMalloc` device-only memory에
두지만, CUDA context가 등록하는 residual addition과 GeGLU 등은 여전히
CPU 구현이다. 이들은 device pointer를 host에서 직접 읽어 crash할 수 있다.

특히 `NNTR_RMSNORM_CUDA_OFF=all`이 prefill RMSNorm도 GPU로 보낸다는
설명과 달리 이 환경변수의 소비자는 하나도 없다. 32행을 넘는 prefill은
그대로 host fallback되어 device-only pointer를 역참조한다. 자동 설정
15개 중 실제 reader가 있는 값은 4개뿐이라 PR의 “명시한 `=0`은 항상
opt-out” 및 “bare CUDA run이 full-GPU가 된다”는 계약도 성립하지 않는다.

## 발견 사항

### P1 — 불완전한 M2-B를 모든 discrete GPU의 기본 decode로 바꿈

위치:

- `nntrainer/cuda_context.cpp:121-124`
- `nntrainer/cuda_context.cpp:146-149`
- `nntrainer/cuda_context.cpp:347-431`
- `nntrainer/cuda/cuda_stream_manager.cpp:209-234`

direct parent #4126에서 `NNTR_CUDA_M2B`는 기본 off인 실험 경로였다. 이
PR은 discrete+cMA와 cMA==0 두 분기 모두에서 값을 `1`로 넣는다. 따라서
사용자가 `NNTR_ENGINE=cuda`만 설정해도 첫 decode를 capture하고 다음
token부터 cached graph를 재생한다.

그러나 #4126에서 확인한 핵심 correctness 조건은 여전히 빠져 있다.

- `cuda_pos_buffer()`는 값을 쓰기만 하며 이를 읽는 kernel 또는 argument
  binding이 현재 head에 없다.
- capture 중 host layer는 graph node가 되지 않는다.
- `_cg_cached_exec`와 output은 모든 모델이 공유하는 함수 정적 상태다.
- `g_m2b_skip_all`은 쓰기만 하고 forwarding loop에서 읽지 않는다.
- graph launch와 synchronize 오류를 무시한다.

PR 본문은 app-side kernel이 들어오기 전 일부 환경변수는 “읽히지 않아
무해하다”고 설명하지만, `NNTR_CUDA_M2B`에는 이미 core reader가 있다.
따라서 이 값은 inert하지 않으며 잘못된 graph를 실제로 활성화한다.

#4126의 position 갱신, host-op capture, 모델별 cache와 오류 처리가 모두
해결될 때까지 M2-B를 auto-default에서 제거해야 한다. 최소한 필요한
app-side consumer가 등록됐는지 검증하고 그렇지 않으면 eager로 돌아가야
한다.

### P1 — `DEV_ACT=1` 때문에 residual addition이 device pointer를 host에서 읽음

위치:

- `nntrainer/cuda_context.cpp:121`
- `nntrainer/cuda_context.cpp:146`
- `nntrainer/cuda_context.cpp:178-181`
- `nntrainer/tensor/manager.h:140-145`
- `nntrainer/cuda_mem_allocator.cpp:84-100`
- `nntrainer/layers/addition_layer.cpp:36-42`
- `nntrainer/layers/addition_layer.cpp:65-78`
- `nntrainer/cuda/cuda_compute_ops.cpp:34-50`

`NNTR_CUDA_DEV_ACT=1`이면 CUDA UVM allocator를 받은 activation pool이
`CudaMemAllocator(device_only=true)`로 바뀌고 discrete GPU에서는 실제
`cudaMalloc` pointer를 반환한다. 그런데 같은 CUDA context는 core
`AdditionLayer`를 등록한다. 이 layer의 첫 copy 일부만 device-aware이고,
두 번째 입력부터 수행하는 `add_i()`는 `CudaComputeOps`가 상속한 CPU
elementwise 구현이다.

따라서 일반 transformer의 residual addition이 `cudaMalloc` pointer를
CPU에서 역참조한다. Linux에서는 segmentation fault, Windows에서는 access
violation이 될 수 있다. `concurrentManagedAccess` capability는 managed
memory의 동시 접근 특성이지 `cudaMalloc` memory를 host-addressable하게
만들지 않는다.

GeGLU 등 CUDA override가 없는 다른 `CpuComputeOps` 경로도 같은 문제가
있다. 모든 activation consumer가 device-only memory를 지원하기 전에는
이 값을 기본으로 켜면 안 된다. 또는 layer별 residency 분석을 통해 host
consumer가 있는 tensor는 UVM/staging에 남겨야 한다.

현재 head에는 CUDA graph가 CPU allocator를 받는 선행 문제도 있어 이
결함이 가려질 수 있다. 하지만 그 allocator blocker를 정상 수정하면 바로
이 기본 경로가 활성화되므로 안전한 profile이라고 볼 수 없다.

### P1 — RMSNorm의 “all rows” 설정이 dead라 prefill이 host crash로 내려감

위치:

- `nntrainer/cuda_context.cpp:123`
- `nntrainer/cuda_context.cpp:148`
- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:79-108`

새 코드는 `NNTR_RMSNORM_CUDA_OFF=all`이 CUDA RMSNorm의 row 제한을 없앤다고
설명한다. 그러나 현재 PR head 전체에서 이 변수의 reader는 없다.
`CudaRMSNormLayer`는 여전히 `gpu_max_rows = 32` 상수를 사용한다.

따라서 길이 33 이상의 prefill은 host `rmsnorm_rows()`로 내려간다. 같은
PR이 `DEV_ACT=1`을 기본으로 넣었으므로 input과 output은 device-only
`cudaMalloc` pointer일 수 있고, host loop가 이를 직접 역참조해 crash한다.
사용자가 주석대로 `NNTR_RMSNORM_CUDA_OFF=1`을 지정해도 아무 변화가 없다.

환경변수를 실제 row-cap 선택에 연결하고 device accessibility를 확인한 뒤
host staging을 제공하거나, 구현이 들어오기 전까지 `DEV_ACT` 기본값을
켜지 않아야 한다. 32행과 33행 경계 테스트가 필요하다.

### P2 — 15개 기본값 중 11개가 읽히지 않아 설명과 opt-out 계약이 맞지 않음

위치:

- `nntrainer/cuda_context.cpp:97-106`
- `nntrainer/cuda_context.cpp:121-130`
- `nntrainer/cuda_context.cpp:146-149`
- `nntrainer/cuda/cuda_compute_ops.cpp:191-195`

현재 head 전체에서 실제 reader가 있는 자동 설정은 다음 4개뿐이다.

| 변수 | 실제 소비자 | `=0` opt-out |
|---|---|---|
| `NNTR_CUDA_ELTWISE` | scalar multiply | 작동 |
| `NNTR_CUDA_DEV_ACT` | activation allocator | 작동 |
| `NNTR_CUDA_M2B` | `runDecode()` | 작동 |
| `NNTR_CUDA_ASYNC` | stream manager | 작동 |

다음 11개는 setter와 주석 외 reader가 없다.

`NNTR_CUDA_ROPE`, `NNTR_CUDA_ATTN`, `NNTR_CUDA_KV_UVM`,
`NNTR_CUDA_GEGLU`, `NNTR_CUDA_QKNORM`, `NNTR_CUDA_FLASH_DECODE`,
`NNTR_CUDA_BLOCKQ`, `NNTR_FC_CUDA_CUBLAS`, `NNTR_CUDA_PREWARM`,
`NNTR_CUDA_VCOPY_PREFILL`, `NNTR_RMSNORM_CUDA_OFF`

특히 common profile 10개 중 실제 동작하는 값은 `ELTWISE` 하나뿐이다.
따라서 이 commit만으로 rope, attention, GeGLU, QK norm과 FC가 GPU로
이동한다는 설명은 사실이 아니다.

`NNTR_FC_CUDA_CUBLAS=0`도 cuBLAS를 끄지 못한다. FP16 prefill의 cuBLAS
호출은 이 값을 읽지 않고 먼저 실행된다. “모든 explicit env가 항상
우선하며 `=0`이 기본 기능을 끈다”는 계약을 제공하려면 각 변수의 실제
consumer와 value check를 같은 stack에 포함해야 한다. 아직 없는 downstream
설정을 미리 process environment에 주입하는 대신 typed execution plan으로
전달하는 편이 검증하기 쉽다.

### P2 — `cMA==0`을 WDDM으로 단정하고 PR 설명과 반대 profile을 적용함

위치:

- `nntrainer/cuda_context.cpp:108-149`
- `nntrainer/cuda/cuda_context_manager.cpp:147-150`

PR 본문은 integrated GPU와 WDDM(cMA==0)이 managed pool과 per-op drain의
안전한 base profile을 유지한다고 설명한다. 현재 head는 반대로 cMA==0
discrete 분기에서도 `DEV_ACT`, `VCOPY_PREFILL`, RMSNorm 설정과 M2-B를
모두 기본 활성화한다. 바로 앞 cMA 분기 주석은 이 기능들이 cMA==0에서 host
access violation을 만든다고 설명하고 있어 코드 내부 설명끼리도 모순된다.

또한 `concurrentManagedAccess==0`은 WDDM만 뜻하지 않는다. 기존 코드도
pre-Pascal 장치를 함께 언급하며, capability query가 실패해 초기값 0이
남은 경우도 이 분기로 들어간다. 특정 WDDM 장치의 측정 결과를 이 모든
장치군의 기본값으로 일반화할 수 없다.

WDDM 여부와 capability query 성공을 별도로 확인하고, PR 본문과 실제
profile 중 어느 것이 의도인지 맞춰야 한다. 적어도 host fallback이 남은
현재 tree에서는 cMA==0 분기도 안전한 base profile을 유지해야 한다.

## sibling PR과의 통합 위험

#4125는 `NNTR_DETERMINISTIC`이 unset인 상태를 기본 on으로 바꾼다. 반면
이 PR은 값이 문자 `1`일 때만 deterministic으로 보고, unset이면
discrete+cMA에서 `NNTR_CUDA_ASYNC=1`을 넣는다. 현재 #4125와 #4127은
#4124에서 갈라진 sibling이라 #4127 head 단독에는 default-on 계약이 없다.
그러나 두 PR을 함께 병합하면 bare CUDA run에서 #4125의 기본 deterministic
계약을 이 PR이 즉시 무효화한다.

두 stack을 통합할 때는 공통의 value-checked helper로 기본값을 한 번만
결정하고, deterministic on이면 M2-B correctness 여부와 별개로 ASYNC를
명시적으로 끄는 테스트가 필요하다.

## 정상으로 확인한 부분

- 현재 실제 reader가 `nntr_env_on()`을 쓰는 `ELTWISE`, `DEV_ACT`, `M2B`는
  명시적인 `=0` opt-out을 존중한다.
- `NNTR_CUDA_ASYNC=0`도 stream manager에서 off로 처리된다.
- integrated GPU에는 `DEV_ACT`, M2-B와 ASYNC 기본값을 넣지 않는다.
- `setenv(..., overwrite=0)`의 POSIX 동작과 Windows shim은 이미 존재하는
  사용자 값을 덮어쓰지 않는다.
- 직접 부모 대비 `git diff --check`를 통과했다.

첫 finding에서 영향만 다시 설명했다.

## 테스트 공백

고유 변경에 자동 테스트가 없다. 최소한 다음 조합을 확인해야 한다.

- residual addition이 있는 bare discrete CUDA model의 prefill/decode
- FP16 RMSNorm의 32행과 33행 경계, UVM과 device-only pool
- M2-B의 두 번째 token에서 position과 KV length 갱신
- 모든 자동 env의 unset, `0`, `1` 값과 실제 dispatch 선택
- integrated, Linux discrete+cMA, WDDM, pre-Pascal 또는 capability-query 실패
- #4125와 통합한 상태의 deterministic unset/0/1 및 ASYNC 조합

현재 환경에는 CUDA GPU와 toolkit이 없어 runtime 검증은 수행하지 못했다.
