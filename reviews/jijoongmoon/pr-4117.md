## 요약

이 PR은 `cuda` context, UVM allocator, stream, NVRTC module/kernel cache와
decode dispatch seam을 추가한다. 직접 부모 #4115 대비 고유 변경은 27개
파일, 약 2,600줄이다.

현재 구현은 CUDA context를 registry에 추가하지만 실제 graph tensor pool을
CUDA allocator에 연결하지 않는다. 또한 선택한 device의 thread-local
context 유지, 비동기 오류 전달, kernel cache의 식별자와 동시성 보장이
부족하다.

## 발견 사항

### P1 — CUDA graph에도 CPU allocator가 연결됨

위치:

- `nntrainer/models/neuralnet.cpp:237-261`
- `nntrainer/cuda_context.cpp:81-85`

`NeuralNetwork::compile()`의 allocator 선택은 `ENABLE_OPENCL` 블록 안에서
`isComputeEngineGPU()`만 검사한다. `isComputeEngineCUDA()`를 확인해
`engine_name="cuda"`로 만드는 경로가 없으므로, CUDA node가 있는 graph도
`NetworkGraph` 생성 시 `"cpu"`를 전달받는다.

결과적으로 이 PR이 `CudaContext`에 설치한 `CudaMemAllocator`가 실제
weight/activation pool에 사용되지 않는다. CUDA layer의 context는
선택되어도 tensor는 일반 host allocator에서 만들어지므로 device-residency
경로가 비활성화되거나 후속 CUDA 연산이 host pointer를 device pointer로
취급해 실패한다.

기존 자동 리뷰의 같은 지적은 현재 헤드에서도 수정되지 않았다. CUDA
node를 우선 확인하고 해당 graph의 pool을 `cuda` context allocator에
연결해야 한다.

### P1 — 선택한 CUDA context를 worker thread에서 다시 current로 만들지 않음

위치:

- `nntrainer/cuda/cuda_context_manager.cpp:117-129`
- `nntrainer/cuda_mem_allocator.cpp:78-203`
- `nntrainer/cuda/cuda_buffer.cpp:32-84`
- `nntrainer/cuda/cuda_stream_manager.cpp:30-49`
- `nntrainer/cuda/cuda_stream_manager.cpp:69-99`

초기화 thread에서는 `NNTR_CUDA_DEVICE`로 고른 primary context를 current로
만들지만, allocator의 `alloc/free`, buffer copy/release, stream copy/sync
같은 public 연산은 호출 thread에서 `EnsureCurrent()`를 실행하지 않는다.
CUDA current device/context는 host thread별 상태다.

따라서 model 준비나 inference가 다른 thread로 이동하면 기본 device 0에
allocation이 생길 수 있다. 특히 `NNTR_CUDA_DEVICE=N`으로 0이 아닌 GPU를
고른 경우, device N에서 만든 stream을 다른 current device에서 사용해
`cudaErrorInvalidResourceHandle`이 발생하거나 엉뚱한 GPU에 메모리를
할당한다.

각 public CUDA 연산과 destructor에서 소유 context를 current로 만들고
결과를 확인해야 한다.

### P1 — stream 동기화 시 비동기 CUDA 오류를 버림

위치:

- `nntrainer/cuda/cuda_stream_manager.cpp:69-99`

`finish()`는 `cudaStreamSynchronize()`와 선택적인
`cudaDeviceSynchronize()`의 반환값을 확인하지 않는다. illegal memory
access나 비동기 launch 오류는 enqueue 시점이 아니라 synchronize에서
처음 드러나는 경우가 많다.

현재는 이 오류를 정상 완료로 처리해 caller가 stale/부분 출력값을 계속
사용할 수 있다. 동기화 실패를 `cudaCheck`로 확인하고 inference 실패로
전달할 수 있는 status 또는 exception contract가 필요하다.

### P1 — 설명에 포함된 `lm_head`와 `qkv_layer` factory가 CUDA context에 없음

위치:

- `nntrainer/cuda_context.cpp:94-125`
- `nntrainer/app_context.cpp:462-471`
- `Applications/CausalLM/models/causal_lm.cpp:229`

PR 설명은 CUDA context에 `qkv`와 `lm_head`도 등록한다고 되어 있지만,
`CudaContext::add_default_object()`는 FC, addition, GeGLU, SwiGLU,
logit-softcapping, scalar, tied-embedding만 등록한다. `QKVLayer`와
`LmHeadLayer`는 CPU `AppContext`에만 등록되어 있다.

따라서 untied embedding을 사용하는 CausalLM graph가 `engine=cuda`로
`lm_head`를 만들면 factory lookup 단계에서 실패한다. 두 layer를
host-on-UVM fallback으로 지원하려는 설계라면 CUDA context에도 실제로
등록하고 생성 테스트를 추가해야 한다.

### P1 — kernel cache key에서 source가 빠져 다른 kernel을 반환할 수 있음

위치:

- `nntrainer/cuda_context.cpp:170-196`

kernel hot cache key는 `kernel_name + compile_options`뿐이며 source 또는
module identity를 포함하지 않는다. 서로 다른 source가 같은 함수 이름과
option을 내보내면 두 번째 등록은 compile조차 하지 않고 첫 번째
`CUfunction`을 반환한다. delimiter가 없어 이름과 option의 문자열 결합이
우연히 같아지는 경우도 있다.

source/module hash, 함수 이름, 구조화된 option을 모두 포함한 key를
사용해야 한다.

### P1 — 전역 kernel/module cache와 kernel argument binding이 thread-safe하지 않음

위치:

- `nntrainer/cuda_context.h:216-220`
- `nntrainer/cuda_context.cpp:175-205`
- `nntrainer/cuda/cuda_kernel.cpp:32-46`
- `nntrainer/cuda/cuda_stream_manager.cpp:52-66`

두 inline-static `unordered_map`의 find/emplace/indexing에 lock이 없어 여러
model을 동시에 준비하면 container data race가 발생한다. 더 심각하게는
cache가 같은 `Kernel` 객체를 모든 caller에 공유하고,
`SetKernelArguments()`가 그 객체의 `arg_storage_`를 직접 변경한다.

두 inference thread가 같은 kernel을 동시에 bind/launch하면 한 launch가
다른 thread의 pointer나 dimension 일부를 사용할 수 있어 잘못된 결과 또는
GPU out-of-bounds 접근으로 이어진다. 단순히 map lookup만 잠그는 것으로는
부족하며, argument storage를 dispatch별로 분리하거나 argument bind부터
`cuLaunchKernel`까지 원자적으로 보호해야 한다.

## 남은 위험

CUDA toolkit과 NVIDIA GPU가 없어 configure/build/runtime 검증은 하지
못했다. 디스크 cache가 `std::hash`와 POSIX `HOME`에 의존하는 점, 공백이
있는 Windows NVRTC option parsing, `NNTR_CUDA_EAGER_CTX`와
`NNTR_CUDA_EAGER_INIT`의 서로 다른 gate도 추가 점검이 필요하다.
