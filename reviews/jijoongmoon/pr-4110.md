- PR: [nntrainer/nntrainer#4110](https://github.com/nntrainer/nntrainer/pull/4110)

- Verdict: **Request changes — PR 고유 correctness blocker 다수**

## Review summary

이 PR은 #4109 위에 v8c int8×int4 OpenCL kernel, weight/activation cache,
GPU FC whole-op dispatch 및 backend-neutral FC layer를 추가한다. #4109 대비
고유 delta 13개 파일, 약 4.1K 추가 라인을 검토했다.

핵심 경로에는 같은 storage의 내용이 갱신되어도 이전 activation을 재사용하는
cache 오류가 있고, 문서화된 host fallback도 여러 quantized dtype에서 실제로
실행되지 않는다. Windows 기본 weight page discard는 남아 있는 fallback과
양립하지 않으며, bias와 fused activation epilogue도 dtype·dispatch·SVM
동기화 문제가 있다.

## Findings

### P1 — 주소는 같지만 값이 바뀐 입력에 이전 계산을 재사용함

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:529`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1046`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1052`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:1153`
- `nntrainer/layers/fc_layer_cl.cpp:146`
- `nntrainer/layers/fc_layer_cl.cpp:166`
- `nntrainer/models/neuralnet.cpp:1559`
- `nntrainer/tensor/manager.h:126`
- `nntrainer/tensor/optimized_v1_planner.cpp:165`
- `nntrainer/tensor/tensor_pool.cpp:222`

쉽게 말하면 이 cache는 “마지막 FC 입력” 하나를 기억한다. 같은 주소가 다시
들어오면 같은 입력이라고 생각해 양자화를 생략한다. 하지만 activation tensor는
메모리 주소를 유지한 채 안의 숫자만 다음 token 값으로 덮어쓸 수 있다. 이때
코드는 새 값이라는 사실을 모르고 이전 token의 계산 결과를 다시 쓴다.

정확한 cache key는 input data pointer, `M/K/M_pad`, dtype이다. producer,
storage 내용의 변경 횟수, forward/token 번호는 key에 없고 cache를 지우는
코드도 없다. 따라서 직전 v8c FC와 현재 FC의 주소·shape·dtype가 같으면 새
입력의 upload와 activation quantization을 모두 건너뛴다.

이 조건이 매 inference마다 반드시 성립하는 것은 아니다. 큰 graph에서는
중간의 다른 FC miss가 마지막 key를 교체할 수 있다. 하지만 pointer identity는
같은 storage라는 뜻일 뿐 내용이 같다는 뜻이 아니며, 다음과 같은 유효한
실행에서는 결정적으로 잘못된다.

일반적인 Qwen류 transformer에서는 이 문제가 잘 보이지 않을 수 있다. q/k/v와
gate/up은 실제로 같은 입력을 함께 쓰므로 cache hit가 맞고, 그 사이의 다른
FC들이 cache를 새 값으로 바꿔 주기 때문이다. 하지만 이는 특정 FC 실행 순서가
우연히 문제를 피하는 것이다. FC가 하나인 graph, 반복해서 같은 subgraph를
실행하는 graph, 첫 tensor 계산이 끝난 뒤 그 메모리 자리를 다른 tensor에
다시 배정하는 graph에는 안전 장치가 없다.

1. 입력 A로 QS4CX FC를 실행해 quant 결과를 cache한다.
2. producer가 같은 Tensor storage를 입력 B로 덮어쓴다.
3. 같은 shape/dtype의 QS4CX FC를 다시 실행한다.
4. 주소가 같아 cache hit가 되고, B를 읽지 않은 채 A의
   `act_i8/scale/zp/row_sum`으로 GEMM한다.

특히 incremental forwarding은 token마다 같은 pool과 offset 0의 shared view를
재사용한다. eligible QS4CX FC가 하나인 graph라면 두 번째 token부터 위 조건이
그대로 성립한다. 이것이 이 finding의 가장 직접적인 재현 경로다.

메모리 자리 재사용 자체는 nntrainer에서 흔한 정상 최적화다. 기본으로 켜진
`OptimizedV1Planner`는 사용이 끝난 tensor와 새 tensor의 크기가 같으면 같은
offset을 명시적으로 배정하고, `TensorPool`은 그 offset을 실제 주소로 연결한다.
따라서 서로 다른 값이 같은 주소를 쓰는 상황은 코드상 가능하다. 다만 이 때문에
false hit까지 나려면 다음 v8c FC의 shape/dtype도 같고, 그 사이 다른 FC miss가
cache key를 바꾸지 않아야 한다. 대표 Qwen graph에서 이 조합이 자주 생긴다는
실측 근거는 없으므로, planner reuse는 확정적인 빈도 주장이 아니라 추가 가능
경로로 본다. 일반 inference에서 allocator가 같은 주소를 다시 내주는 경우도
동일하게 가능하지만 결정적인 주 근거로 삼지 않는다.

구체적으로는 다음처럼 생길 수 있다. FP16 `[1, 4096]` 크기의 `X`가 v8c
FC-A에 들어가면 `X`의 양자화 결과가 cache에 남는다. FC-A가 `X`를 다 쓴 뒤,
LayerNorm이나 ReLU 같은 일반 연산이 같은 크기의 `Y`를 만든다고 하자.
메모리 배치기는 수명이 끝난 `X`의 자리를 `Y`에게 줄 수 있다. 이어서 `Y`가
v8c FC-B에 들어가면 주소, `M`, `K`, dtype이 모두 이전 `X`와 같다. 그 사이
다른 v8c FC가 cache를 바꾸지 않았다면 FC-B는 `Y`를 새로 읽지 않고 `X`의
양자화 결과를 사용한다.

주차장에 비유하면, `X`가 7번 칸에서 나간 뒤 같은 크기의 `Y`가 그 칸에
주차한 상황이다. 현재 cache는 차량 번호가 아니라 “주차 칸 번호와 차 크기”만
확인하므로 새 차 `Y`를 예전 차 `X`로 착각한다. nntrainer의 memory planner
단위 테스트도 사용 시간이 겹치지 않는 tensor들이 같은 offset을 공유하는 것을
정상 동작으로 확인한다. 여기서 “곧바로”란 두 FC가 코드상 바로 붙어 있어야
한다는 뜻이 아니라, 둘 사이에 cache key를 교체하는 다른 v8c FC miss가 없어야
한다는 뜻이다.

mutex는 호출을 직렬화할 뿐 storage freshness를 만들지 않으므로 이 문제를
해결하지 않는다. cache를 명시적인 fanout group 범위로 제한하거나
producer/content generation을 key에 넣고, token/forward 경계와 storage
mutation 때 invalidate해야 한다. 같은 storage에 서로 다른 A/B를 연속으로
넣고 두 번째 결과를 cache-off reference와 비교하는 회귀 테스트가 필수다.

### P1 — v8c 거부 후 “host fallback”이 같은 OpenCL op table에서 예외를 냄

위치:

- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:93`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:108`
- `nntrainer/tensor/float_tensor.cpp:956`
- `nntrainer/tensor/float_tensor.cpp:991`
- `nntrainer/tensor/float_tensor.cpp:1003`

`dotCl_v8c()`가 dtype/shape/env/runtime 오류로 `false`를 반환하면
`ClComputeOps::fc()`는 quantized weight에 `input.dot()`을 호출한다. 하지만
input은 여전히 `ClComputeOps`를 가진다. `Q4_K`와 `Q6_K`의
`gemm_q4_K_fp32()`/`gemm_q6_K_fp32()`, 그리고 `M=1` Q4_0의
`gemm_q4_0_fp32()`는 `ClComputeOps`가 override하지 않아 base
`ComputeOps`의 not-implemented 예외로 끝난다.

즉 지원하지 않는 shape/dtype을 CPU로 안전하게 내린다는 주석과 달리,
FP32 activation을 쓰는 Q4_0 decode와 Q4_K/Q6_K GPU FC가 실패할 수 있다.
명시적으로 CPU op table에 dispatch하거나 모든 fallback dtype을 OpenCL에서
구현해야 한다. v8c disabled/rejected 상태의 각 quantized dtype과
`M=1/M>1` 테스트가 필요하다.

### P1 — Windows 기본 page discard 후에도 host fallback이 남아 있음

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:734`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:746`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:762`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:108`

x86 Windows에서는 `NNTR_V8C_DROP_PLAIN`이 기본 ON이며, device weight
prebuild 뒤 `DiscardVirtualMemory()`로 원본 QS4CX nibble/scale page를
버린다. 성공한 page는 다시 읽을 때 zero가 된다. 그러나 같은 PR은
`dotCl_v8c()`의 kernel/image/SVM/scratch 실패를 `false`로 반환하고
`input.dot(weight, ...)` host fallback으로 처리한다.

따라서 prebuild 뒤 런타임 OpenCL 경로가 한 번이라도 거부되면 fallback은
원본 weight가 아니라 버려진 zero page를 읽어 corrupt/zero 출력을 낸다.
host fallback이 가능한 동안 원본을 버리면 안 되며, 복구 가능한 copy를
유지하거나 device backing으로 완결되는 별도 fallback이 필요하다. Windows
에서 prebuild 성공 후 의도적으로 kernel 생성/할당을 실패시키는 테스트가
필요하다.

### P1 — resident output을 async read-map한 직후 host epilogue가 접근함

위치:

- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:887`
- `nntrainer/tensor/cl_operations/blas_kernel_interface.cpp:911`
- `nntrainer/layers/fc_layer_cl.cpp:131`
- `nntrainer/layers/fc_layer_cl.cpp:141`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:140`

v8c resident-output helper는 GPU copy/convert를 enqueue한 뒤 output SVM을
`CL_MAP_READ`로 nonblocking map하고 곧바로 반환한다. 그 직후 FC layer는
bias add를 시도하고, fused activation이 있으면 host `ActiFunc`로 같은
포인터를 읽고 쓴다.

coarse-grain SVM에서는 map 완료 전 host 접근 자체가 잘못이고, fine-grain
SVM에서도 앞선 kernel 완료를 기다리지 않아 stale/partial output을 볼 수
있다. `NNTR_FC_SVM_SYNC=1`로 blocking을 강제해도 map flag가
`CL_MAP_READ`이므로 host epilogue의 쓰기는 access mode 위반이다.

epilogue를 같은 OpenCL queue의 kernel로 수행하거나, host 접근 전에
read-write blocking map/event wait를 보장해야 한다. 최종 output 또는
mixed CPU/GPU graph처럼 “다음 consumer는 항상 GPU”가 아닌 경로도
테스트해야 한다.

### P1 — quantized bias의 dtype과 add dispatch가 모두 잘못됨

위치:

- `nntrainer/layers/fc_layer_cl.cpp:87`
- `nntrainer/layers/fc_layer_cl.cpp:102`
- `nntrainer/layers/fc_layer_cl.cpp:131`
- `nntrainer/tensor/cl_operations/cl_compute_ops.cpp:41`
- `nntrainer/tensor/tensor.cpp:665`

GPU FC는 bias를 weight와 같은 dtype으로 요청한다. 따라서 QS4CX/QINT4/Q4
weight에서는 serialized FP bias까지 quantized dtype으로 해석한다. 일반
CPU FC가 quantized weight의 bias를 FP32로 유지하는 규칙과도 다르다.

게다가 `hidden_.add_i(bias)`는 output의 `ClComputeOps::ele_add_*()`를
호출하지만 이 class는 해당 op를 구현하지 않는다. base 구현의 예외는
`Tensor::add_i()`에서 error code로 바뀌고, FC layer가 반환값을 무시하므로
같은 dtype인 경우조차 bias가 조용히 빠질 수 있다.

CPU FC와 같은 bias dtype 규칙을 사용하고, 지원되는 GPU/host epilogue를
명시적으로 dispatch한 뒤 오류를 확인해야 한다. 현재 LLM projection의
`disable_bias=true`가 이 문제를 가리고 있다.

## Residual risk

로컬 OpenCL hardware 실행과 전체 빌드는 반복하지 않았다. pointer+shape만
쓰는 process-global weight cache도 model unload/reload 시 같은 주소가
재사용되면 이전 model weight를 반환할 수 있다. 또한 `NNTR_FC_BUF=1`은
buffer kernel을 고르면서 caller 쪽 handle 선택은 image path로 남아 있고,
profiling/static scratch object의 multi-thread/model lifetime도 별도 검증이
필요하다.
