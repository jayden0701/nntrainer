# PR #4109 review

- PR: [nntrainer/nntrainer#4109](https://github.com/nntrainer/nntrainer/pull/4109)
- Title: `[opencl] Rework the OpenCL infrastructure: SVM allocator pool, device probe, in-order queue`
- Author: `jijoongmoon`
- Reviewed head: `38977cfffafc4178d61f90e5ca8e5053ec014fef`
- Review date: 2026-07-28
- Verdict: **Request changes — PR 고유 finding 3건 + dependency blockers**

## Review summary

이 PR은 GPU graph의 기본 activation allocator를 OpenCL SVM으로 바꾸고,
in-order queue, capability probe, program cache, profiling 및 향후 `cl_mem`
residency를 위한 pool/view 기반을 추가한다. PR #4106 대비 고유 delta 36개
파일을 검토했다.

가장 큰 문제는 SVM 할당 실패 시 ordinary host memory로 fallback하면서도
그 allocation을 계속 SVM으로 표시한다는 점이다. 이는 이번 PR이 GPU graph를
해당 allocator로 기본 라우팅하면서 정상 실행 경로에 들어온다. 또한 opt-in
`ClBufferPool`은 서로 다른 planner offset을 같은 정렬 key로 합칠 수 있고,
재초기화 시 allocator factory를 우회한다.

## Findings

### P1 — SVM 실패의 host fallback을 SVM 포인터로 표시함

위치:

- `nntrainer/models/neuralnet.cpp:237`
- `nntrainer/cl_svm_allocator.cpp:58`
- `nntrainer/cl_svm_allocator.h:74`
- `nntrainer/tensor/memory_pool.cpp:248`

이번 PR은 GPU node가 하나라도 있는 graph에 `ClSVMAllocator`를 기본
activation allocator로 선택한다. 그런데 `clSVMAlloc()`이 실패하면
`ClSVMAllocator::alloc()`은 `MemAllocator::alloc()`으로 ordinary aligned
host memory를 반환한다. 그럼에도 allocator 단위 capability인
`isDeviceVisible()`은 항상 `true`이고, `MemoryPool::getMemory()`는 모든
allocation에 `setSVM(true)`를 기록한다.

따라서 SVM을 지원하지 않는 OpenCL 1.2/NVIDIA 장치나 SVM 용량이 소진된
경우, CPU fallback으로 안전하게 내려가는 대신 malloc 포인터가
`clSetKernelArgSVMPointer()` 또는 SVM map/unmap 경로에 전달된다. 결과는
`CL_INVALID_VALUE`/`CL_INVALID_ARG_VALUE`, kernel 실패 또는 잘못된 출력이다.
특히 큰 단일 activation plane의 SVM 할당 실패는 실제로 가능한 경로다.

allocation 결과가 SVM인지 포인터별로 보존하여 `MemoryData`에 기록하거나,
SVM 실패를 hard failure로 처리한 뒤 명시적인 host staging 경로로
전환해야 한다. 최소한 `CL_DEVICE_SVM_CAPABILITIES=0`과 강제 allocation
failure 회귀 테스트가 필요하다.

### P2 — 정렬한 offset이 서로 다른 planner allocation의 cl_mem identity를 합침

위치:

- `nntrainer/tensor/cl_operations/cl_buffer_pool.cpp:78`
- `nntrainer/tensor/cl_operations/cl_buffer_pool.cpp:85`
- `nntrainer/tensor/cl_operations/cl_buffer_pool.cpp:126`
- `nntrainer/tensor/cl_operations/cl_buffer_pool.cpp:218`

`ClBufferPool::allocate()`는 각 planner offset을 위쪽으로 정렬한
`padded_offset`으로 변환하고, 그 값을 `offset_maxsize_`와 `offset_sub_`의
유일 key로 사용한다. 서로 **같은 raw offset**을 재사용한 tensor만 같은
allocation identity로 취급해야 하지만, 서로 다른 offset이 같은 alignment
bucket으로 반올림되는 경우까지 합쳐진다.

구체적으로 alignment가 128이고 동시에 살아 있는 tensor의 크기가
32, 64, 32 byte라면 `BasicPlanner`는 서로 겹치지 않는 범위에 raw offset
`0, 32, 96`을 배치한다. 현재 식은 이를 `0, 128, 128`로 바꾼다. 따라서
원래 범위 `[32,96)`와 `[96,128)`는 유효하게 인접해 있는데도 뒤의 두
tensor가 `offset_sub_[128]` 하나를 공유한다. `OptimizedV1/V2/V3`도
offset을 device alignment 단위로 맞춘다는 계약이 없고, `TensorPool`은
tensor의 정확한 byte 수를 그대로 planner에 넘기므로 planner가 이 충돌을
막아주지 않는다.

현재 PR에서는 `device_mem` handle을 stamp만 하고 이를 실제 residency로
bind하는 consumer가 아직 inert이다. 따라서 #4109 단독의 정상 실행에서
즉시 data corruption이 발생한다고 보기는 어렵다. 그러나 후속 변경이 두
tensor를 `GPU_CLMEM`으로 분류하는 순간 두 producer가 같은 `cl_mem`의
0번 byte부터 쓰게 되어 active correctness bug가 된다. 이 이유로 심각도를
즉시 실행 장애인 P1이 아니라 후속 residency 활성화를 막는 P2로 분류한다.

현재 구현은 key마다 독립 `clCreateBuffer()`를 만들며 sub-buffer를 만들지
않는다. 독립 buffer의 base alignment는 OpenCL runtime이 보장하므로
`padded_offset`이 필요하지 않다. 이 구조에서는 raw planner offset을
identity key로 유지하면 된다. 향후 단일 parent buffer의 sub-buffer로
바꾼다면 각 raw allocation을 별도의 정렬된 위치에 다시 pack해야 하며,
raw offset을 개별적으로 round-up하는 것만으로는 충돌을 막을 수 없다.
동시에 살아 있는 `0, 32, 96` 예제를 포함한 회귀 테스트가 필요하다.

### P2 — `reinitialize()`가 backend pool factory를 우회함

위치:

- `nntrainer/tensor/tensor_pool.h:58`
- `nntrainer/tensor/tensor_pool.h:88`
- `nntrainer/tensor/tensor_pool.h:99`

일반 생성자는 새 `allocator_->makePool()` virtual을 호출하므로
`NNTR_GPU_CLMEM_POOL=1`이면 `ClBufferPool`을 얻는다. 반면
`TensorPool::reinitialize()`와 `setAllocator()`는 여전히
`std::make_shared<MemoryPool>(allocator_)`를 직접 호출한다.

그 결과 같은 graph를 reinitialize하면 allocator는 유지되지만 pool 종류는
조용히 plain SVM `MemoryPool`로 바뀌며, 이후 tensor에는 `device_mem`이
stamp되지 않는다. `fsu_name`도 factory 재호출을 위해 보존되지 않는다.
모든 pool 생성 지점이 `makePool()`을 사용하도록 통일하고,
reinitialize 전후 concrete pool/capability가 유지되는지 테스트해야 한다.

## Residual risk

로컬 OpenCL hardware 실행과 전체 빌드는 반복하지 않았다. CI는
SVM 미지원/할당 실패 장치, 서로 다른 offset의 alignment collision,
`NNTR_GPU_CLMEM_POOL=1` 상태의 graph reinitialize를 다루지 않는다.
profiling event의 process-global 수명과 coarse-grain SVM host coherence도
추가 hardware 검증이 필요하다.
