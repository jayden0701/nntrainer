## 요약

이 PR은 decode 한 번의 CUDA 작업을 graph로 캡처한 뒤 다음 token부터
재생해 C++ layer walk와 kernel launch 비용을 줄이려는 변경이다. 직접 부모
#4124 대비 고유 diff는 5개 파일, 343줄 추가와 2줄 삭제다.

현재 단독 PR에서는 M2-B 재생에 필요한 token 위치가 어떤 CUDA kernel에도
연결되지 않는다. PR 설명도 후속 app-side kernel이 있어야 전체 correctness가
성립한다고 밝히지만, core의 `NNTR_CUDA_M2B=1` 경로는 지금 바로 활성화할
수 있고 성공한 것처럼 동작한다.

그보다 넓은 문제도 있다. CUDA graph에는 GPU 작업만 기록되는데 현재 CUDA
모델에는 CPU fallback과 host layer가 남아 있다. 캡처 중에는 이 host 연산이
아직 실행되지 않은 GPU 결과를 읽고, 재생 때는 아예 다시 실행되지 않는다.
graph cache는 모델별이 아닌 프로세스 전역이고, embedding-only 실행을
만들려는 skip flag도 실제로 읽는 코드가 없다. CUDA launch 실패까지
성공으로 처리하므로 현 상태로는 opt-in이라도 안전하게 사용할 수 없다.

## 발견 사항

### P1 — 후속 token 위치를 쓰지만 이를 읽는 kernel이 하나도 없음

위치:

- `nntrainer/cuda_context.cpp:303-334`
- `nntrainer/cuda/cuda_stream_manager.cpp:209-234`

두 번째 token부터 바뀌는 graph 입력은
`cuda_set_pos(from, from + 1)`뿐이다. 이 함수는 두 정수를
`cuda_pos_buffer()`로 복사한다. 그러나 현재 PR 헤드 전체를 검색하면
`cuda_pos_buffer()`를 읽거나 그 주소를 kernel 인자로 전달하는 소비자가
없다. 정의부와 `cuda_set_pos()` 내부 호출만 존재한다.

따라서 캡처된 graph node에는 첫 token에서 사용한 `from`과 KV 길이가
그대로 남는다. 이후 token도 같은 KV cache slot과 attention 범위를 사용할
수 있어 출력이 결정적으로 틀어진다. PR 설명에 적힌 app-side
per-layer-slice, argmax, scalar-multiply 변경이 아직 없다는 사실과도
일치한다.

후속 소비자가 실제로 연결될 때까지 `NNTR_CUDA_M2B`를 성공 경로로
노출하지 않거나, 필요한 kernel node parameter를 이 PR에서 직접 갱신해야
한다. 최소한 position buffer 소비자가 없으면 명확한 오류나 eager
fallback으로 돌아가야 한다.

### P1 — host fallback은 graph에 기록되지 않아 첫 capture부터 stale 값을 굳힘

위치:

- `nntrainer/cuda_context.cpp:114-144`
- `nntrainer/cuda_context.cpp:337-361`
- `nntrainer/cuda_context.cpp:396-418`
- `nntrainer/cuda/cuda_stream_manager.cpp:82-91`
- `nntrainer/cuda/cuda_stream_manager.cpp:168-177`
- `nntrainer/cuda/cuda_compute_ops.cpp:217-220`

stream capture 중 CUDA kernel은 실행되는 대신 graph에 기록된다. 그런데
`StreamManager::finish()`와 `finishIfAsync()`는 `capturing_`이 true이면
동기화를 생략하고 즉시 반환한다. 그 상태에서 FC fast path가 실패해 host
dot으로 내려가거나 `AdditionLayer` 같은 CPU layer가 실행되면, 아직
실행되지 않은 앞 GPU kernel의 이전 값을 host가 읽게 된다.

더 큰 문제는 host 계산 자체가 CUDA graph node가 아니라는 점이다. 예를
들어 `CUDA FC -> residual addition -> CUDA FC` 순서를 캡처하면 두 FC만
재생되고 중간 addition은 캡처 시점의 stale 입력으로 한 번 계산된 채
고정된다. 실제 CausalLM 모델은 residual addition을 사용하며, CUDA
context도 `AdditionLayer`를 CPU 구현으로 등록한다.

현재 opt-in audit 로그는 이 상황을 진단할 뿐 capture를 실패시키지 않는다.
capture 중 host fallback이 한 번이라도 발생하면 해당 graph를 폐기하고
eager로 다시 실행하거나, 모든 중간 연산이 CUDA graph node임을 보장한
실행 계획에서만 capture를 허용해야 한다. M1 decode, M2-B, prefill graph가
모두 영향을 받는다.

### P1 — graph cache가 모든 모델에 공유되어 다른 모델의 graph를 재생함

위치:

- `nntrainer/cuda_context.cpp:284-310`

`_cg_cached_exec`와 `_cg_cached_out`은 `runDecode()`의 함수 정적 변수다.
모델 identity, tensor 주소, weight 주소, shape 정보 없이 모든
`NeuralNetwork` 인스턴스가 하나를 공유한다.

스레드 없이도 다음 순서로 잘못된다.

1. 모델 A가 prefill과 첫 decode를 수행해 A의 graph를 저장한다.
2. 모델 B의 `from == 0` 호출이 전역 A graph를 제거한다.
3. 모델 B의 첫 decode가 B graph와 B output을 전역 변수에 저장한다.
4. 모델 A의 다음 decode가 B graph를 실행하고 B output vector를 반환한다.

동시에 호출하면 정적 변수 자체의 data race와 실행 중 graph 파괴까지
추가된다. NVIDIA도 CUDA graph object는 thread-safe하지 않다고
[명시한다](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__GRAPH.html).

cache는 `NeuralNetwork` 또는 sequence별 소유 상태여야 한다. 새 sequence,
tensor 재할당, shape 변경과 모델 소멸 때 해당 모델의 exec만 무효화하고,
재생 전에 owner와 주소 계약을 확인해야 한다.

### P1 — M2-B skip flag가 write-only라 eager forward와 graph를 모두 실행함

위치:

- `nntrainer/cuda_context.cpp:316-336`
- `nntrainer/models/neuralnet.cpp:529-536`

후속 token의 non-light 경로는 다음 순서다.

1. `setM2BSkipAll(true)`
2. `nn.incremental_forwarding(...)`
3. `setM2BSkipAll(false)`
4. `cudaGraphLaunch(...)`

하지만 `g_m2b_skip_all`은 선언되고 setter에서 대입될 뿐 저장소 어디에서도
읽히지 않는다. 따라서 두 번째 단계는 embedding-only refresh가 아니라
전체 layer walk와 eager forward를 그대로 수행한다. 그 뒤 cached graph를
다시 실행하므로 CPU dispatch 제거라는 성능 목적을 달성하지 못하고,
KV cache나 sampling처럼 상태가 있는 연산을 token마다 두 번 적용할 수
있다.

이 문제는 GitHub 자동 리뷰가 이전 head에서도 지적했으며 현재
`c1fa0171`에서도 그대로 재확인됐다. flag를 process-global 변수가 아니라
모델 인스턴스 상태로 옮기고 forwarding loop가 실제로 읽게 해야 한다.
더 안전하게는 embedding node만 명시적으로 실행하고 나머지 graph walk를
호출하지 않는 구조가 낫다.

### P1 — graph launch와 비동기 실행 오류를 무시하고 stale 출력을 정상 반환함

위치:

- `nntrainer/cuda_context.cpp:332-336`
- `nntrainer/cuda_context.cpp:357-361`
- `nntrainer/cuda_context.cpp:389-418`
- `nntrainer/cuda_context.cpp:477-481`

모든 실행 분기에서 `cudaGraphLaunch()`와
`cudaStreamSynchronize()` 반환값을 버린 뒤
`cuda_graph_captured = true`로 설정한다. illegal memory access 같은
비동기 kernel 오류는 synchronize에서 처음 드러날 수 있는데, 이 경우에도
eager fallback을 막고 `_cg_cached_out` 또는 계산되지 않은 `out`을 정상
token처럼 반환한다.

두 API가 모두 성공한 경우에만 capture 성공 상태로 전이해야 한다. 실패하면
cached exec와 output을 무효화하고, 안전하게 재실행할 수 있는 오류인지
판단해 eager fallback하거나 호출자에게 오류를 전달해야 한다.
`cuda_set_pos()`의 allocation과 copy 실패도 같은 방식으로 전달할 필요가
있다.

### P2 — layer 예외가 발생하면 stream이 영구 capture 상태에 남음

위치:

- `nntrainer/cuda_context.cpp:337-367`
- `nntrainer/cuda_context.cpp:396-430`
- `nntrainer/cuda_context.cpp:464-490`
- `nntrainer/cuda/cuda_stream_manager.cpp:183-199`

`beginCapture()` 성공 뒤 `nn.incremental_forwarding()`이 예외를 던지면
`endCapture()`까지 도달하지 않는다. `capturing_`은 계속 true이고 실제
CUDA stream capture도 종료되지 않는다. 이후 `finish()`와
`finishIfAsync()`는 계속 no-op이며 다음 capture도 실패하므로 한 번의
shape·allocation·layer 오류가 CUDA backend 전체를 망가뜨린다.

capture 세션을 RAII scope로 만들고 정상 반환과 예외 양쪽에서 반드시
종료 또는 abort해야 한다. 예외 뒤에는 invalidated graph와 sticky CUDA
오류도 정리해야 한다.

## 추가 계약 문제

`setPrefillCaptureDisabled()`는 “load-time warmup을 eager로 실행해 scratch를
먼저 키운다”고 설명하지만 현재 헤드에는 이 setter의 호출자가 없다.
반면 `NNTR_CUDA_GRAPH=1`이면 integrated GPU에서 prefill graph가 기본으로
활성화된다. PR 본문의 “decode-speed path only, prefill을 건드리지 않는다”는
설명과 실제 동작도 맞지 않는다.

Orin warmup에서 이 flag를 실제로 설정·해제하는 호출부를 같은 변경에
넣거나, 호출자가 들어오기 전까지 prefill capture를 기본 활성화하지 않는
편이 안전하다.

## 정상으로 확인한 부분

- graph 관련 환경 변수가 모두 없으면 마지막의 일반
  `incremental_forwarding()` 한 번만 실행한다.
- `NNTR_CUDA_M2B`는 값이 `1`일 때만 활성화되어 `=0`을 on으로 오인하지
  않는다.
- sequence의 `from == 0`에서 기존 M2-B exec를 파괴하려는 초기화 분기는
  존재한다.
- capture가 정상적으로 끝난 뒤 원본 `cudaGraph_t`를 파괴하는 수명 순서는
  맞다.
- 직접 부모 대비 `git diff --check`를 통과했다.

## 테스트 공백
