## 요약

이 PR은 device-only activation과 관련된 FP32/FP16 copy를
`cudaMemcpyAsync`로 보내고, dtype 변환은 host 임시 버퍼를 거치도록
`CudaComputeOps`를 확장한다. 직접 부모 #4120 대비 고유 변경은
`cuda_compute_ops.cpp` 한 파일, 134줄 추가와 10줄 삭제다.

연속 same-dtype copy의 byte 수와 `cudaMemcpyDefault` 방향 판별은 맞다.
하지만 표준 concat/split이 만드는 mapped tensor는 CUDA context를
잃으므로 새 override 자체에 도달하지 않는다. 도달하는 경로에서도
변환 copy 실패와 D2H 완료 오류를 정상 성공으로 숨긴다. CUDA graph
capture 중에는 아직 실행되지 않은 D2H 값을 host가 읽거나 동기 copy가
capture를 무효화한다.

## 발견 사항

### P1 — concat/split의 mapped tensor가 CUDA copy override를 우회함

위치:

- `nntrainer/tensor/tensor.h:526-541`
- `nntrainer/layers/concat_layer.cpp:154-188`
- `nntrainer/layers/split_layer.cpp:107-132`
- `nntrainer/tensor/tensor_base.cpp:17-23`
- `nntrainer/cuda/cuda_compute_ops.cpp:50-90`

`Tensor::Map()`은 기존 buffer를 가리키는 새 tensor를 만들지만 원본의
`ContextData`를 전파하지 않는다. concat과 split은 CUDA input/output의
부분 영역을 `Tensor::Map()`으로 감싼 다음 `dest_tensor.copy()`를
호출한다.

mapped destination에는 CUDA context가 없으므로 `getOps()`는 global CPU
table을 반환한다. 결국 새 `CudaComputeOps::device_copy()`에 도달하지
않고 CPU loop가 `cudaMalloc` pointer를 직접 읽고 써 fault한다. 이는
외부 CPU tensor가 CUDA device-only tensor를 `copyData()`로 받을 때도
같다. copy dispatch가 destination의 context만 보기 때문이다.

mapped view에 원본 context를 전파하거나, backend migration/copy 계층에서
양쪽 pointer의 residency를 보고 copy 구현을 선택해야 한다.

### P1 — dtype 변환 전송 실패를 무시해 0 또는 이전 output을 반환

위치:

- `nntrainer/cuda/cuda_compute_ops.cpp:94-121`
- `nntrainer/cuda/cuda_compute_ops.cpp:126-153`
- `nntrainer/cuda/cuda_context_manager.cpp:281-289`

FP32→FP16과 FP16→FP32 경로는 D2H와 H2D에 사용하는
`cuda::copy_any()`의 `bool` 반환값을 네 군데 모두 무시한다.

device input의 D2H가 실패하면 value-initialize된 `xs`를 정상 입력처럼
변환해 0에 가까운 값을 destination에 쓴다. device output의 H2D가
실패하면 output이 갱신되지 않았는데도 함수가 성공 반환해 이전
activation이 남는다.

same-dtype D2H도 enqueue 결과만 검사한다. 뒤의 `sm.finish()`는 내부
`cudaStreamSynchronize()` 결과를 반환하거나 검사하지 않아 producer
kernel 또는 실제 copy의 실행 오류를 숨긴다. 모든 transfer와 host
소비 경계의 sync 오류를 예외 또는 호출자에게 전달해야 한다.

### P1 — graph capture 중 D2H가 실행되기 전에 host가 값을 소비함

위치:

- `nntrainer/cuda/cuda_compute_ops.cpp:59-73`
- `nntrainer/cuda/cuda_compute_ops.cpp:101-120`
- `nntrainer/cuda/cuda_compute_ops.cpp:133-152`
- `nntrainer/cuda/cuda_stream_manager.cpp:69-79`

capture 중 `cudaMemcpyAsync`는 copy를 즉시 실행하지 않고 graph node로
기록한다. 그런데 host destination인 경우 호출하는 `sm.finish()`는
`capturing_`일 때 의도적으로 아무 동기화도 하지 않는다.
`device_copy()`는 그 상태에서도 성공 반환하므로 호출자는 replay 전의
stale 또는 미초기화 destination을 즉시 읽는다.

dtype 변환은 더 직접적으로 capture를 깨뜨린다. `finish()`가 no-op인
상태에서 `copy_any()`의 동기 `cudaMemcpy`와 CPU 변환을 실행한다. 이
copy는 backend stream의 graph node가 아니며 active capture와 충돌해
capture invalidation/error를 낼 수 있다. 현재 코드는 audit log만 찍고
계속하며 전송 오류까지 무시한다.

capture 중 host-consumed copy를 명시적으로 거부하거나 capture 밖으로
이동해야 한다. 변환을 capture하려면 device kernel과 수명이 보장된
staging을 사용해야 한다.

### P2 — H2D copy가 host source 수명을 보장하지 않고 반환

위치:

- `nntrainer/cuda/cuda_compute_ops.cpp:50-73`
- `nntrainer/tensor/float_tensor.cpp:1603-1612`
- `nntrainer/tensor/half_tensor.cpp:1189-1198`

destination `Y`가 device-only이면 함수는 sync 모드에서도
`cudaMemcpyAsync`를 enqueue한 직후 반환한다. 다음 CUDA consumer는 같은
stream에서 순서가 보장되지만 host source `X`의 수명은 보장되지 않는다.

`Tensor::copy(const void *buf)`의 기존 CPU 구현은 반환 시 copy가 끝나지만,
새 H2D 경로에는 completion event나 source 보존 계약이 없다. `X`가
pinned/mapped host buffer이면 실제 DMA가 남아 있는 동안 호출자가
buffer를 수정·재사용·해제해 device 결과가 오염될 수 있다.

D2D만 비동기로 유지하고 host-source H2D는 완료를 기다리거나, 소유권이
있는 persistent staging과 명시적인 completion 계약을 제공해야 한다.

## 의존 PR에서 이어지는 문제

allocator routing 문제 때문에 현재 CUDA graph에 연결되지 않을 수 있다.
또한 #4119의 output residency와 CPU fallback 문제도 그대로 포함한다.

## 남은 위험

고유 변경에는 copy 단위 test가 없다. PR 본문의 재현 명령도
`-Denable-fp16=false`라 새 FP16 및 mixed-dtype 변환 코드를 컴파일·실행하지
않는다. CUDA toolkit/GPU가 없어 runtime 검증을 하지 못했으므로
FP32/FP16 각 방향, mapped view, transfer failure, pinned host source,
graph capture를 포함한 test가 필요하다.

device-only pointer의 strided copy도 공개 `scopy` 계약과 달리 즉시
예외를 던진다. 현재 저장소의 직접 호출은 대부분 stride 1이지만,
일반 view API까지 지원 범위를 명확히 해야 한다.
