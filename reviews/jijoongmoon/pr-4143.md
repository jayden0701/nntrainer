## 한눈에 보기

RMSNorm 계산은 각 행의 값이 너무 커지지 않도록 크기를 맞추는 작업이다.
이번 PR은 FP16 값끼리 제곱할 때 숫자 범위를 넘는 문제를 피하려고, 합계만 FP32로
계산하는 CUDA 경로를 추가한다. 이 방향과 커널의 기본 수식은 맞다.

그러나 계산기에 들어갈 gamma 가중치를 잘못된 자료형으로 예약한다. 또한 GPU만 읽을 수
있는 메모리를 선택한 경우에도 일부 입력을 CPU 반복문으로 보낸다. 계산기 자체는
정확해도 재료를 잘못 읽거나 접근할 수 없는 창고 주소를 주면 결과가 나올 수 없는
상태다.

## 발견 사항

### P1 — FP16 모델에서 FP32 gamma 가중치를 FP16으로 잘못 읽음

위치:

- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:35-42`
- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:79-91`
- 비교 기준 `Applications/CausalLM/layers/rms_norm.cpp:31-41`
- `nntrainer/layers/layer_node.cpp:691-696`

새 레이어는 gamma의 자료형을 다음처럼 모델의 일반 weight 자료형에서 가져온다.

```cpp
TensorDim::TensorType(context.getFormat(), context.getWeightDataType())
```

CausalLM의 보통 `rms_norm`은 `packed=false`를 사용한다. 이 경우 LayerNode는 해당
레이어의 weight 자료형을 activation 자료형과 같게 만든다. 따라서 FP16 activation을
사용하면 gamma도 FP16으로 선언된다.

하지만 CausalLM 모델 파일의 RMSNorm gamma는 양자화되지 않은 FP32로 저장된다.
직접 부모의 CPU RMSNorm도 바로 이 이유로 gamma를 항상 FP32로 요청한다. 그 주석에는
FP16으로 선언하면 저장된 FP32 바이트를 FP16으로 잘못 해석해 gamma가 망가진다고
명시돼 있다. 이 방어 코드는 작성자가 과거에 직접 추가한 수정이므로 단순한 추측이
아니라 이미 알려진 회귀다.

비유하면 4바이트 규격으로 포장된 부품 상자를 2바이트 규격이라고 적어 두고 읽는
것이다. 상자 안의 값이 다른 값으로 보이고, 순서대로 읽는 파일에서는 뒤에 이어진
가중치의 시작 위치까지 어긋날 수 있다. 결국 이 PR이 고치려는 FP16 모델이 다시
쓰레기 출력을 만들 수 있다.

수정할 때는 두 부분을 함께 처리해야 한다.

1. gamma는 모델 파일 형식대로 FP32로 요청한다.
2. CUDA 커널이 `FP16 input + FP32 gamma`를 직접 지원하거나, FP32를 올바르게 읽은 뒤
   안전하게 만든 FP16 사본을 사용한다.

gamma만 FP32로 바꾸면 현재 GPU 조건인 `gt == FP16`을 통과하지 못해 CPU fallback으로
빠지므로 절반짜리 수정으로는 충분하지 않다.

### P1 — device-only activation에서 CPU fallback이 GPU 주소를 직접 읽음

위치:

- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:79-110`
- `nntrainer/tensor/manager.h:128-146`
- `nntrainer/cuda_mem_allocator.cpp:84-100`

현재 CUDA 커널은 다음 조건을 모두 만족할 때만 사용된다.

- input, output, gamma가 모두 FP16
- 행 수가 32개 이하

그 밖의 경우에는 `rmsnorm_rows()`라는 CPU 반복문으로 내려간다. 따라서 보통 prefill처럼
행이 32개보다 많거나, 현재 저장소의 여러 FP32 activation 설정에서는 CPU 경로를 탄다.

그런데 `NNTR_CUDA_DEV_ACT=1`을 켜면 discrete GPU의 activation pool은
`cudaMalloc`으로 만든 device-only 메모리가 된다. 이 주소는 GPU는 읽을 수 있지만 CPU가
일반 포인터처럼 역참조할 수 없다. 새 fallback은 이 주소를 그대로 `in.getData()`와
`out.getData()`로 받아 CPU에서 읽고 쓴다.

비유하면 “GPU 직원만 출입 가능한 창고”의 선반 번호를 CPU 직원에게 주고 직접 물건을
가져오라고 하는 셈이다. `finishIfAsync()`는 앞선 GPU 작업이 끝날 때까지 기다릴 뿐,
물건을 CPU가 읽을 수 있는 장소로 옮겨 주지는 않는다. access violation/segfault 또는
정의되지 않은 동작으로 이어질 수 있다.

권장 수정:

- device-only 포인터라면 행 수 제한과 관계없이 GPU 커널을 사용한다.
- FP32와 `FP16 input + FP32 gamma` 커널도 마련한다.
- CPU fallback이 꼭 필요하면 명시적인 device-to-host 복사와 결과의 host-to-device
  복사를 거친다.
- device-only 상태에서 커널 생성이나 실행 요청이 실패했다면 접근 불가능한 CPU
  fallback으로 조용히 내려가지 말고, 안전한 복사 경로를 쓰거나 명확한 오류를 낸다.

### P2 — `NNTR_CUDA_PACE` 모드에서는 CPU가 아직 끝나지 않은 GPU 결과를 읽을 수 있음

위치:

- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:93-96`
- `nntrainer/cuda/cuda_stream_manager.cpp:112-149`
- `nntrainer/cuda/cuda_stream_manager.cpp:151-158`

CPU fallback 직전에는 `finishIfAsync()`를 호출한다. 이 함수는
`NNTR_CUDA_ASYNC=1`일 때만 GPU 작업이 끝날 때까지 기다린다.

그러나 `NNTR_CUDA_PACE`를 켜면 async가 꺼져 있어도 최근 N개의 GPU 작업을 완료시키지
않은 채 다음 레이어로 넘어갈 수 있다. 이 상태에서 RMSNorm이 CPU fallback으로 오면
`finishIfAsync()`는 아무것도 하지 않고, CPU가 아직 GPU가 쓰는 중인 입력을 읽는다.

비유하면 “비동기 배달” 표지가 있을 때만 트럭 도착을 기다리는데, 별도의 “묶음 배달”
모드에서도 트럭이 늦게 온다는 사실을 빠뜨린 것이다. CPU가 메모리를 읽는 경계에서는
모드와 관계없이 전체 stream을 비우는 `finish()`를 사용해야 한다.

### P2 — 레이어 속성과 기본 gamma 초기화 계약이 기존 RMSNorm과 다름

위치:

- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.h:51-56`
- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:40-41`

새 레이어는 `epsilon`과 `skip_prefill`만 읽고, 남은 속성을 검사하지 않고 버린다.
그 결과 다음 문제가 생긴다.

- `gamma_initializer=ones` 같은 정상 속성이 조용히 무시된다.
- gamma initializer는 항상 `NONE`으로 요청된다.
- `epslion=...` 같은 오타도 오류가 나지 않고 기본값으로 실행된다.

기존 OpenCL RMSNorm은 `GammaInitializer`를 읽어 weight 요청에 적용하고, 기존 CausalLM
RMSNorm은 모르는 속성이 남으면 오류를 낸다. 모델 파일에서 가중치를 불러오는 CausalLM
실행에서는 initializer가 덮어써지지만, 파일을 불러오지 않고 일반 레이어로 사용하는
경우에는 초기화되지 않은 gamma 때문에 출력이 틀릴 수 있다.

drop-in replacement라면 기존과 같은 속성을 지원하고, 지원하지 않는 값은 조용히
버리지 말고 명확한 오류를 내야 한다.

### P3 — 두 번째 대화의 여러-token prefill을 `skip_prefill`이 알아보지 못함

위치:

- `nntrainer/layers/cuda_layers/cuda_rmsnorm_layer.cpp:121-125`
- 비교 기준 `Applications/CausalLM/layers/rms_norm.cpp:60-64`
- `Applications/CausalLM/models/causal_lm.cpp:550-575`

CUDA 구현은 `skip_prefill=true`일 때 `from == 0`인 호출만 건너뛴다. 기존 CPU 구현은
`from == 0`뿐 아니라 `to - from > 1`, 즉 여러 token을 한꺼번에 처리하는 호출도
prefill로 본다.

같은 CausalLM 객체로 두 번째 대화를 실행하거나 미리 계산한 system prompt를 쓰면,
prefill 시작점 `from`은 0보다 크면서 처리할 token은 여러 개일 수 있다. 이때 CUDA
RMSNorm만 불필요하게 계산하고 출력을 덮어쓴다.

현재 Gemma4의 KV 공유 블록에서는 뒤 레이어들도 함께 건너뛰므로 곧바로 최종 오답이
된다고 단정할 수는 없다. 그래도 기존 레이어의 계약과 다르며, 앞으로 출력이 소비되는
구성이 생기면 잘못된 값이 전달될 수 있다. 기존과 같이
`!from || (to - from) > 1`로 판정하는 편이 맞다.

## 구현 설명과 실제 코드가 다른 부분

PR은 행이 많은 prefill을 “multi-threaded host path”로 보낸다고 설명한다. 그러나 새
`rmsnorm_rows()`는 ThreadManager나 병렬 실행을 쓰지 않는 단순 직렬 반복문이며, 기존
CPU backend intrinsic도 호출하지 않는다.

정확도 결함은 아니지만 `rows > 32`를 무조건 CPU로 보내는 성능 선택의 근거가 코드와
측정 결과로 확인되지 않았다. 실제 prefill benchmark로 경계값과 성능 주장을 검증해야
한다.

## 확인한 정상 부분

- CUDA RMSNorm의 `sum(x²)`은 FP32로 누적되며 기본 RMSNorm 수식은 맞다.
- custom half→float 변환은 가능한 65,536개 half bit pattern을 모두 비교했고, 반대
  변환은 경계값과 임의 finite float 약 200만 개를 IEEE 반올림 기준과 비교해 별도
  불일치를 찾지 못했다.
- 한 block이 한 행을 처리하는 인덱싱, 256-thread reduction, batch/channel을 행으로
  접는 계산에서 별도 오류는 찾지 못했다.
- Meson 소스 연결은 `enable-cuda` 안에만 있어 비-CUDA 빌드로 새 소스가 새지 않는다.
- 직접 변경 파일은 clang-format 14 dry-run과 `git diff --check`를 통과했다.
