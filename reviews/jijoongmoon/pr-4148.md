## 한눈에 보기

이 PR은 긴 프롬프트를 한꺼번에 처리하는 full-attention prefill을 Intel GPU의
XMX/DPAS 행렬 연산기로 빠르게 계산하는 길을 추가한다. 직접 변경분은 2개 파일,
572줄 추가와 45줄 삭제이다.

비유하면 기존 일반 계산대 옆에 “행렬 계산 전용 고속 계산대”를 만든 것이다. 타일
인덱스, GQA head 선택, causal 위치 계산, 마지막에 남는 query/key 처리와 메모리
범위를 직접 따라가 본 결과, 새 계산대 안쪽의 기본 계산에서는 확정 오류를 찾지
못했다.

가장 큰 문제는 입구의 안내원이다. 지금 코드는 “DPAS라는 기능이 있다”는 표지만
보고 모든 장치를 **16명 단위로 움직이는 계산대**에 보낸다. 하지만 공식 규격에는
DPAS 기능은 있어도 8명 단위를 요구하는 장치가 존재한다. 이런 장치에서는 새
경로가 기본으로 켜져 OpenCL kernel 빌드 실패, 정의되지 않은 동작 또는 잘못된
출력이 날 수 있다.

또한 이 branch 안에는 `flash_attention_prefill_f16_cl()`을 부르는 코드가 아직
없다. 따라서 현재 저장소의 CausalLM 실행이 바로 망가지는 회귀는 아니지만, 새
기능을 다음 PR에서 연결하거나 API를 직접 부르면 문제가 드러나는 **잠재
blocker**이다.

## 직접 변경분의 문제

### P1 — DPAS 확장 기능의 존재만 보고 SG16 전용 kernel을 기본으로 켬

위치:

- `nntrainer/cl_context.cpp:109-111`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2697-2718`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:967`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1056`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1155`

`caps().dpas`는
`cl_intel_subgroup_matrix_multiply_accumulate` 확장 문자열이 있는지만 확인한다.
새 dispatch는 이 값이 참이면 XMX를 기본으로 선택한다. 그러나 새 kernel은 다음과
같이 subgroup 크기 16과 그에 맞는 operand 형식을 고정한다.

```text
intel_reqd_sub_group_size(16)
short4/short8 A operand
```

[Khronos의 공식 확장 규격](https://registry.khronos.org/OpenCL/extensions/intel/cl_intel_subgroup_matrix_multiply_accumulate.html)은
최소 subgroup 크기가 8인 장치와 16인 장치를 모두 정의한다. 최소 크기가 8인
장치에서는 이 행렬 함수를 subgroup 8로 호출해야 하며, 다른 크기로 호출한 결과는
정의되지 않는다고 명시한다. 즉 “DPAS 지원”과 “이 SG16 kernel 지원”은 같은
질문이 아니다.

비유하면 건물에 엘리베이터가 있다는 표지만 보고 무조건 16인승일 것이라고
판단한 셈이다. 실제 엘리베이터가 8인승 규칙을 따른다면 문이 열려 있어도 16명씩
태우는 운행 방식은 사용할 수 없다.

기기가 요구하는 최소 subgroup 크기를 조회해 SG8과 SG16 kernel을 구분해야 한다.
SG8 변형을 아직 만들 수 없다면 현재 SG16 경로는 최소 크기 16인 장치에서만
켜고, 나머지는 기존 block-Q 경로로 안전하게 돌아가야 한다. kernel 등록이나
빌드가 실패했을 때도 block-Q로 재시도하는 것이 좋다.

### P2 — `NNTR_DETERMINISTIC=1`이 새 XMX 경로에는 적용되지 않음

위치:

- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2618-2625`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2716-2718`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1126-1130`

같은 함수의 기존 block-Q 경로는 `NNTR_DETERMINISTIC=1`일 때 GPU vendor가 내부
덧셈 순서를 정하는 subgroup reduction을 끄고, 순서가 고정된 LDS tree를
선택한다. 그런데 바로 아래의 `use_xmx` 조건은 이 설정을 보지 않는다. XMX
kernel도 `sub_group_reduce_max/add`를 사용하므로 DPAS 장치에서는 deterministic
설정을 켜도 다시 subgroup 경로로 들어간다.

비유하면 “항상 같은 순서로 계산” 스위치가 기존 고속도로만 막고, 새로 만든
고속도로는 그대로 열어 둔 상태다. PR 본문의 2회 byte-identical 측정은 해당
장치에서 반복 실행 결과가 같았다는 좋은 관찰이지만, 다른 driver와 장치에서도
설정의 약속을 구조적으로 보장하지는 않는다.

deterministic 모드에서는 기본 XMX 선택을 끄고 LDS-tree block-Q로 돌아가거나,
사용자가 `NNTR_FLASH_XMX=1`을 명시한 경우에만 XMX를 강제하도록 조건을 정리하는
것이 안전하다.

### P2 — `NNTR_FLASH_FP16_SCORE` 설정을 XMX만 무시함

위치:

- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2776-2788`
- `nntrainer/tensor/cl_operations/cl_kernels/flash_attention.cl:1117-1129`

`NNTR_FLASH_FP16_SCORE=1`은 softmax에 넣기 전에 score를 FP16으로 한 번 줄여서
기존 3-kernel 계산과 같은 정밀도를 비교하기 위한 진단 설정이다. host는
`FLASH_FP16_SCORE` compile option을 XMX program에도 전달하지만, XMX kernel은
이 macro를 전혀 확인하지 않고 항상 FP32 score를 사용한다.

“두 계산기 모두 소수 둘째 자리에서 반올림하라”는 비교 설정을 켰는데 새
계산기만 반올림하지 않는 것과 같다. 특히 XMX CHECK를 함께 켜면 기준 block-Q와
XMX가 서로 다른 계산 규칙을 사용하므로, 관찰된 차이가 인덱스 오류인지 단순한
정밀도 차이인지 구분할 수 없다.

XMX에도 기존 block-Q와 같은 FP16 cast를 넣거나, 이 설정이 켜졌을 때는 XMX를
끄는 편이 명확하다.

### P2 — XMX CHECK가 안전하게 메모리를 읽지 않고 NaN도 성공으로 처리할 수 있음

위치:

- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2924-2938`
- `nntrainer/tensor/cl_operations/attention_kernels.cpp:2977-3013`
- `nntrainer/opencl/opencl_context_manager.cpp:107-128`

기본 SVM allocation은 fine-grain이 아니라 coarse-grain이다. 이 메모리를 GPU가
쓴 뒤 CPU가 읽으려면 blocking SVM map으로 소유권과 가시성을 넘겨받아야 한다.
CHECK 코드는 `clFinish()`만 한 뒤 `O_host`를 바로 읽고, 다음 GPU 실행 전 unmap도
하지 않는다. `clFinish()`는 GPU 작업이 끝날 때까지 기다리는 동작이지,
coarse-grain SVM을 CPU가 읽을 수 있도록 map하는 동작은 아니다.

비유하면 GPU 작업자가 일을 마칠 때까지 기다리기는 했지만, 창고 열쇠를 CPU에게
돌려받지 않고 안의 물건을 확인하는 셈이다. 일부 driver에서 우연히 보일 수
있어도 OpenCL의 coarse-grain 계약에 맞지 않는다.

비교식에도 별도 문제가 있다.

```text
dd = fabs(xmx - reference)
if (dd > max_diff) ...
if (dd > 0.02) ...
```

둘 중 하나가 NaN이면 `dd`도 NaN이고 두 비교는 모두 거짓이다. 양쪽이 무한대일
때의 `Inf - Inf`도 마찬가지다. 최악에는 출력이 NaN이어도
`maxdiff=0, over_tol=0`이라는 깨끗한 결과를 출력할 수 있다.

CHECK 전후에 coarse-grain SVM map/unmap을 넣고, 두 값을 `std::isfinite()`로
먼저 검사해 NaN/Inf를 별도 실패로 세어야 한다.

## 현재 branch에서 확인된 범위

- XMX는 block-Q가 켜져 있고, causal이며, 실질적인 sliding window가 없고,
  `head_dim`이 16의 배수이면서 512 이하일 때만 선택된다.
- `NNTR_FLASH_XMX=0`은 정상적으로 기존 block-Q로 돌아간다.
- non-causal과 실제 sliding-window 호출은 XMX로 가지 않는다.
- `head_dim=128/256/512`, GQA mapping, resumed prefill의
  `q_pos_off=N_kv-M`, 마지막 query/key tile과 OOB 경계를 수식으로 확인했다.
  이 부분에서는 확정 오류를 찾지 못했다.
- `flash_attention_prefill_f16_cl`의 저장소 안 caller와 XMX 전용 test는 0개다.
- `.cl` 파일은 C++ 문자열로 포함되며 XMX program은 실제 호출 시
  `clBuildProgram`으로 runtime compile된다. 따라서 현재의 green CI는 새 XMX
  kernel을 OpenCL compiler로 컴파일하거나 실행했다는 증거가 아니다.
- PR 본문도 성능과 CHECK 결과가 이 branch 자체가 아니라 이 코드를 가져온
  development tree에서 측정됐고, 현재 branch는 compile-only라고 밝힌다.

최소한 다음 검증이 필요하다.

1. 최소 subgroup 8 장치와 16 장치의 dispatch/fallback test
2. 현재 head에서 XMX runtime compile 및 작은 tensor의 CPU/block-Q 비교
3. tail `M`, tail `N_kv`, GQA, `d=128/256/512` 비교
4. NaN을 의도적으로 넣어 CHECK가 실패를 보고하는 test
5. `NNTR_DETERMINISTIC`과 `NNTR_FLASH_FP16_SCORE` 설정별 선택·출력 test

## 최종 판단

새 XMX kernel의 기본 타일 계산은 자세히 살펴본 범위에서 일관성이 있었다.
하지만 “DPAS 기능이 있으면 SG16 경로를 기본으로 켠다”는 장치 선택 조건은 공식
규격보다 넓고, 합법적인 DPAS 장치에서 새 기능의 핵심 경로를 실패시킬 수 있다.
먼저 subgroup 요구 조건을 정확히 구분하고 안전한 fallback을 넣어야 한다.

그 뒤 현재 branch에서 실제 runtime compile과 수치 비교를 수행해야 한다. 특히
현재 CHECK는 coarse-grain SVM과 NaN을 안전하게 다루지 못하고 비교 설정 하나도
XMX에 적용되지 않으므로, 지금 출력만으로 correctness를 입증했다고 보기 어렵다.
또한 전체 PR을 병합하려면 누적 stack의 unresolved blocker도 함께 해결해야 한다.
