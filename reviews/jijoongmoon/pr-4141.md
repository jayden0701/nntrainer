## 한눈에 보기

이 PR은 `NNTR_MEM_PLANNER=basic|v1|v2|v3` 환경 변수로 메모리 배치 방법을
선택하게 한다. 변경은 `manager.cpp` 한 파일, 20줄 추가와 8줄 삭제다.
환경 변수를 지정하지 않으면 기존 V1을 쓰므로 기본 동작은 바뀌지 않는다.

문제는 새로 선택 가능해진 V2가 일부 학습용 gradient의 사용 시간을 잘못 비교한다는
점이다. 겹치는 두 gradient에 같은 메모리 자리를 줄 수 있다. 단순한 배열에서는 마지막
검사가 오류를 내지만, 요청 순서에 따라 검사가 충돌을 놓쳐 학습값이 조용히
덮어써지는 경우까지 직접 재현했다.

## 발견 사항

### P2 — V2가 동시에 살아 있는 두 gradient에 같은 메모리를 줄 수 있음

위치:

- `nntrainer/tensor/manager.cpp:921-931`
- `nntrainer/tensor/manager.cpp:421-432`
- `nntrainer/tensor/manager.cpp:483-493`
- `nntrainer/tensor/optimized_v2_planner.cpp:224-260`
- `nntrainer/tensor/memory_pool.cpp:106-109`
- `nntrainer/tensor/memory_pool.cpp:317-330`

V2는 큰 weight gradient부터 빈 자리를 찾는다. 그런데 두 사용 시간의 일부 겹침만
검사하고, 한 구간이 다른 구간을 통째로 감싸는 경우를 놓친다.

예를 들어 큰 gradient가 7시부터 10시까지 사물함을 쓰고, 작은 gradient가 1시부터
10시까지 쓴다고 하자. 두 예약은 분명 7~10시에 겹친다. 현재 V2는 이를 겹치지
않는다고 판단해 같은 사물함 번호를 준다.

이 형태는 억지 예가 아니다. 역전파에서는 layer마다 gradient 계산 시작 시점이
다르다. global-norm clipping이나 mixed precision을 쓰면 여러 gradient의 종료 시점이
`PERSIST_END_ORDER`까지 같이 늘어난다. 따라서 `[늦은 시작, 같은 끝]` 구간을
`[이른 시작, 같은 끝]` 구간이 감싸는 모양이 실제 학습 그래프에서 생길 수 있다.

두 가지를 실제 planner로 확인했다.

1. gradient 두 개만 둔 경우

   - 크기와 시간: `128 [7,11)`, `64 [0,11)`
   - 결과: 두 offset이 모두 `0`, 계획 크기는 `128`
   - 같은 시간에 필요한 크기는 `192`이므로 `MemoryPool`이 오류를 내고 멈춤

2. 중간에 일반 tensor 하나가 있는 경우

   - 요청 순서: `gradient 100 [7,10)`, `일반 tensor 500 [1,2)`,
     `gradient 80 [1,10)`
   - 결과 offset: `500, 0, 500`
   - 계획 크기 `600`, 최소 필요량 `580`으로 검사를 통과
   - 실제 할당 뒤 두 gradient의 포인터가 같았음

두 번째 경우가 더 위험하다. 마지막 안전 검사도 정렬한 목록을 만들어 놓고 내부
반복에서는 정렬 전 번호를 사용한다. 중간에 다른 요청이 끼면 충돌 쌍을 건너뛸 수
있다. 오류 메시지도 없이 두 gradient가 같은 칸에 쓰므로 학습 결과만 조용히
틀어질 수 있다.

따라서 PR 주석의 “잘못 배치하면 `validateLayout()`이 항상 크게 실패한다”는 설명은
맞지 않는다. GitHub에 이미 달린
[`Don't expose V2 for training tensor pools`](https://github.com/nntrainer/nntrainer/pull/4141#discussion_r3643388647)
리뷰는 핵심과 P2 우선순위가 적절하지만, 실제 위험은 그 댓글보다 크다.

기본 V1은 그대로이고 사용자가 `NNTR_MEM_PLANNER=v2`를 명시해야만 이 경로에
들어가므로 P1보다는 P2가 알맞다.

권장 수정:

1. V2의 시간 겹침을 반쪽 열린 구간의 표준 식
   `a.start < b.end && b.start < a.end`로 검사한다.
2. `MemoryPool::validateOverlap()`도 정렬된 `perm`의 위치끼리 비교하도록 고친다.
3. 두 수정 전까지는 학습 모드의 `v2` 선택을 거부하거나 V1으로 되돌린다.
4. 위 두 재현과 persistent-gradient 학습 모델을 회귀 테스트로 추가한다.

### P2 — `getenv()`가 준 주소를 영구 보관해 실행 중 설정 변경에 안전하지 않음

위치:

- `nntrainer/tensor/manager.cpp:921-922`

코드는 환경 변수의 문자열 값을 복사하지 않고 `getenv()`가 돌려준 주소를
`static const char *`에 저장한다.

```cpp
static const char *planner_env = std::getenv("NNTR_MEM_PLANNER");
```

두 가지 문제가 있다.

- 첫 model을 만들 때 변수가 없었다면, 나중에 `v3`로 설정해도 저장된 값은 계속
  `nullptr`라서 V1을 쓴다.
- 처음에는 값이 있었더라도 실행 중 환경 변수를 바꾸면 C runtime이 이전 문자열
  공간을 재사용할 수 있다. 저장한 주소가 오래된 값이나 엉뚱한 값을 가리킬 수 있다.

Windows UCRT에서 `v2`의 주소를 저장한 뒤 더 긴 값으로 교체하고 환경 저장소를
사용하게 하자, 이전 주소의 내용이 다른 문자로 바뀌는 것을 재현했다.

비유하면 설정 내용을 수첩에 베낀 것이 아니라, 포스트잇이 붙어 있던 벽의 위치만
기록한 셈이다. 누군가 포스트잇을 떼거나 바꾸면 그 위치에는 다른 글이 있을 수 있다.

프로세스를 새로 시작하면서 환경 변수를 고르는 일반적인 사용은 괜찮다. 같은
프로세스에서 여러 model을 만들어 A/B하려는 경우가 문제다. 시작할 때 한 번만 읽는
정책이면 `static const std::string`으로 즉시 복사하고 그 정책을 문서화해야 한다.
실행 중 변경도 지원하려면 호출할 때마다 환경 값을 즉시 지역 `std::string`으로
복사해야 한다.

## 범위와 설명에서 확인할 점

- 제목은 “activation pool 선택기”라고 하지만 같은
  `finalizeTensorPool()`이 weight pool과 activation/gradient pool에 모두 쓰인다.
  실제로 weight pool이 먼저 선택값으로 배치된다. activation만 비교하려는 목적이면
  두 pool을 구분해야 하고, 둘 다 바꾸려는 목적이면 제목과 측정 설명을 고쳐야 한다.
- PR은 V3를 `best-fit`이라고 설명하지만 구현은 주소가 낮은 빈칸부터 보다가 처음
  들어가는 곳을 고르는 `first-fit`이다. 관찰한 메모리 증가 현상은 가능하지만,
  원인 설명과 알고리즘 이름은 바로잡아야 한다.
